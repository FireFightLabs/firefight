# New branch and PR

Opening the PR is the end of this workflow. Merging is a separate, explicit instruction.

## 1. Start from a main that is actually current

```bash
git pull --ff-only origin main
```

Do this even if you merged something minutes ago. `gh pr merge` merges on GitHub and then fails to fast-forward the local branch, because it pulls through the `github` remote which has no SSH configured. Local `main` is stale far more often than it looks, and branching off it silently reintroduces reverted code.

Branch names follow the existing convention: `fix/<kebab-summary>` or `feat/<kebab-summary>`.

## 2. Implement

Keep the branch to one change set. If a second problem surfaces mid-flight, note it and either finish the first or say plainly that you are widening scope.

## 3. Regenerate what the change implies

These are part of the change, not a follow-up. Forgetting either breaks the app at import time rather than at test time.

- Touched `config/routes.rb` → `bin/rails js:routes:typescript`
- Added or edited a serializer → `bundle exec rake types_from_serializers:generate`

## 4. Verify, in three passes

**Backend.** `PGGSSENCMODE=disable bin/ci` (the env var is required locally or PG auth hangs).

**Frontend.** `bin/ci` does not run eslint or tsc, so green CI says nothing about the frontend:

```bash
npm run lint
npx tsc --noEmit
```

**The page itself.** Green CI never renders a pixel. Open the screen at `https://ff.bugrewind.com` (not `localhost:3000`, the session lives on the tunnel) and look at it. If you did not look, say so in the PR body rather than implying you did.

Two traps that make local and CI disagree:

- A test that renders an Inertia page with a plain `get` needs a built Vite manifest, which the CI test job does not produce. Use `inertia_headers` from `test/support/inertia_test_helper.rb` and assert on the returned component name.
- A Tailwind class used only in a shared component sometimes never gets generated by the dev watcher, so it sits on the element doing nothing. Probe for the rule before rewriting layout code, and restart `bin/dev` if it is missing.

## 5. Commit and push

Focused commits. The message explains why the change is right, not what the diff shows. End with:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
Claude-Session: <session url>
```

## 6. Open the PR

The body states what changed, why this approach over the alternative, and a verification section that separates what was checked from what was not. Naming the gap is the point: silence reads as complete.

## 7. Stop

**Never merge without an explicit instruction to merge in the current message.** Opening a PR when asked to build something is expected. Merging is always the user's call, every time. A bug report, an approval on a previous PR, or an obvious-looking green build are none of them permission.

## When merging is explicitly requested

1. Wait for checks: `gh pr checks <n> --watch --interval 15`. Do not merge on a partial pass.
2. `gh pr merge <n> --squash --delete-branch`
3. Expect `Could not read from remote repository` and `not possible to fast-forward`. The merge still succeeded. Confirm with `gh pr view <n> --json state` before reporting a failure.
4. `git pull --ff-only origin main`

## Guardrails

- One change set per branch.
- If CI fails, read the failure and fix the cause. Never merge through a red check.
- Report outcomes faithfully. If tests fail, show the output. If a step was skipped, say which.
