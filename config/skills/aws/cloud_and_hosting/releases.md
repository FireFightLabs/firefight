On the resource map a CodePipeline pipeline is a pipeline, a CodeDeploy deployment group a release flow named application/group, and a CloudFormation stack a stack. What each releases is linked to it as released by: the ECS service, deployment group, stack or Elastic Beanstalk environment a pipeline's deploy actions name, the ECS services a deployment group lists, and every resource a stack made. App Runner services and Elastic Beanstalk environments are services beside ECS's.

1. Runs. `run_history` on a pipeline lists its executions, on a deployment group its deployments, on a stack its operations (create, update, delete), on an App Runner service its operations and on an Elastic Beanstalk environment its deploys, newest first, with how long finished ones usually take. With `run` it reads one with its steps: a pipeline execution's actions, a deployment's lifecycle events (or one step per instance for EC2), a stack operation's resources, an environment's events. To follow a release as it goes, start a watch on it with run_history: it hears the first step that fails and reads that step's log.
2. Why a step failed. Each step names its error, and its log is read the way the step says: a CodeDeploy action reads the deployment with its lifecycle events, a CloudFormation action the stack's operations, an ECS action or an ECS deployment's lifecycle event the service's logs over its time. A stack's failed resource carries CloudFormation's reason, which is usually enough, and the first one that failed is the cause, the rest failed after it. An App Runner deployment's log is its service log group, and an Elastic Beanstalk deploy's is its instances' eb-engine.log when the environment streams logs to CloudWatch Logs.
3. When a pipeline execution failed in a deploy action, read the release the action ran (the deployment group's deployment or the stack's operation), since that holds the cause.
4. Stop or roll back what is going now:
   - an ECS deployment still going: `rollback` on the service with `to` set to the deployment's id from `recent_deploys` stops it and rolls the service back to the revision it ran before. `stop_service_deployment` with mode abort stops it where it is.
   - a stage of a pipeline: `rollback` on the pipeline with `to` set to an earlier execution that succeeded there, as stage:execution, such as Deploy:1a2b3c4d-..., or the execution alone when one stage deploys. Only a V2 pipeline can.
   - a CodeDeploy deployment still going: `rollback` on the deployment group with `to` set to the deployment's id stops it and rolls back what it changed. `stop_codedeploy_deployment` with roll_back false stops it and leaves what it changed.
   - a stack update still going: `rollback` on the stack with `to` set to the operation's id cancels it, and CloudFormation rolls the stack back to how it was.
   - a pipeline execution: `stop_pipeline_execution` lets the actions going finish, and with abandon stops them at once, which can leave a deployment half done.
5. An App Runner service and an Elastic Beanstalk environment are read, not changed. Their logs are in CloudWatch Logs, read with logs_insights_query on the log group their run history names.
