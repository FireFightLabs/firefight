---
name: watching
when: The person asks to be told later, such as when a run finishes, a build or deploy starts or succeeds, or a resource comes back, or they just started something that takes a while
tools: [get_resource_map, search_map]
---
1. Find each thing to follow on the map with `get_resource_map` or `search_map`: the repository whose CI run it is, the service whose build or deploy it is. A run the person names by number keeps that number.
2. Plan the steps in the order they happen, one per thing the person asked to hear about. A CI run, a build or a deploy is a step reading run_history with its resource, a name such as release, build or deploy when the resource has several kinds of runs, and the run: when you started it or can identify it (the person gave its number, a tool answer named its id, or the run carries a name you know, such as one made from the tag the release pushed), always pass its id, number or own name, so the watch follows that exact run rather than whichever run of that name starts next. A provider's workflow or pipeline that is on the map is followed the same way with run_history on it, which reads the run's state as the provider gives it rather than judging a list of runs. For a code host's CI, run_history with the run is the read, since it brings the run's jobs. Set report_start on a step when they asked to hear when it starts.
3. Order the steps the way the work happens, from what the person said or the runbook gives. A step that only means something once another is done waits for it with waits_for, by its label or number: a run another run starts waits for the run that starts it, a deploy waits for the run that ships it, and a health check or a log check waits for the deploy it checks, so it reads the new containers rather than the old ones. Steps that happen side by side, such as two services deploying from one release, wait for the same step and not for each other. A step that waits is not read until what it waits for succeeded, and is skipped when that fails, so the watch ends on the real failure. When the person says "watch X, then Y and Z together, then W once Y passed", that is X, then Y and Z each waiting for X, then W waiting for Y.
4. Anything else is "keep checking X until Y": a step with any read you can make in this chat, and the question in plain words as goal, such as every instance of web runs the new version, or the error rate stays under 1% for ten minutes. A model judges it over the step's recent readings, so add done_when or failed_when to say what to look for, such as status success. When the answer is long and one part says how it stands, name that part as focus, a dotted path into its JSON such as data.status or data.nodes. A resource coming back or settling reads resource_status or another capability. A logs step judges failure by error-level lines, so name in failed_when what an error looks like rather than any warning. A step that waits for a deploy, a rollout or a release to go live counts only a deploy newer than the one live when the watch starts, so pass new_deploy on it with the version you expect whenever you know it: the commit the release run built (a run's line in run_history names it), the tag it pushed, or the branch it deploys from, and {} when any newer deploy will do. On a step reading with a tool, name the resource deployed in new_deploy too. Anything run_history does not hold, such as a provider's workflow run when its history only lists builds, is a step naming a read tool you hold as tool, with its arguments, such as the provider's API request with method GET for that one run's address by its id (workflows/release/runs/<id>), or for the workflow's newest run when its id is not known yet. When run_history answers that it holds no runs of the name you gave, it says which it does hold, so switch to a read tool at once. Find the address in the provider's skill and guides or with search_docs before the web, and try the read once yourself before you start the watch, so you know it shows the thing. A tool that can also change things only reads in a watch. A page that should load cleanly, such as after a fix, is a step naming check_in_browser as tool with its url and one screen size as arguments, and a goal such as the page loads with no console errors.
5. Pass minutes only when the person asked for how long to watch, at most a day. When run history cannot show how long it takes, recall what you remember and pass expected_minutes from it, and pass nothing when you remember nothing. Pass reads_per_hour only when the provider's documented rate limit or cost is tighter than the default.
6. Call start_watch with a title naming what it waits on, such as Deploy finished or Release run #46 passed, which shows as Watch "Deploy finished", the steps, and purpose: why the person wants it, in their words, such as get GitHub releases deploying through the webhook again. Every line the watch says measures what happened against it. Keep one watch per subject. When a watch is already going in this chat on the same release, deploy, run or incident, such as the release build when you are about to watch its rollout and the health checks after, pass add_to with that watch's id and these steps join it, its time limit moving to leave them time. Something unrelated going at the same time, such as a database backup during a release, is its own watch: pass separate true. While a watch is going, start_watch asks you to choose before it starts anything.
7. Tell the person what it answered: how long it usually takes and how long you will watch, its ceiling on reads, and anything it cannot follow and why. In the dashboard chat the watches going show in the Watching strip above the message box, each opening to its card, so point there rather than drawing a table of them. Then stop. Each milestone and the end come to the chat and their direct messages on their own: each job or step as it starts or passes, in one short line per check, the first one that fails at once with its reason, and a reading moves to running as soon as it shows the thing has begun.
8. When a step's read finds nothing to follow, such as a run that never shows up in its history or a first reading that is not the thing at all, the watch hands it back to you. Find a different read, try it once, and call repair_watch with the watch, the step, the new read and why the old one showed nothing, so the same watch follows it from here. When no read can show it, call repair_watch with give_up. The same read again is refused, since it already showed nothing. Never start a second watch for the same thing.
9. A reading you take now beats what a watch remembers. When the person asks how it is going, read list_watches, which reads each watch that is still going again first. When a reading you took disagrees with what a watch or you said before, say so plainly and go by the fresh reading, and when it shows the watch follows the wrong thing, repair it. When the person corrects how a step or the watch ended, or a reading you took shows the ending was wrong, such as a check judged on the old deploy's logs, check it with a fresh read, then reopen that step with repair_watch and reopen true, with a better read when the old one was the cause, so the watch follows it again rather than the wrong ending being repeated. When they ask for longer, call extend_watch with the minutes in all, at most a day. When they ask to stop, call stop_watch.
