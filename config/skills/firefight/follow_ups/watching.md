---
name: watching
when: The person asks to be told later, such as when a run finishes, a build or deploy starts or succeeds, or a resource comes back, or they just started something that takes a while
tools: [get_resource_map, search_map]
---
1. Find each thing to follow on the map with `get_resource_map` or `search_map`: the repository whose CI run it is, the service whose build or deploy it is. A run the person names by number keeps that number.
2. Plan the steps in the order they happen, one per thing the person asked to hear about. A CI run, a build or a deploy is a step reading run_history with its resource, a name such as release, build or deploy when the resource has several kinds of runs, and the run: when you started it or can identify it (the person gave its number, a tool answer named its id), always pass its id or number, so the watch follows that exact run rather than whichever run of that name starts next. For a code host's CI, run_history with the run is the read, since it brings the run's jobs. Set report_start on a step when they asked to hear when it starts. A resource coming back or settling is a step reading resource_status, or another read, with done_when or failed_when as words its answer would hold, and a goal sentence for anything words cannot decide.
3. Anything run_history does not hold, such as a provider's workflow run when its history only lists builds, is a step naming a read tool you hold as tool, with its arguments, such as the provider's API request with method GET for that one run's address by its id (workflows/release/runs/<id>), never a list of recent runs. Find the address in the provider's skill and guides or with search_docs before the web. A tool that can also change things only reads in a watch. It needs done_when, failed_when or goal like any other read.
4. Pass minutes only when the person asked for how long to watch, at most a day. When run history cannot show how long it takes, recall what you remember and pass expected_minutes from it, and pass nothing when you remember nothing.
5. Call start_watch with a short title, such as release run #46 and the deploy, the steps, and purpose: why the person wants it, in their words, such as get GitHub releases deploying through the webhook again. Every line the watch says measures what happened against it.
6. Tell the person what it answered: how long it usually takes and how long you will watch, and anything it cannot follow and why. Then stop. Each milestone and the end come to the chat and their direct messages on their own: each job or step as it starts or passes, in one short line per check, the first one that fails at once with its reason, and a reading moves to running as soon as it shows the thing has begun. When a run never shows up in its history, the watch hands it back to you within minutes: find the run another way and start a new watch with a read tool step and the same purpose.
7. When they ask how it is going, read list_watches and answer from it. When they ask for longer, call extend_watch with the minutes in all, at most a day. When they ask to stop, call stop_watch.
