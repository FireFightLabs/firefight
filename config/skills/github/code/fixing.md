---
name: github_fixing
when: Writing a code change with Firefight's own coding agent, in a chat or as a fix's step, especially one that touches another system's interface such as a webhook, an API, a config format or a CI trigger
tools: [fix_code]
---
1. Before designing the change, read what it depends on. When it touches another system's interface, such as a webhook, an API, a config format or a CI trigger, read that system's documented contract, from its provider's skill and guides, its own documentation tool, or its documentation with search_web, and read how it is set up now with the tools that reach it. Never design it from what such systems usually do.
2. Write the `brief` for someone who has only the repository: what to change and why, the exact error or behaviour, the files and lines, the contract and the setup you read with what each said, and a list of anything you could not verify. The person's own words and the results you read travel with it, so quote rather than summarise what matters.
3. Name the repository as owner/name in `repo`. The `title` says what the change does in plain words. The `summary` leads the pull request in one or two plain sentences: what it does and why, or, when adding to an open pull request, what this update changes. Never words about how the work was done, such as brief or session. Name a `base` when the change belongs on another branch, `pull_request` or `branch` to add it to an open one, and say in `context` what other changes in the same fix did.
4. The agent reads the connected systems as the person who asked and may ask them a question while it works, which shows under the step with its options, the one it recommends and why, and a box for anything else. Nobody answering within five minutes means the agent goes with its recommendation.
5. Its change is checked and reviewed against what the person asked before it opens. Everything is measured against the base branch, so what a merge brought from the base is never part of it. A change the review finds wrong goes back to the agent once, and one still wrong is not opened. The answer lists what was verified and how, what could not run here and why, what the review found and the open questions. Tell the person in short plain words: what the change does, what was verified, and only the open questions that matter. A check that could not run here, such as tests that need a database, is not a doubt about the change, so say it could not run and why, once, under Could not run here, and never present it as a risk. Never call it blocked or a blocker or list it under Blocked, since blocked means something stopped the change itself. The repository's own CI runs it on the pull request.
6. In a chat, call `fix_code` only once the person agreed to the change. It runs as them, and an approval rule can hold it. Give them the link the answer carries.
7. A new pull request is written on the base branch's newest commit. The agent works in a real git copy of the branch with the newest base fetched, and may commit, merge, rebase or resolve conflicts, and Firefight pushes the branch once the change is reviewed. To fix a pull request that conflicts with its base, call `fix_code` with that `pull_request` and ask in the `brief` for the base to be merged in and the conflict resolved.
8. The answer ends with what the code host says now about whether the pull request can merge and its checks. Repeat only that. Never say a conflict is resolved unless the host says it can merge.
9. Halon follows every pull request it opened until it is merged or closed, and tells the chat when one conflicts with its base, a check fails or a reviewer asks for changes, with Fix it. Fixing one is yours, with the person's yes. Never change its branch until they press Fix it or ask you to.
