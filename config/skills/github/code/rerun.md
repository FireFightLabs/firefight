---
name: github_rerun
when: Rerunning a GitHub Actions run after a failure that is not the code, starting a workflow by hand, canceling a run, such as a deploy that should not go out, reviewing a deployment waiting on an environment's reviewers, or clearing a cache
tools: [ci_status, workflow_runs, workflow_jobs, job_log, ci_runs, rerun_workflow, rerun_job, run_workflow, cancel_workflow, pending_deployments, review_pending_deployment, clear_actions_cache]
references: [actions/re-run-workflows-and-jobs.md, actions/manually-run-a-workflow.md, actions/cancel-a-workflow-run.md, actions/workflow-cancellation.md]
---
1. Each of these changes real CI, so none is done while investigating. Propose it, say what it does and why, and call it only in a chat once the person agrees. It runs as them, and an approval rule can hold it.
2. Rerun only when what failed is not the code. Read the failure first with `ci_status`, `workflow_jobs` and `job_log`. A job that failed and then passed on the same commit in `workflow_runs`, a timeout, a network error, a runner that went away, or a service the tests reach that has since come back is a reason to rerun. A failure that began with one commit and repeats on every run since is the code, so propose a fix instead, since a rerun only spends the time it takes.
3. Call `rerun_workflow` with `repo`, the run's `run_id` and `failed_only` set, so only the failed jobs and the jobs that depend on them run again and the jobs that passed are kept. Leave `failed_only` off to run every job again, such as when a job that passed used something that has since changed. Only a run that finished can run again. `rerun_job` runs one job again by its `job_id`, with the jobs that depend on it, when only that one job should run, such as one flaky job in a run that otherwise passed. `ci_runs` with `run` and `attempt` reads an earlier try of a run that ran again.
4. `run_workflow` starts a workflow by hand, such as a smoke test or a deploy, with `workflow` as its file name, `ref` for the branch or tag, and `inputs` by name. Only a workflow whose file on the default branch has a workflow_dispatch trigger can be started, and Firefight checks the inputs against the ones it declares. Starting a deploy ships whatever is on that ref, so say which commit it will deploy before the person agrees.
5. `cancel_workflow` stops a queued or running run, such as a deploy that should not go out. Say what it stops before the person agrees. A job or step whose if condition still holds, such as always(), keeps running after a cancel. Only when a run keeps going after a cancel, call `cancel_workflow` again with `force`, which stops every job at once.
6. A run whose deploy job waits on an environment's required reviewers is waiting in `ci_runs`, not queued, and shows in `pending_deployments`, with who may review it and whether Firefight's GitHub App may. `review_pending_deployment` approves or rejects it with a `comment`, only when the person asks or a runbook step says to, and only works when the App is one of that environment's required reviewers. Otherwise name the reviewers, who approve it on the run's page.
7. `clear_actions_cache` deletes the caches with a `key`, or every cache on a `ref`, such as a dependency cache that keeps a build failing after its lockfile changed. Read the job's log first to show the cache is the cause. The next run builds the cache again, so it is slower once.
8. When GitHub refuses for a missing permission, the answer names the permission. Tell the person an owner of the GitHub account grants it, and do not try again until they have.
9. Each answer links the run. Give the link, then follow the run with `workflow_jobs` or `ci_status`, and say whether it passed.
