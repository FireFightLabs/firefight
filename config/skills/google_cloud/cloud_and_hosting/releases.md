Cloud Deploy promotes each release through a delivery pipeline's stages in order, one target a stage. Each promotion is a rollout made of phases, and each phase runs jobs (predeploy, deploy, verify, postdeploy), each as a Cloud Build build. On the resource map a pipeline is a pipeline, each stage a release flow named by the pipeline and its target, such as web prod, and a Cloud Run service or job Cloud Deploy released is linked to the stage that released it. A Cloud Run job is a job, and each of its runs is an execution made of tasks.

1. Rollouts. `run_history` on a stage lists its rollouts, newest first, each named by its release and its own id, release/rollout, with why a failed one failed. On the pipeline it lists every stage's, and `name` keeps one stage's. With `run`, the rollout as release/rollout, it reads that rollout with each phase's jobs, how each went and why a failed one failed. To follow a release to production as it goes, start a watch on the stage with run_history: it hears the first job that fails and reads that job's log.
2. Why a job failed. Its log is what its build printed: `search_logs` on the stage with `run` set to the rollout and the job after it, release/rollout/phase/job, such as rel-7/rel-7-to-prod-0001/stable/deploy. With the rollout alone it reads every job of it, and without `run` the newest rollout. A verify job that failed means the release deployed and its checks failed, so read the released service's own logs over the job's time too.
3. A rollout waiting for an approval reads as running, with waiting for an approval in its detail. Approving it is a person's decision in the console, never Halon's.
4. Roll a stage back: `rollback` on the stage with `to` set to the release to go back to, as the rollouts list shows it. Cloud Deploy makes a new rollout of that release to the stage's target, which runs the stage's jobs again and may need an approval like any other. Undo by promoting the release it ran before. A suspended pipeline makes no rollout, so it is refused until someone resumes it.
5. Stop a rollout that has not finished: `cancel_rollout` with the stage and `run`. What it already deployed stays, so a canary that went out still serves until the stage is rolled back.
6. Cloud Run job executions. `run_history` on the job lists its executions with how many tasks succeeded, failed or were retried. With `run`, the execution's name, it reads each task with its exit code. A task's lines are `search_logs` on the job with `run` set to the execution and the task's index after it, such as nightly-x2k9p/1, one execution's with the execution alone, and every run's without `run`.
7. A rollout or an execution finishing is not in Google Cloud's audit log, so a watch on one reads it each minute rather than being woken.
