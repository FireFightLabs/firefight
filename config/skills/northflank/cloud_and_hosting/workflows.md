A workflow is a set of nodes, such as build, deploy, run a job or wait for an approval, that run in order when something starts it. A release flow is the same thing attached to one stage of a pipeline. What starts one is its triggers. The two pages under references describe them in Northflank's words, and search_docs finds anything else Northflank's documentation says. Workflows, pipelines and each stage's release flow are on the resource map, each linked to what it releases.

1. Runs. `run_history` on the workflow or release flow on the map lists its recent runs, with how long finished ones usually take. With `run`, the run's id, it reads that run with each node, how each went, the error a failed one gave and its retries. One made since the map's last hourly read is not on it yet, so read its runs with `api_request` GET workflows/<id>/runs (or the release flow's runs) until then. To follow a release as it goes, start a watch on the workflow or release flow with run_history, not a general read: it hears the first node that fails and reads that node's log. Give it the run by its id, or by its own name when you know it, such as release-v1-4-0 for a run a webhook named after the tag, so the watch follows that exact run.
2. Why a node failed. A failed build node's log is its build's: `build_logs` with the service or job as `resource`, the build as `build`, and the node's start and end. A failed job node's log is its run's: `search_logs` with the job as `resource` and the run as `run`. A failed release node is the service it released failing to come up, so read that service's own logs over the node's time with `search_logs`.
3. Read what is there before designing anything. `api_request` with `method` GET and `path` workflows lists the project's workflows, and workflows/<id> returns one with its triggers, arguments and nodes. A release flow is pipelines/<pipeline>/release-flows/<stage>, the stage in lower case. Each trigger has a kind and a ref, the name its values are read by in the nodes, such as ${triggers.release.sha}. A webhook trigger's token never comes back, since its URL is a credential.
4. The kinds of trigger:
   - vcs-push runs on a push to a branch matching its patterns, and vcs-pr when a matching pull request is opened or updated. Both can be narrowed by paths and skipped by flags in the commit message.
   - vcs-release runs when a release is published on GitHub or GitLab. On GitHub it is the release created event, so pushing a tag alone does not start it.
   - vcs-pr-label runs when a matching label is applied, and vcs-check-suite when a pull request's check suite from one GitHub app completes successfully.
   - cron runs on a schedule in UTC, at most every 10 minutes, one per workflow.
   - webhook runs on a GET or POST to its URL, https://webhooks.northflank.com/workflows/<token>. Anyone holding the URL can start a run.
5. A webhook reads only its query string. A POST body is ignored. <git trigger ref>.branch, .sha, .pullRequestId and .repoUrl set the values of the Git trigger with that ref, name and description label the run, and every other parameter becomes ${args.<name>}. So a CI job that should deploy the commit it built calls the URL with release.sha=<commit> only when the workflow has a Git trigger whose ref is release, which step 3 shows. Never put a secret in the query string. Secrets go in the workflow's argument overrides.
6. Choose what fits. To release on Northflank whenever a GitHub release is published, a vcs-release trigger does it with no CI step at all. A webhook fits when a CI job must finish first, such as tests or a build elsewhere, and then start the release with the exact commit.
7. To add a webhook trigger, call `add_workflow_webhook` with the workflow and a ref for the trigger, once the person agreed. It is a change, so it may ask them or an approver first. Its URL never comes back to you. Tell the person they reveal it under the step in Firefight. To hand it to GitHub Actions as a repository secret, load github_actions_secrets and pass the reference the tool answered as value_from, so the URL goes from Northflank to GitHub without passing through the chat.
8. Every other trigger change, such as a Git trigger, a schedule or pausing one, is a POST to workflows/<id> (or the release flow's path) with the whole definition read in step 3, its name, apiVersion and spec unchanged and only the triggers changed. A webhook trigger's token reads as [hidden], and Firefight puts the real one back when the definition is sent, so its URL stays the same. Never write a token yourself, which is refused. In the dashboard: open the project, select the environment, open the workflow, click Add trigger, choose the kind, save the trigger, then save the workflow.
9. Starting and stopping, each a step of a fix through `api_request`: POST workflows/<id>/runs starts a run with arguments, and POST workflows/<id>/runs/<run>/abort stops one that is running. A release flow's are POST pipelines/<pipeline>/release-flows/<stage>/runs and its runs/<run>/abort. A build is stopped with DELETE services/<id>/build/<build> (or jobs/<id>/build/<build>), and a job run with DELETE jobs/<id>/runs/<run>. Stopping a run leaves what its finished nodes already did in place.
10. Preview environments. A pipeline's previews are made from a preview blueprint. GET preview-blueprints/<id> reads one, preview-blueprints/<id>/previews lists its previews, and preview-blueprints/<id>/runs lists the runs that made or changed them, each read by id. A preview is paused, resumed or reset with POST preview-blueprints/<id>/previews/<preview>/pause, resume or reset, and a run stopped with its abort, each a change.
11. Rolling back what a run deployed is deploying the build or image that was live before it: find it with `recent_deploys` and `recent_builds`, then roll back through northflank_fixes. Running the workflow again with the earlier commit in its Git trigger's values does the same through the release's own steps. Northflank's "roll back to this release" on a release flow is only in its dashboard, with no call in its API, so when the person wants that exact action it is a step for them there.
12. Templates belong to the team the token is in rather than a project, and the map holds each as a stack. `run_history` on the template lists its runs, and with `run` reads one with each node, such as a project, a service, a build or a release, how each went and the error a failed one gave. A node's log is read only when it ran in a project this connection reaches. To follow a template run as it goes, start a watch on the template with run_history. `run_template` starts a run, with the values its ${args.<name>} read as arguments, and `abort_template_run` stops one that is running. Both are changes, so they may ask the person or an approver first. Never put a secret in a template's arguments. `api_request` never reaches templates, since its paths stay inside a project.
