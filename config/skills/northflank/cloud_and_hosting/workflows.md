A workflow is a set of nodes, such as build, deploy, run a job or wait for an approval, that run in order when something starts it. A release flow is the same thing attached to one stage of a pipeline. What starts one is its triggers. The two pages under references describe them in Northflank's words, and search_docs finds anything else Northflank's documentation says.

1. Read what is there before designing anything. `api_request` with `method` GET and `path` workflows lists the project's workflows, and workflows/<id> returns one with its triggers, arguments and nodes. A release flow is pipelines/<pipeline>/release-flows/<stage>. Each trigger has a kind and a ref, the name its values are read by in the nodes, such as ${triggers.release.sha}. A webhook trigger's token never comes back, since its URL is a credential.
2. The kinds of trigger:
   - vcs-push runs on a push to a branch matching its patterns, and vcs-pr when a matching pull request is opened or updated. Both can be narrowed by paths and skipped by flags in the commit message.
   - vcs-release runs when a release is published on GitHub or GitLab. On GitHub it is the release created event, so pushing a tag alone does not start it.
   - vcs-pr-label runs when a matching label is applied, and vcs-check-suite when a pull request's check suite from one GitHub app completes successfully.
   - cron runs on a schedule in UTC, at most every 10 minutes, one per workflow.
   - webhook runs on a GET or POST to its URL, https://webhooks.northflank.com/workflows/<token>. Anyone holding the URL can start a run.
3. A webhook reads only its query string. A POST body is ignored. <git trigger ref>.branch, .sha, .pullRequestId and .repoUrl set the values of the Git trigger with that ref, name and description label the run, and every other parameter becomes ${args.<name>}. So a CI job that should deploy the commit it built calls the URL with release.sha=<commit> only when the workflow has a Git trigger whose ref is release, which step 1 shows. Never put a secret in the query string. Secrets go in the workflow's argument overrides.
4. Choose what fits. To release on Northflank whenever a GitHub release is published, a vcs-release trigger does it with no CI step at all. A webhook fits when a CI job must finish first, such as tests or a build elsewhere, and then start the release with the exact commit.
5. To add a webhook trigger, call `add_workflow_webhook` with the workflow and a ref for the trigger, once the person agreed. It is a change, so it may ask them or an approver first. Its URL never comes back to you. Tell the person they reveal it under the step in Firefight. To hand it to GitHub Actions as a repository secret, load the GitHub secrets skill and pass the reference the tool answered as value_from, so the URL goes from Northflank to GitHub without passing through the chat.
6. Every other trigger change, such as a Git trigger, a schedule or pausing one, is a POST to workflows/<id> (or the release flow's path) with the whole definition read in step 1, its name, apiVersion and spec unchanged and only the triggers changed. A webhook trigger's token reads as [hidden], and Firefight puts the real one back when the definition is sent, so its URL stays the same. Never write a token yourself, which is refused. In the dashboard: open the project, select the environment, open the workflow, click Add trigger, choose the kind, save the trigger, then save the workflow.
7. Runs: GET workflows/<id>/runs lists them with their status, and runs/<run> shows each node. POST workflows/<id>/runs starts one with arguments, and runs/<run>/abort stops one that is running.
8. Rolling back what a run deployed is deploying the build that was live before it: find it with `recent_deploys` and `recent_builds`, then follow northflank_fixes. Running the workflow again with the earlier commit in its Git trigger's values does the same through the release's own steps.
