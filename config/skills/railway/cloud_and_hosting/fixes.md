name: railway_fixes
when: Writing or applying a fix to a service on Railway, such as a restart, a rollback to an earlier deployment, a change in how many replicas it runs in a region, a redeploy, cancelling or stopping a deployment, or approving one Railway holds
tools: [rollback, restart, scale, scale_service, recent_deploys, resource_status, run_history, list_resources, redeploy_deployment, cancel_deployment, stop_deployment, approve_deployment]
references: [deployments/deployment-actions.md, deployments/scaling.md, deployments/restart-policy.md, services.md]
---
Each change is one step of a fix, and each step says how to undo it. Read what is there first: `resource_status` gives the latest deployment, the replicas and the region, and `recent_deploys` what ran when. The undo comes from these values.

1. Restart, for a deployment that crashed and ran out of restarts while its code is fine: `restart` with the service in `resource`. Railway restarts the latest deployment's containers from the same image, without building. Nothing to undo.
2. Roll back, when a deployment broke it: find the last good deployment with `recent_deploys` and pass its id as `to` to `rollback`. Railway puts back that deployment's image and its variables without building, and only while it still keeps the image, which is for a few days after it stopped serving depending on the plan. A deployment it can no longer roll back to is redeployed from its commit in Railway instead, which builds it again. Undo by rolling back to the deployment that was live before.
3. Scale, for load the service cannot keep up with: `scale` with the replicas in `instances`, at most 50 across every region. Railway commits the new count for the service's region and starts the new replicas from the image it runs, without a redeploy. A service that runs in more than one region, which `resource_status` shows as replicas by region, is scaled one region at a time with `scale_service` and the region's id as `region`, and its other regions keep their replicas. One of several regions may go to 0 while another still runs replicas. A region it does not run in yet is added in Railway's service settings by a person. Undo by scaling each region back to the replicas `resource_status` showed.
4. Redeploy, for a deployment that failed for a reason outside its code, such as a registry or network error while building, or to deploy the same code again: `redeploy_deployment` with the service and the deployment, or none for the latest. Railway builds the same code with the same settings as a new deployment, and its answer names it, so follow it with `run_history` and that id as `run`. Undo by rolling back to the deployment that was live before.
5. Cancel, for a deployment still queued, building or deploying that should not go live, such as one that carries the bad commit: `cancel_deployment` with its id from `recent_deploys`. The deployment serving before it keeps serving. Nothing to undo.
6. Stop, for a deployment that does harm while it runs, such as one sending bad data, when serving nothing is better: `stop_deployment` with the service, which stops its latest deployment unless another is named. The service serves nothing afterwards, so say that before asking. Undo with `restart`, which starts the stopped deployment again.
7. Approve, for a deployment Railway holds until someone approves it, such as a push by a GitHub user with no linked Railway account, which `recent_deploys` shows as NEEDS_APPROVAL or WAITING: `approve_deployment` with its id. Railway then builds and deploys it. Approving deploys code nobody on the team reviewed in Railway, so say whose commit it is before asking. Undo by rolling back to the deployment that was live before.
8. A change acts only in the connection's own environment, since what a person may change is granted per connection. To change a PR environment or another one, a person connects it on the Integrations page as an environment of its own.
9. A fix that changes the start command, the target port, a variable or the health check is a step for a person, naming the setting and the value. When the service is configured in code, such as a railway.json in its repository, the fix is a pull request to that file, since the next deployment reads it.
