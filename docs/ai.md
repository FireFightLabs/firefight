# AI (firefight_ai engine)

All AI features live in the `engines/firefight_ai/` engine. Read this before touching AI generation, the inference ledger, or the transcript store.

## Structure

```
engines/firefight_ai/
  lib/firefight_ai/configuration.rb                  # default_model, openai_api_key, request_timeout
  app/services/firefight_ai/
    postmortem_generator.rb                          # Incident record + narrative summary → structured postmortem draft
    postmortem_section_rewriter.rb                   # Rewrite a single postmortem section on request
    incident_summary_service.rb                      # Layered incident summaries (catchup, live summary)
    incident_responder.rb                            # The one reply /ff catchup posts
    incident_record.rb                               # The incident timeline, posted updates and actions as prompt text, shared by every incident prompt
    milestone_extractor.rb                           # Transcript → the milestones of the investigation, as data
    change_reviewer.rb                               # A coding agent's diff against what was asked, before its pull request opens
    question_answerer.rb                             # A coding agent's question, answered only when what Halon read settles it
    contract_rule.rb                                 # Read another system's contract and setup before designing a change to it
    teammate_rule.rb                                 # Offer the next step, fix only from evidence, follow what it starts
    plan_rule.rb                                     # Plan a request of more than one step, keep the plan true, check every change against normal, report
    helper.rb                                        # One narrow check Halon hands off, run beside the loop, whose plain reply is its report
    outside_rule.rb                                  # Read what changed first, an upstream's status page when errors point outward, and name what is not connected
    replay_judge.rb                                  # How a replayed chat went against its scenario: right, moved forward, questions it did not need
    schemas/postmortem.rb                            # Structured-output schema for postmortem generation
    schemas/milestones.rb                            # Structured-output schema for milestone extraction
  lib/firefight_ai/errors.rb                         # TransientError / TerminalError / OutOfCredit, the only errors that leave the engine
  lib/firefight_ai/credit.rb                         # Reads a provider's refusal for credit and what it can still pay for

app/jobs/
  postmortem_generation_job.rb                       # Runs the generator while Postmortem#generation_state is "generating", delivers the result
  incident_ai_response_job.rb                        # Runs the responder for /ff catchup, posts the answer
  milestone_noting_job.rb                            # Runs one milestone pass from the close and cancel workflows
app/services/
  postmortem_generation_service.rb                   # Draft → Postmortem row + event + channel announcement
  milestone_noting_service.rb                        # Milestones → MILESTONE_NOTED events + the watermark
```

**The engine writes text, the app delivers it.** Engine services return plain results: `PostmortemGenerator#generate` returns a `Draft` (title, summary, markdown per section, model) and `IncidentResponder#answer_question` returns a string. Nothing under `engines/firefight_ai/` names a job queue, a channel, or a platform adapter. The app-side jobs own entitlement checks, persistence (`Postmortem.complete_generation!`), announcements through `WorkspaceAdapter`, and failure notices. Each platform describes its own markup through `PlatformAdapter#ai_output_style`, which the app passes into the responder, so the engine never learns Slack mrkdwn.

**Errors stop at the engine boundary.** Every model call runs inside `FirefightAi.translating_errors`, which maps the client library's exceptions to `FirefightAi::TransientError` (worth retrying) and `FirefightAi::TerminalError` (retrying gives the same answer). Both carry `reason`, the client error's own name, for failure messages. App jobs `retry_on` the first and `discard_on` the second and never name the client library. A rate limit is transient whatever class the library raised it under: `FirefightAi.rate_limited?` reads the response status and the message, since OpenAI's tokens per minute limit arrived as a bad request and a bad request is given up on. `FirefightAi::OutOfCredit` is a `TerminalError` for an account with no credit left (see Output budgets and credit below), so every job that discards terminal errors gives up on it without retrying, and a job a person waits on can say so in plain words.

## Model-agnostic by configuration

The engine calls models through `RubyLLM` — no provider-specific SDK code in services. Every provider RubyLLM supports is configured the same way: one env var per RubyLLM setting, named after it. `FirefightAi::Configuration::PROVIDER_SETTINGS` is the list (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `BEDROCK_REGION`, `VERTEXAI_SERVICE_ACCOUNT_KEY`, `OLLAMA_API_BASE`, `OPENROUTER_API_KEY`, ...). `config/initializers/firefight_ai.rb` reads them into `configuration.provider_settings` and the engine hands them to `RubyLLM.configure` untouched, so adding a provider RubyLLM gains is one entry in the list. Bedrock takes an explicit access key and secret (`BEDROCK_API_KEY`, `BEDROCK_SECRET_KEY`, and `BEDROCK_SESSION_TOKEN` for temporary credentials), and Vertex AI its project (`VERTEXAI_PROJECT_ID`). A workspace's own Bedrock or Vertex AI account must bring explicit keys, see Who pays. The wire protocol and the model registry are both RubyLLM's to decide. OpenAI gets the Responses API, since it refuses tool calls with reasoning on Chat Completions, which is every call the agent makes. Model lookups read the `ruby_llm_models` table, which `RubyLLM.models.refresh` fills from the published catalog, so a model the gem does not know can be added with its pricing. `RefreshModelRegistryJob` runs that nightly in every environment, since nothing else updates the table and a gem upgrade does not touch it. A model with no pricing is billed at zero and its spend cap never fires, so the same job warns with `ai.models_without_pricing` when a model this deployment is configured to run has no price.

Every call has a purpose (`AiPurpose::POSTMORTEM`, `INCIDENT_RESPONSE`, `SUMMARY`, `MILESTONES`), and every service resolves its model through `FirefightAi.model_for(purpose, workspace:)`. That answers the first payer in the workspace's order (see Who pays, below), so a workspace with its own AI account runs on that account's model. The deployment's own model, which the house pays with, comes from `FirefightAi.deployment_model_for(purpose, workspace:)`, most specific first:

1. The workspace's `AiModelOverride` for that purpose
2. The workspace's `AiModelOverride` for `AiPurpose::ANY`
3. The purpose's env var (`POSTMORTEM_AI_MODEL`, `INCIDENT_AI_MODEL`, `SUMMARY_AI_MODEL`, `MILESTONES_AI_MODEL`, `INVESTIGATION_AI_MODEL`, `CITATION_CHECK_AI_MODEL`, `CODE_FIX_AI_MODEL`, `HELPER_AI_MODEL`)
4. The model the providers recommend for the purpose, which only code fixes have (`FirefightAi.recommended_model_for`): `AiProviders.deployment_code_fix_choice`, the first provider in `config/ai_providers.yml` with a `code_fix` model that the deployment holds a key for and the registry prices for that provider (`FirefightAi.priced_for?`). That is Claude Opus 5.5 on an Anthropic key (`claude-opus-5-5`) or an OpenRouter key (`anthropic/claude-opus-5.5`). With neither, code fixes fall through to the investigation's model as before
5. For a purpose with a parent (`AiPurpose::PARENTS`), everything above for the parent: `CITATION_CHECK` uses the investigation's model until it is given its own, `HELPER` uses the side jobs' (`SUMMARY`) model, and so does `POSTMORTEM`, so a postmortem with no model of its own is written on the same model as Halon's answers rather than a built-in one
6. `FIREFIGHT_AI_MODEL`
7. The purpose's built-in fallback (a purpose with a parent has none of its own, it ends at its parent's)

The answer is a `FirefightAi::ModelChoice` (`model`, `provider`). A provider only travels with a model RubyLLM's registry cannot place on its own, such as a Bedrock or Ollama deployment: set `POSTMORTEM_AI_PROVIDER`, `FIREFIGHT_AI_PROVIDER`, or the override row's `provider`. `FirefightAi.chat(choice)` opens the chat and passes `assume_model_exists` for a model the registry does not list under the choice's provider. Every registry lookup about a model (`registered?`, `context_window`, `max_output_tokens`, `input_modalities`, `cost_micros`) takes the provider when one is known, since one id can be listed by several providers with different sizes, limits and prices, and without it the registry picks one by its own preference. `Inference.provider_for(model, provider:)` records the explicit provider or asks the registry, never guesses from the model name.

## Output budgets and credit

A provider reserves a call's whole output cap against the account's balance before it writes a word, and a call with no cap reserves the model's own maximum (65,536 tokens on the model dev ran, about $0.08 a call). An account with a few cents left then refused every call, although a normal reply writes a few hundred tokens. So every call carries a cap that fits what its purpose writes.

- **`FirefightAi.output_cap(purpose, choice:)`** returns an `OutputCap` (`max`). The maximum is the purpose's `<PREFIX>_MAX_OUTPUT_TOKENS` env var (`INVESTIGATION_AI_MAX_OUTPUT_TOKENS`, `POSTMORTEM_AI_MAX_OUTPUT_TOKENS`, ...), else the built-in in `FirefightAi.output_caps`, and never above the `max_output_tokens` the registry holds for the model as the choice's provider serves it. A purpose never takes its parent's cap, since what it writes is its own even on its parent's model. No workspace override exists, since a workspace that switches model is held to that model's own limit already.
- **The built-ins**, from the inference ledger (`output_tokens` by feature, reasoning included):

  | Purpose | Max | Why |
  |---|---|---|
  | `INVESTIGATION` (every agent turn of a run or chat, and the undo writer) | 16,000 | Turns wrote at most about 5,200 tokens (p99 about 3,400) on the largest model, a `conclude` carrying theory, evidence and fix plan is the longest. |
  | `POSTMORTEM` (generation and section rewrite) | 16,000 | A whole document of nine sections in one structured answer, plus reasoning. |
  | `CITATION_CHECK`, `LESSONS` (and the regression judge) | 8,000 | Checks wrote at most about 1,500 tokens. One model ran away to 59,000 tokens of reasoning and was cut off anyway. |
  | `HELPER` (each turn of a helper, see Helpers) | 8,000 | A turn asks for a read or writes a report of at most five lines, with room for reasoning on a model that thinks. |
  | `INCIDENT_RESPONSE`, `SUMMARY`, `MILESTONES` | 4,000 | Each wrote under 300 tokens. |

  A coding agent's own calls run through `FirefightAi::ModelProxy`, which caps its output at `MAX_OUTPUT_TOKENS`, so `CODE_FIX`'s cap (8,000) is for the review of its change and the question Halon answers for it. An embedding writes nothing.
- **`FirefightAi.generate(choice, purpose:, inference:) { |chat| ... }`** is how every single-call service calls a model: one fresh chat with the cap, inside `Inference.track` and `translating_errors`. The agent loop takes the cap as `output:` and sets it on the saved chat when it runs.
- **Never shrunk to fit a balance.** OpenRouter refuses with a 402 that names what the balance still covers ("You requested up to 65536 tokens, but can only afford 60329"). That call is never made again with fewer output tokens, since an answer cut to fit a balance is worse than a clean failure that tells the team. It is out of credit like any other refusal for credit: a workspace's own account hands over to the next in its order, and anything else fails and alerts. The refused call is a ledger row with `error_kind` `out_of_credit`.
- **Out of credit.** A refusal for credit that no other account takes over becomes `FirefightAi::OutOfCredit` and is logged at error level as `ai.out_of_credit` for alerting. What counts, read by `Credit#out_of_credit?`: any 402 (OpenRouter, Anthropic's `billing_error`, DeepSeek), OpenAI's `insufficient_quota` (a 429 that would otherwise be retried as a rate limit), Anthropic's "credit balance is too low" (a 400) and Gemini's "prepayment credits are depleted" (a 429). OpenRouter's in-flight budget 402, with a `Retry-After` header or `limit_source` `openrouter_in_flight_budget`, is a wait and stays a `TransientError` (reason `InFlightBudget`).
- **What a person is told** comes from `AiCredit` (`app/models/ai_credit.rb`), never the provider's words and never its name, and depends on whose account it is. A workspace whose own accounts and credits are what ran out is told so and where an admin fixes it ("Halon cannot answer right now because this workspace's AI account is out of credit. An admin can fix this under Settings, Workspace, AI accounts.", and the same shape for a refused key and no account set up). Credits used up end with the hosted build's `top_up` instead, which names where an admin buys more. The house's own account is told as before, which `Entitlements.ai_account(workspace)` answers from the backend. The open-source backend says `operator`, since a self-hosted install runs on its own keys: "Halon couldn't reach its AI just now." (`AiCredit::COULD_NOT_REACH`), never claiming anyone was told, since an install with no alert webhook tells nobody. Any other backend (the cloud build's) is Firefight's account: "Halon cannot answer right now because the AI account behind this workspace is out of credit. Firefight's team can see this." For both, once an alert can reach the team (`AiAccount.alerting?`, which is `TeamWebhook.configured?`), people hear only "Halon couldn't reach its AI just now. The team has been told." (see Alerting the team below). A chat in the dashboard, Slack or MCP (`Conversation::Delivery.give_up!`), a catchup answer, a run's stop reason (`Investigation#stopped_because`, while `error_summary` keeps `OutOfCredit` for operators), a postmortem (`Postmortem#generation_failure_note`, on the page and in the requester's ephemeral), a section rewrite and an undo each say it with what Halon could not do. Lessons, milestones and embeddings have nobody waiting and are discarded. A regression case settles as errored with `Investigation::Regression::OUT_OF_CREDIT`.
- **The account's state** is `AiAccount`, one row per provider for the whole deployment, for the deployment's own keys only. A workspace's own account keeps its own state (`WorkspaceAiAccount#out_of_credit_since`, `failing_since`), see Who pays. A call refused for good (`FirefightAi.refused_for_good`, from `generate`, the agent loop and `embed`, and `CodeAgent::Relay`) moves it to out of credit with one guarded `update_all` (`AiAccount.ran_out!`, which answers whether this call moved it). The engine never writes that state or enqueues anything itself: it hands the payer, provider and error to `FirefightAi.configuration.on_refused`, which the app's initializer points at `AiRefusal.record!`, and that service records it and asks `AiAccountAlert` to alert. Every answered call clears it (`Inference.track`), and so does `AiAccountBalanceJob`, hourly, when `FirefightAi::Balance.remaining` shows at least a dollar. That reads OpenRouter's credits endpoint with `OPENROUTER_MANAGEMENT_KEY`, the only key OpenRouter lets read it (see Reading what an account holds). Without that key the job reads nothing, logs `ai.balance_unchecked` once a run, and the account waits for its next answered call.
- **Alerting the team.** `AiAccountAlert` posts to the team webhook (`TeamWebhook`, the `INSTALL_NOTIFICATION_WEBHOOK_URL` new workspaces are announced on) through `AiAccountAlertJob`, plain text, naming the provider and either when it ran out or what the account has left and has spent, and starting with `<@FIREFIGHT_AI_ALERT_SLACK_USER_ID>` when that is set. Two things alert: every refusal for credit on the deployment's keys (`AiRefusal.house_ran_out!`), and `AiAccountLowBalanceJob`, hourly, when the account has less than `FIREFIGHT_AI_LOW_BALANCE_USD` (default 10) of credit left. Each kind is claimed with one guarded `update_all`, so alerts racing each other send one. Running out is never held back by a low balance alert: the refusal that moved the account to out of credit (`AiAccount.ran_out!` answered true) always alerts, and refusals after it while it stays out alert again once per `AiAccount::ALERT_INTERVAL` (4 hours) of the last out of credit alert, on `ai_accounts.out_of_credit_alerted_at` (`AiAccount.out_of_credit_alert_due!`). A low balance alert is sent at most once per interval and never within one of any alert, on `ai_accounts.alerted_at`, which every alert sets (`AiAccount.low_balance_alert_due!`). With no webhook set nothing is claimed or sent and `ai.account_alert_unsent` is logged. The alert, its log lines and the ledger never hold a key.
- **Reading what an account holds.** `FirefightAi::Balance` holds one reader per provider whose API says (`READERS`), and the balance checks ask only those, so no other code names a provider. OpenRouter's reader asks `GET /api/v1/credits`, which OpenRouter answers only for a management key, never the key calls are made with. So it reads with `OPENROUTER_MANAGEMENT_KEY` (`FirefightAi.configuration.openrouter_management_key`, kept out of `provider_settings` so it never reaches RubyLLM or a model call), and returns a `Balance::Account` of `total_credits - total_usage` (what is left, in dollars) and `total_usage`. Without that key nothing is read: both jobs log `ai.balance_unchecked` once a run, and `Balance.unchecked` names each provider the deployment calls whose balance goes unread, which the operator console lists under Needs attention. A provider with no reader is never checked. Output caps are never lowered to fit a low balance.
- **What a workspace on the deployment's keys is told.** When those keys ran out and an alert can reach the team (`AiAccount.alerting?`), `AiCredit.cannot` says only "Halon couldn't reach its AI just now. The team has been told.", whatever Halon was doing, on every surface below, so nobody on them hears of balances or credit. A self-hosted install with no alert webhook says "Halon couldn't reach its AI just now." without the second sentence. A code fix whose agent stopped after a refusal on those keys says the same (`CodeAgentSession#house_refused_for_credit?`) rather than the agent's own log. Workspaces whose own accounts ran out keep their own notice.

`AiModelOverride` rows are operator data: set from the Rails console today and from the operator console in firefight_cloud later, never from the dashboard. Self-hosters set env vars. Don't read model env vars directly in services — go through `FirefightAi.model_for`.

## Who pays: a workspace's own AI accounts

A workspace can bring its own model keys, under Settings, Workspace, AI accounts. Admins only (`Ability::Action::RESOURCE_AI_ACCOUNTS`, admin only), dashboard only, never the API or MCP.

| Piece | Holds |
|---|---|
| `WorkspaceAiAccount` | one account: provider, label, encrypted `credentials`, a `credential_hint`, non-secret `settings` (an address, a region), `models` (main and fast), `position`, `enabled`, and its state (`verified_at`, `last_used_at`, `out_of_credit_since`, `failing_since`, `last_error` in plain words). `kind` is `api_key`, or `oauth` for Sign in with ChatGPT |
| `AiProviders` | the providers a workspace may add, from RubyLLM's own `configuration_options` and `configuration_requirements` plus `config/ai_providers.yml` (display name, recommended main and fast models, field labels, which are offered). The only reader of `RubyLLM::Provider` |
| `AiFunding` | who pays, in order: `AiFunding.for(workspace, purpose)` |
| `AiPayer` | one payer (`paid_by`, `account`), what the ledger records, and how a refusal is told to it |
| `AiSpend` | charging a credits call through the hosted backend |
| `WorkspaceAiAccountService` | saving an account and checking it with one tiny call |
| `AiAccountSignIn` | the Sign in with ChatGPT seam (behind `FeatureFlags::CHATGPT_SIGN_IN`) |

The rules:

- **The context starts empty.** A `RubyLLM.context` is a copy of the deployment's configuration, so a context made from a workspace's Anthropic key would still carry Firefight's OpenAI key and Bedrock's credential provider. `WorkspaceAiAccount#llm_context` sets every option every RubyLLM provider declares (`AiProviders.every_provider_option`) to nil, then only the account's own settings, and the deployment's `request_timeout`. Nothing else builds a context (ArchSpec `ai.keys`), and `test/models/workspace_ai_account_test.rb` holds the leak shut. Bedrock and Vertex AI would otherwise reach for credentials the server holds, so both need explicit keys (`AiProviders::EXPLICIT_CREDENTIALS`). `FirefightAi::Configuration::PROVIDER_SETTINGS` lists Bedrock's access key, secret and session token too, so the deployment configures Bedrock the same explicit way.
- **The order.** `AiFunding.for` answers one `FirefightAi::ModelChoice` per payer: the workspace's enabled accounts by `position` that are neither out of credit nor refused, then the house. The house is the operator's own keys, unbilled, on an install someone runs themselves (`Entitlements.ai_account` is `operator`), Firefight's own key for Firefight's own workspaces (`Entitlements.firefight_pays_for_ai?`, true until the hosted backend says otherwise), or the workspace's Firefight credits while `Entitlements.ai_credit(workspace)` is `spendable?` (nil on an install someone runs themselves). A choice carries `context` (the account's, nil for the house) and `payer`. With nobody to pay, `model_for` still answers the deployment's model so a caller can read it, with `AiPayer::NOBODY`, and any call on it raises `FirefightAi::OutOfCredit` before it is made.
- **Main and fast.** An account runs its fast model for `AiPurpose::QUICK` (summaries, milestones, catchups, helpers) and its main model for everything else, investigations and what grows from them. Both default to the provider's recommended models. The main model must be one the registry can size, since the agent loop makes room from the window.
- **Embeddings stay on the deployment's model and account** (`FirefightAi.embed` uses `deployment_model_for`), since every vector in a workspace must come from one model. Rehearsals, replays and the regression judge are Firefight measuring Halon, so they run on the deployment's account too (`Investigation#ai_model`, `Investigation::Rereading`).
- **Falling through.** A call refused because a workspace account ran out of credit, or refused its key (401 or 403), is recorded against that account with one guarded `update_all` (`ran_out!`, `key_refused!`, which answer whether this call moved it), so of calls refused together only the first moves it, and `AiRefusal` then enqueues `WorkspaceAiAccountNoticeJob` (the model enqueues nothing), which direct messages each admin and owner once through the workspace's adapter. Email is not sent, since the app has no mail yet. Then the call is made again on the next payer: `FirefightAi.generate` asks `take_over` for a fresh choice, and the agent loop does the same at the same step, rebinding the saved chat to the next account's model and context (`FirefightAi.bind`) and its output cap, so a run carries on mid-way. With nobody left the call is `OutOfCredit`, and `AiCredit` says what ran out. A refusal on the house's own keys is the operator's, as before.
- **Coming back.** An answered call clears the account's state. `WorkspaceAiAccountRecheckJob` checks every account set aside, hourly, with one tiny call each, and an admin can press Check again. Saving re-checks too.
- **Saving checks.** `WorkspaceAiAccountService` stores what was entered, then makes one call on the fast model (`FirefightAi.check_account`, ledgered as `ai_account_check`). A refusal keeps the account but out of use, with the reason from `AiAccountError.words` (never the provider's message whole, redacted). Saves and checks are limited to ten a minute per workspace.
- **Addresses.** A custom API base must be http or https with no user name. Where `Entitlements.private_ai_endpoints?` is false (any hosted backend that does not say otherwise), a private, loopback or link-local address is refused as written (`AiAccountAddress`) and the name must resolve, when saved, to an address `Integrations::ModelAddress` lets a call reach, the same check every call makes, so a name that does not resolve is refused and a host the operator allowed saves. It is checked again on every call, so DNS rebinding cannot reach inside: the account's context calls through the `firefight_public_address` Faraday adapter (`Integrations::PublicAddressAdapter`), and the code fix relay hands the proxy a `connect_to` check, both resolving through `Integrations::ModelAddress` (`PublicAddress`, with `INTEGRATION_AI_ACCOUNT_PRIVATE_HOSTS` for hosts an operator allows) and connecting to the address they checked. Local providers (RubyLLM's `local?`, Ollama and GPUStack) are offered only where private endpoints are allowed.
- **Code fixes.** `Integrations::Packs::Github::Fixing` picks the first payer whose provider `FirefightAi::ModelProxy.supported?` (Anthropic, OpenAI or OpenRouter). An account writes code fixes with its provider's `code_fix` model from `config/ai_providers.yml` while the registry prices it for that provider (`AiProviders::Provider#code_fix_model_ready`), Claude Opus 5.5 for Anthropic and OpenRouter unless `<PROVIDER>_CODE_FIX_MODEL` (`ANTHROPIC_CODE_FIX_MODEL`, `OPENROUTER_CODE_FIX_MODEL`, `OPENAI_CODE_FIX_MODEL`, in that provider's own name for the model) replaces it, and with its main model otherwise, OpenAI's included, so an admin's main model choice is unchanged for everything else. The session stores `paid_by` and the account, the relay builds the proxy from that account's `llm_context` configuration, and an account removed mid-change stops the change rather than moving it to another payer.
- **Sign in with ChatGPT** is a seam: an OAuth authorization code flow with PKCE whose every address comes from the environment (`CHATGPT_OAUTH_CLIENT_ID`, `CHATGPT_OAUTH_AUTHORIZE_URL`, `CHATGPT_OAUTH_TOKEN_URL`, `CHATGPT_OAUTH_SCOPES`, `CHATGPT_API_BASE`), shown only with the flag on and all of them set. The session holds only the state and verifier during the redirect. The tokens are the account's credentials, and `WorkspaceAiAccountTokenRefreshJob` refreshes them before they expire.
- **Firefight credits** are the hosted build's. Its backend answers `ai_credit` (with `spendable?`, `used?`, `summary`, the row the settings card draws under the accounts with an optional `action` link that only someone who manages AI accounts sees, and `top_up`, where an admin buys more, which ends the credits used up message in place of the AI accounts pointer) and `charge_ai!`, which bills a credits call once and answers what it billed. Neither exists on an install someone runs themselves, so nothing is charged and no row is drawn.

## Inference ledger — every call is tracked

Every row says which prompt produced it. `prompt_template` is the prompt's name and `prompt_version` is `FirefightAi::Prompt.version`, a digest of the wording itself, so an edited prompt cannot keep an old version and two wordings cannot share one. Per run values (the asker, the incident, the seed pack) are excluded, since they change every call and live in the saved chat. `PromptVersion` holds each wording once, written the first time the ledger sees it, so a version can be read back as the words the model was given. Ordering comes from when a version was first seen, not from the digest. `inferences.prompt_version` is a string, the digest as written, so a row joins its `PromptVersion`. It was once an integer, which kept only the digits a digest began with, and those values were cleared.

Every LLM call is wrapped in `Inference.track` (`app/models/inference.rb`), which records feature, provider, model, token counts (input/output/cache), `cost_micros`, latency, finish reason (`stop_reason`), the provider's request id, and status — success or error — plus who triggered it (`member` or `api_key`) and what it was about (`inferable` polymorphic). `paid_by` says who paid (`workspace_account`, `firefight_credits`, `operator`, `firefight`), `workspace_ai_account_id` which of the workspace's accounts when it was one, and `billed_micros` what Firefight charged for it, set only for credits by the hosted backend (`AiSpend.record!` calls `Entitlements.charge_ai!`). A call with no payer chosen is the deployment's (`operator` on an install someone runs themselves, `firefight` on the cloud), which is also what every row from before this was backfilled with. `CodeAgent::Relay` writes the same columns for a coding agent's calls. `max_output_tokens` is the cap the call reserved, and `error_kind` is `out_of_credit` on a call the provider refused for credit (set in `Inference.track` and by `CodeAgent::Relay` for a coding agent's calls), including a refusal a shorter retry then answered.

```ruby
Inference.track(workspace:, feature:, provider:, model:, inferable: incident, member:) do
  chat = RubyLLM.chat(model: model_id)
  chat.with_instructions(system_prompt)
  chat.ask(prompt_text)
end
```

A call with `with_schema` reads its answer from `response.parsed`. `response.content` is the raw JSON text.

Never call `RubyLLM` outside an `Inference.track` block — the ledger is the cost/usage observability layer (and the substrate for AI credit billing).

## Transcript store + secret scrubbing

AI features read incident channel history from `IncidentTranscriptMessage`, not live Slack calls. Messages are scrubbed on the way in by `IncidentTranscriptMessage::Scrubbing`, which redacts secrets (AWS/GitHub/Slack/Anthropic/OpenAI/Stripe/etc. token patterns) **before persistence and before any prompt**. New secret formats belong in `SECRET_PATTERNS` there. The same patterns, through `Chat::SecretFree`, take credentials out of every provider's answer (docs/integrations.md, Secrets in answers).

## Where a proposed change came from

Text Halon reads from outside (an issue, a pull request, a log line, a web page, any provider's answer, a file a person attached) can be written to steer it. `Chat::Tools::Provenance` decides on what was read, never on what it says:

- Every tool answer counts as outside except Halon's bookkeeping (`Chat::Tools.internal_names`), its memory tools, the watch list tools, and Firefight's tools that declare `own_words` (`Mcp::Tools::Base`), which return only what the workspace wrote in Firefight, such as its settings and runbooks. A new tool counts as outside unless it declares otherwise.
- Once a chat has read anything outside, Allow for the rest of this chat no longer stops a tool asking (`Provenance.allowed?`, passed to `Conversation::Turn#confirms?` as `allowed:`).
- Each call then put to the person keeps what was read before it on its row (`provenance` on `ruby_llm_tool_calls`, written by `Provenance.record!` when the turn stops to ask). The reads holding one of the call's own values come first, a value the person wrote themselves counting as theirs. The confirmation (`Chat::Tools::Confirmation#read_lead`, `read_rows`) shows them in the dashboard and in Slack, and offers no Allow for the rest of this chat.
- `Chat#decide!` never allows a tool for the chat from such a call, and `Conversation::Confirming` never approves one alongside an allowed tool, so an old Slack button cannot either.

## Transcript access and retention

Two things gate reading a transcript from outside the product, and they answer
different questions. `Ability::Action::RESOURCE_INCIDENT_TRANSCRIPTS` is its own
grantable resource rather than part of `incidents`, because reading an incident
and reading everything said in its channel are different asks, and folding the
second into the first would have widened every grant already made. On top of
that, `Workspace#transcript_access_blocked_reason` refuses unless an admin has
turned access on under Settings, Workspace. A grant says who may ask, the
setting says whether there is anything to ask for.

`TranscriptRetentionJob` drops the raw messages once the incident they belong to
has been over for `transcript_retention_days`, nightly. The window starts at the
end rather than at close because postmortem generation reads the transcript and
one is usually written the next morning. A null retention keeps them forever,
which a workspace can choose.

**The transcript is scaffolding, the timeline is the artifact.** Milestones
already carry the decision, the quote and the person onto the timeline, and the
postmortem carries the write-up, so purging drops the conversation and not the
memory. Anything that wants to learn from past incidents should extract at close
rather than assume the messages will be there later.

Scrubbing redacts secret *formats* and nothing else. Names, customers, hostnames
and links survive it. It was built so a credential never reaches a prompt, not
so a transcript is safe to hand to a third party, which is why the surface above
it is gated twice.

## Entitlements gate

AI features are gated per workspace via `Entitlements.allows?(workspace, Entitlements::AI)`. In the open-source build this always allows (see the Entitlements section in [architecture.md](architecture.md)); the proprietary cloud build swaps in a backend enforcing trial/credit state. Gate new AI features the same way — never with a hardcoded flag.

## Milestone noting

An incident's timeline records what Firefight did. What the team worked out lives in the channel, and `FirefightAi::MilestoneExtractor` is the one pass that reads it and turns it into timeline events. It runs once per incident, from the last step of `IncidentCloseWorkflow` and `IncidentCancelWorkflow`, after the channel has already been told the incident is over. Nothing is posted to Slack.

The engine returns data and never writes. `#extract(incident, messages:, summary:, timeline:)` gives back `Milestone` structs (`kind`, `statement`, `message_id`, `confidence`). `MilestoneNotingService` does the writing, one `IncidentEvent::MILESTONE_NOTED` per milestone with the person, the quote, and the permalink stored on it. See the metadata contract in [architecture.md](architecture.md).

Three things cap what a pass can cost:

- **Once, not continuously.** No live passes, no timers, no message-count triggers. `Incident#milestones_noted_through` holds the message id of the last message read, so a reopen-and-re-resolve pass reads only what was said since, and the watermark moves even when the pass finds nothing.
- **A trimmed transcript.** `MAX_INPUT_TOKENS` caps the input, and the oldest messages are dropped first since the `IncidentSummary` passed alongside already covers them.
- **A confidence floor.** `MIN_CONFIDENCE` drops anything the model is guessing at, and a milestone citing a `message_id` that is not in the batch is discarded rather than trusted.

`FirefightAi.configuration.milestones_enabled?` is the deploy-level kill switch, read from `AI_MILESTONES_ENABLED`. Unset means on. An explicit `false`, `0`, or `off` turns the pass off for every workspace without a release, and the entitlement check still gates it per workspace underneath. With the switch off, or the entitlement blocked, `note!` returns an empty list without calling a model or moving the watermark, so the timeline is exactly what it is today.

Dismissal is error correction, not deletion. `IncidentEvent#dismiss!(by:)` stamps `dismissed_at` into the metadata and the `undismissed` scope keeps the row out of every text surface: the AI context (`Incident#to_full_context`, which feeds postmortem generation and `/ff catchup`), the Slack timeline modal, `get_incident`, and the REST timeline. The dashboard is the exception, collecting dismissed notes at the end of their day so the correction stays visible.

## Investigator

Phase 1 of the AI SRE build. Where the pieces are:

| Piece | Holds |
|---|---|
| `Investigation` | one run: the subject, trigger, who asked, budget, status |
| `Investigation::Hypothesis` | one theory |
| `Investigation::Step` | one tool call |
| `Investigation::Finding` | the one answer, with its named confidence factors |
| `Investigation::Evidence` / `Investigation::Citation` | one claim of a finding, and the steps it or a settled theory rests on |
| `Chat` / `Chat::Message` | the agent's saved conversation with the model, see Saved chat |
| `Investigation::ToolCall` | the gateway wrapper every tool call goes through, always as the agent |
| `FirefightAi::AgentLoop` / `FirefightAi::Investigator` | the loop and the prompts, in the engine |
| `Investigation::Runner` / `Investigation::Tools` | the app side of a run: the chat, the tools, what each turn spent |
| `Investigation::Delivery` | what a run says while it works, see What a run says in Slack |
| `Conversation` / `Conversation::Runner` | a person talking to the agent, see Conversations |
| `Chat::Tools` / `Chat::ToolCall` | the tools both share, and the gateway call every one goes through |
| `SystemAgent` | Firefight's own agents, global, one row each, granted per workspace |
| `Investigation::Seeding` | picks the seeder for the subject and stores its pack on `seed_pack` |
| `Investigation::IncidentSeed` | the facts Firefight already holds about an incident |
| `InvestigationService` / `InvestigationJob` | starts a run, runs it on the `investigations` queue |
| `ConversationReplyJob` | answers one chat turn, on the `conversations` queue |
| `Commands::StartInvestigation` / `Interactions::StartInvestigationButtonHandler` | the entry points. A mention whose first word is investigate (`Events::AppMentionHandler`) is dispatched as the same command, so no model decides it and the permission, refusals and brief are the command's |

The rules:

- Evidence is a reference (a step, and later a PR, a file range, an Issue), never a copied blob. See Evidence points at steps below.
- **A run acts as the agent, not as the person who asked.** A conversation is the opposite, see below. `SystemAgent.investigator` is one global row, because the software is the same for every customer and only the grants differ. `Investigation::ToolCall` takes no principal argument, so no caller can run a tool as the human by mistake. A workspace grants the agent what it may reach under Gateway, Permissions, where built in agents are their own section. An agent granted nothing is denied, whoever asked. Three grants are there from the start (`Workspace::AgentDefaults::INVESTIGATOR_DEFAULTS`): `map.read` in every environment (migration `GrantInvestigatorMapRead` for workspaces made before), since a run locates what it investigates on the map first, and `memory.create` and `memory.update` (migration `GrantInvestigatorMemory`), so a run saves what it learns and disputes a memory a result contradicted (see Memory). Each is an ordinary grant on the Permissions screen, so an admin narrows or revokes it, and nothing grants it back.
- Built in agents are defined in code (`SystemAgent::BUILT_IN`) and created on demand, so a fresh install loading `schema.rb` gets them without running the migration.
- Every tool call goes through `AbilityGateway` carrying `SOURCE_INVESTIGATION`, and stores its invocation id on the step. Tool output lives on the step, encrypted, and never reaches the ledger. `params` is the binding the ledger stores, so it names what was asked and never carries a payload.
- One live run per subject, enforced by a partial unique index, so a second request is told rather than duplicating the work and posting a second answer to the same channel. It is not a cost control, budgets are.
- Every entry point asks `Investigation.start_refusal(workspace, incident)` and spells no refusal of its own.
- Steps are ordered by when they happened. Branches run in parallel, so a shared counter would be a number two of them fight over.
- Budgets are code defaults in `Workspace::InvestigationLimits`, overridden per workspace by the nullable `investigation_*` columns an operator sets. The cap is in cents and spend is counted in micros, never rounded. Turns are a loop guard, not a cost unit. Each run snapshots both, so changing a default never rewrites what an old run was allowed to spend.
- `AiPurpose::INVESTIGATION` picks the model for runs and chats, env prefix `INVESTIGATION_AI`. Both think on the strongest model, in one context (see Design, Agent runtime). Small models work inside tools and around a run, never inside the reasoning: the citation re-read has `AiPurpose::CITATION_CHECK` (`CITATION_CHECK_AI`), one call with no tools, and falls back to the investigation's model until it is set.
- **The subject is polymorphic.** An investigation is a bounded piece of research that ends in a finding, and an incident is the first thing worth researching, not the only one. `subject_type` plus `subject_id` replaced `incident_id`, the one live run index keys on the subject, and `Investigation#incident` returns the subject only when it is an incident, which is what the ledger's `incident_id` and the announcement's channel both ask for. A polymorphic column carries no database foreign key, so the cascade is Rails' `has_many :investigations, as: :subject, dependent: :destroy`.
- **A run needs no incident.** Someone asks why billing is slow before anyone declares one, so a run with no subject investigates its question (`Investigation#question`, the brief's symptom, required when there is no subject). `/ff investigate <what is wrong>` and a mention that starts with investigate take one in any channel, a chat takes one through `start_investigation`, and MCP takes a symptom in place of an incident. It answers where it was asked (see Where a run is read). The live run index keys on the subject, so questions are not limited to one at a time.
- **A run can offer an incident.** The prompt asks the agent to set `suggest_incident` in `conclude` when there is no incident and users are hurt now, stored as `Finding#suggests_incident` and ignored for a run that has one. The answer then offers Declare incident, in Slack (`Interactions::DeclareFromInvestigationHandler`, the run carried in `ModalState#investigation_id`) and on the dashboard (`investigation_id` on the declare form). `IncidentLifecycleService#create(from_investigation:)` ties the run to the new incident with `Investigation#attach_to!`, once and only from no subject, and the run's start and answer go on the incident's timeline at the times they happened. The declare form starts with the question as the incident's name (the Slack modal reads it from the run in its state, so a rebuilt modal keeps it), and `IncidentCreationWorkflow#post_carried_over_investigation` opens the new channel with the answer, once.
- **A question can be asked again.** A run with no incident that stops on our side offers Run again (`Identifiers::RERUN_INVESTIGATION_QUESTION`), which asks the same question in the same place as whoever pressed it. A run on an incident keeps its own button, which reruns the incident.
- **Every workspace has the agent.** There is no switch for it. What can still refuse is the AI entitlement or a model setup that is not finished (`Investigation.unavailable_reason`), and every way in says so with `Investigation.start_refusal` before it asks for a question. A mention outside an incident's channel that does not start with investigate is ignored.
- **A seeder per subject type.** `Investigation::Seeding::SEEDERS` maps a subject type to a class and a subject with no entry raises `UnknownSubject` rather than storing an empty pack. `Investigation::IncidentSeed` gathers an incident's facts, and `Investigation::QuestionSeed` (the `nil` entry) holds only the question and the brief. What is open, what fired and which services exist are for the agent to look up when the question needs them.
- **The seed pack is gathered once and stored.** The seeder reads only Firefight's own tables (the incident and its state, the lead and roles, the alerts with their provider fields, attached runbooks, resolved past incidents that fired the same alert, and the services named on the incident with the repository each keeps its code in) and writes one jsonb blob, with the clues (below) under `Investigation::Seeding::KEY_CLUES`. No model call and no tool call are involved, so the same run always produces the same pack.
- **A run starts from the map.** `Investigation::MapFacts` puts `resources` in an incident's pack: the resources its catalog services run on (through `ResourceMap::EntryLink`), then any the clues' names and repositories name (`ResourceMap::Resource.named`), present ones only and within the investigator's reach (`ResourceMap::Resource.visible_to(acting_principal)`), so a narrowed grant keeps hidden names out of the pack too. At most `MapFacts::LIMIT` (10), and `resources_held_back` counts the rest. Each has its id, a line saying what it is and where it runs (`Resource#line`), why it is there (the services it runs, or the clue that named it), its dependents from `ResourceMap::BlastRadius` in total and by kind, and the changes the map recorded on it in the 24 hours before the clues' start time (`Change#line`, the last ten). It reads only Firefight's tables and is anchored to the start time, so the same run gets the same facts. Resource names are plain on the map itself, so they stay in `seed_pack` rather than the encrypted `seed_notes`, which hold what people wrote. `FirefightAi::Investigator::MAP_START` tells the run to start from them with the map tools.
- **A run is started with a brief.** `Investigation::Brief` is what whoever asked said: what is failing, roughly when it started, any names and any error text, each kept with where it came from. The chat's `start_investigation` hands it over from the conversation (its description says to ask when it started if nobody has said), the MCP tool takes the same fields (`Investigation::Brief::SCHEMA`), and `/ff investigate` keeps the words after the subcommand. It is stored on `investigations.brief` and repeated in the seed pack.
- **Nothing is checked before the agent starts.** There is no fixed list of sources. The agent starts from the facts and from where the signal came from, and calls only what the question needs. A question about metrics reads metrics, and an error in logs leads to the code that raised it. A fixed first step used to read GitHub for every run, which cost a metrics question a code host call it did not need.
- **The clues say where to look.** `Investigation::Clues` reads them from Firefight's own records, each with its source: the start time (the earliest of an alert received, a first seen field, the brief, detected and declared, with when the run was asked for only as a last resort, and marked an estimate when no alert or report said), commits, releases, service and repository names in alert fields, stack frames in alert payloads (frames in dependencies skipped), exception names in alert titles, the brief, and the incident's catalog services. They are part of the seed pack. When a code change could explain what broke, the prompt points the agent at the GitHub connection's `changes_before`, which takes those clues and ranks what changed, as an ordinary numbered step.
- **Suspects are ranked with their reasons.** `CodeChange::Ranking` orders changes the way an engineer weighs them: touching a file the stack trace runs through, being in a repository the clues name, changing migrations, config, flags, dependencies or infrastructure, being a deploy rather than a merge, and being close before the start. The reasons are printed with the rank, so the agent and a reader can disagree. Changes after the start are shown apart. When nothing in the window explains it, the answer says to look past code, and it always carries the blame of the failing lines however old and the week before, which is how a slow burn is found.
- **A service's repository is a catalog role.** `CatalogAttributeDefinition::ROLE_REPOSITORY` marks the text attribute that holds it, on the built-in Service type by default, and `CatalogEntry#repository` reads it through `CodeChange.repository_name`, which alert fields use too.
- **Nothing is posted yet.** A run gathers the pack and finishes. A briefing with no answer behind it is half a feature, and the message that will carry a finding is not this one, so the posting lands with the agent loop instead.
- **People in the pack are a name and nothing else.** No platform id, so the pack is plain domain facts the engine can be handed without learning that `<@U123>` means a person. Whatever renders a mention asks the incident for it.
- A past incident matches on `alert_source_id` **and** `fingerprint`, because a fingerprint is only unique within its source, and only resolved incidents count. A match carries its `Investigation::Finding` summary when it has one.
- The pack caps alerts at `Seeding::ALERT_LIMIT` and records `alerts_held_back`, so whatever renders it can say how many it did not get. Alert `fields` are kept whole, because the agent reads them, and must be escaped by whatever renders them.

Not built yet: a deadline on a run (nothing runs long enough to need one yet), and the per person environment cap on a run (the scope a person may investigate lands with the agent loop, which is what decides the environment a tool call targets). No implementation stands behind `ConfidenceScorer` or `Matcher` yet.
- **One agent with tools, no sub-agents.** The Investigator reads every tool result into one context itself. There is no planner handing theories to branch runners and no specialist agents returning summaries, because a handoff passes on only part of what the previous step knew. Theories are `Investigation::Hypothesis` rows the same agent writes as it works.

## Reading code

Code is read in a sandbox per run, through the GitHub connection's code tools, so every read is a numbered step through the gateway like any other connection call. The run's `code_box_key` (`Investigation#code_box_key`, `Conversation#code_box_key`, or `Principal#code_box_key` for an outside agent over MCP) names its box, `Integrations::CodeReading` starts it on the first read and pushes each repository with its whole history the first time the run names it, and the box holds no credential. An investigation closes its box when it finishes, a conversation's box closes once idle, and a sweep catches the rest. Both prompts tell the agent to read at the running commit and, for a failing page or endpoint, to check that everything running before the handler is defined before it looks at data or configuration, which is what `find_definition` answers across repositories. See Code sandbox in [integrations.md](integrations.md).

## Monitoring and security

The monitoring and security module is the same agent pointed somewhere else: skills, a permission, and two triggers that start a run nobody asked for. It adds no loop of its own. The page is Halon, Monitoring (`HalonMonitoringController`, `/halon/monitoring`).

| Piece | Holds |
|---|---|
| `Investigation::Check` | a check the workspace runs on a schedule: what it looks at (`kind`, each with the skill that says how, `KIND_DETAILS`), notes people wrote for it (encrypted), daily or weekly at an hour in its own time zone, and when it runs next |
| `Investigation::Notice` | one problem Halon raised on its own, by `key`, with what it last said, when, where, and why one is still waiting to be said |
| `Investigation::CheckSeed` | a check run's facts: the check, its notes and skill, what it raised before, and for a cost check which connected providers report spend |
| `FirefightAi::Monitor` | the prompts for a check run, in the same `AgentLoop` as an investigation |
| `Investigation::Tools::NoteProblem` / `FinishCheck` | a check run's two ways to finish, in place of `record_hypothesis` and `conclude` |
| `Investigation::CheckDelivery` | what a check run says, which is only its news |
| `HalonCheckSweepJob` | starts each due check, every five minutes (`config/recurring.yml`) |
| `Investigation::SecurityTrigger` / `SecurityEventJob` | starts Halon on a security event a connected provider reported |
| `list_notices` | what Halon raised, for Halon and outside agents (Monitoring and security group) |

The rules:

- **A scheduled check is an investigation whose subject is the check.** `Investigation#scheduled?`, `TRIGGER_SCHEDULE`, and the one live run per subject index means a check never has two runs at once. It acts as the investigator, reads only, has no clues (`Investigation::Clues` is about a symptom), and is answered with a finding whose summary says what it looked at, found and could not read, which `Finding#search_embeddable?` keeps out of similarity search. It runs on `FirefightAi::Monitor`, whose prompt asks for slow problems with the day each starts to hurt, a trend from more than one reading, everything the check covers rather than the first thing, and a gap for what it could not read rather than calling it fine.
- **Taking a due check is one statement.** `Investigation::Check#claim_due!` moves `next_run_at` on in an `update_all` naming the time it was due, so two sweeps never both start it. The next time is computed in the check's own time zone, so a daylight saving change moves nothing a person set. A workspace that cannot run Halon (`Investigation.start_refusal`) starts nothing, and its schedule still moves on. Run now (`InvestigationChecksController#run`) starts one at once and leaves the schedule alone.
- **Noise control is `Investigation::Notice`.** `note_problem` records a `Reading` (signal, topic, summary, urgency, the day it becomes a problem, the resource on the map, the steps that show it) through `Notice.observe!`, one row per `key`: the provider's own reference when it has one, else the resource's id, else the topic in words. A reading is news when the problem was never said, was unseen for `RESURFACE_AFTER` (14 days), is more urgent, or is due sooner by at least a quarter of the time that was left and at least a day, so a forecast that wobbles by a day is not said every morning. News is flagged `unsaid` until the delivery takes it, so a problem noted before a run stopped is still said, and one whose channel failed is said at the next run. The seed pack lists what the check raised before, so the agent keeps a problem's topic and resource stable from run to run.
- **The right channel.** `Notice.channel_for`: a service's own notification channel in the catalog (`ROLE_NOTIFICATION_CHANNEL`), then its owning team's, through the resource's catalog entries (`ResourceMap::EntryLink`), else the workspace's `halon_monitoring_channel`. With none, the notice waits on the page with why (`NO_CHANNEL`). The message is `Slack::Messages::MonitoringNotice` through `PlatformAdapter#post_monitoring_notice`, with its urgency, the day, the resource, the run, and whether it was said before.
- **Cost is a signal from the billing reads providers offer.** A provider skill marked `signals: [cost]` reads spend through its provider's cost tool, written the same way by `Integrations::Spend` (docs/integrations.md, Spend is a tool of the pack). A cost check's seed pack lists those skills for the connected providers and names the connected providers that report none, and the Monitoring page says the same, so a bill Halon cannot read is never called flat.
- **The security module.** Firefight's skills `leaked_secret`, `credential_stuffing` and `suspicious_access`, beside the monitoring skills `disk_trends`, `certificate_expiry`, `error_budget_burn` and `cost_trends`, sit under the Monitoring and security group. A provider's event source may report a security event (`Integrations::SecurityEvents`), and `Investigation::SecurityTrigger` starts an ordinary investigation on it (`TRIGGER_SECURITY_EVENT`, no subject, its question built from the event) in the owning team's channel, else the monitoring channel. The event is a notice keyed by the provider's reference, so a redelivery starts nothing and only the same alert getting worse, such as a leaked secret found public, starts Halon again. The run proposes the revoke and replace as its fix, which a person applies. Like a run an alert started, nobody asked for it, and `Investigation::QuestionSeed` says so in its facts (`security_event`) with the skill to load. It has no incident to page on, so the facts ask it to set `suggest_incident` when the secret still works or is public, which offers Declare incident, and declaring one is how whoever is on call is paged. The on-call module's paging and unattended rules act only on a run an alert started on an incident (On call, above). A workspace turns it off with `halon_security_events_enabled` (on by default).
- **Who may change it.** `monitoring` is its own grantable resource. Members read it, and creating, editing, enabling, disabling, deleting and running a check, the monitoring channel and the security switch need `monitoring` create, update or delete. A check that ran is disabled rather than deleted, so its runs stay readable (`deletion_blocked_reason`). Every change says so with a notice.

- **Checks use the general tools a run holds.** `certificate_expiry` checks each hostname with `check_from_outside` (the certificate users are served: expiry, days left, whether it is trusted and covers the host) and reads how it renews from the provider that issued it as the second source. `cost_trends`, `disk_trends` and `error_budget_burn` read `what_changed` for the days a cost, a disk or an error rate jumped, and `error_budget_burn` reads a third party's status page with `check_status_page` when errors point at its host. `FirefightAi::Monitor` carries the same what changed, status page, blind spot and helper rules as the investigator.

## Rehearsals: replays and the bench

A rehearsal is an investigation nobody in the workspace sees, made to measure Halon (`Investigation::Rehearsal`). It is `rehearsal: true` with `TRIGGER_REHEARSAL`, delivers through `Investigation::QuietDelivery`, is left out of the one live run per incident index, the sweep, `get_investigation`, past incidents in the seed pack (`Investigation.seen`) and similarity search (`Finding#search_embeddable?`), and can be told a model (`model_override`, `provider_override`, handed to `FirefightAi::Investigator` as a `ModelChoice`). It reads memory but never changes it (`Investigation#changes_memory?`): it is offered only `recall`, and a recall does not count as a use, so nothing it does reaches the Memory page.

- **A replay** (`bin/rails 'halon:replay[INVESTIGATION_ID,MODEL,PROVIDER]'`) reruns a finished run from its seed pack and any steps taken before the loop (runs from before the fixed first step was removed have one), and `Investigation::ToolCall.replay!` answers each call with what the original recorded for the same action and arguments, in order, failures included. A call the original never made is answered `NOT_RECORDED`, and the count says how much of the replay was really compared, since a model that explores differently leaves the record quickly.
- **The bench** (`bin/rails 'halon:bench[CASES_YAML,MODEL,PROVIDER]'`) runs cases whose cause is known against live systems, sandbox included, and scores a case found when the finding names every expected text. A case is `workspace` (an id), `incident` (its identifier), `said` (what the person asked, the run's brief) and `expect`. Cases name private repositories, so they are kept outside this repository.

Both print turns, spend, steps and time, and close the run's code box whatever happens.

### The regression set

A workspace that turns on `halon_regression_enabled` (off by default, Settings, Workspace, and `update_workspace_settings` over MCP) lets Firefight replay its rated answers to test new versions of Halon. Nothing new is read from its systems and nothing is posted, since a replay answers from the record.

- **The cases** (`Investigation::Finding.regression_cases`): findings the team confirmed or marked wrong, from runs that succeeded and are not rehearsals, in workspaces that opted in, newest outcome first. A run takes the latest `Investigation::RegressionRun::CASES` (30).
- **A run** (`Investigation::Regression.start!`) records the prompt version as deployed (`FirefightAi::Investigator.prompt_version`, from its fixed wording) and the model, nil meaning Halon's own, and one `Investigation::RegressionResult` per case. `HalonRegressionCaseJob` replays each case, two at a time across every run (`limits_concurrency`).
- **Grading.** `FirefightAi::AnswerJudge`, one call on Firefight's own `CITATION_CHECK` model and never a workspace override, says whether the replay names the same cause as the rated answer (`same`, `different` or `unclear`, with a reason). A confirmed case passes on `same`. A wrong case passes only on `different`, since `unclear` has neither repeated the mistake nor answered. A replay with no answer fails without grading, and one that raises is `errored`, which counts neither way. Each case is claimed once (`RegressionResult#claim!` sets `started_at` from nil), so a retried job never replays and pays twice, and settles once with a guarded `update_all` from pending, so nothing overwrites a grade. The run finishes in one statement when no case is left pending. The replay's id is kept as it starts (`Rehearsal.replay!` takes `started:`), so a case that raises still links its replay and what it spent.
- **Opting out** is checked again as each case starts. A workspace that turned the setting off, or lost AI, has its queued cases `skipped`, never replayed.
- **When it runs.** `HalonRegressionWatchJob` (hourly, `config/recurring.yml`) settles cases still pending `RegressionResult::STALE_AFTER` (2 hours) after they started, since their worker was lost, and starts a run the first time a new prompt version is deployed, once per version through a partial unique index. Nothing is recorded while no workspace has a case, so the next check tries again. Operators also start one from the console on any model the registry can price (`FirefightAi.priced_chat_models`), one run at a time (`Operator::Actions.regression_blocked_reason`).

### The chat bench

Chats are measured too (`Conversation::Bench`). A chat is replayed where nobody sees it, on Halon's real prompt (`FirefightAi::Responder`) and loop, on the model it is told (`Responder` takes a `ModelChoice` like the investigator), and every tool call is answered from a record, so only Halon's reasoning varies between two replays. The bench always runs on the deployment's own account, never a workspace's, so a score says how Halon did and not whose key it had.

- **A case** (`Conversation::BenchCase`) is who is asking and where (the context the runner would add, starting "You are acting for"), the person's turns in order with how they answer each confirmation (`approve` or `deny`, and a confirmation left unanswered is moved past by the next turn as live, `NOT_CONFIRMED`), the tools Halon is offered, what each call answers, and what a good run reaches. A tool says whether it reads (`reads`, or `reads_when` for argument values such as a GET through a general API tool), whether a change through it waits for the person (`confirms`), and whose it is (`source`). A read never waits, as decided for Halon. A connected tool that reads owes the answer the check before it goes out, as in a live chat. An answer matches a subset of the arguments without regard to case, a value written `/like this/` is a pattern, `times` lets a run's status move from running to failed between two reads, `after` makes an answer wait for an earlier call (a token refused once it was rotated), and `reads` marks a call through a tool that cannot tell, such as a script, as one that only read. A call nothing recorded gets `NOT_RECORDED` and is counted. A tool's `default` answers what a scenario did not record, where `%{tools}` lists the tools offered.
- **Scenarios** live in `config/halon_bench/*.yml`, written from real failures with made up names and no customer data. Tools many scenarios offer are described once in `_tools.yml` and named by a scenario. Firefight's own tools, the capabilities and the chat's own tools there (`what_changed`, `check_status_page`, `blind_spots`, `run_command`, `check_from_outside`, `run_helpers`, `make_plan`, `start_watch`, `repair_watch` and the rest) carry the descriptions and parameters a chat is offered live, copied from their definitions, so a replay offers Halon what it has, and are copied again when a tool changes. A capability that reads a connected system answers as it does live, a failing log line naming an upstream host included with that provider's status page. The five failures that started the bench (a release whose watch followed nothing, a slow query investigation that timed out, one "no" treated as a standing answer, two workspaces from one signup, a confirmation asking for choices already made) and the 19 stress test scenarios of the North Star design are there, the stress tests as far as a replay can express them: a replay cannot make the model itself fail, so scenario 16 is the reads failing instead. `search_handbook` is described in the shared file until the handbook's own tool is on main. `test/models/conversation/bench_case_test.rb` holds every scenario to an outcome, a next step, the failure it comes from, evidence some answer returns, and the house punctuation.
- **A real chat** becomes a case from its own record (`Conversation::Rehearsal.capture`): the person's messages and decisions, each tool its calls used as the tool is offered today (description, schema and whether it confirms, from the live catalog), or as its calls looked for a tool that is gone, and each call's answer once. Its right outcome was never written down, so that score is left out. It replays in its own workspace.
- **A replay** (`Conversation::Rehearsal`) saves its chat under a `Conversation::BenchResult`, which nobody in the workspace sees, through `Conversation::Rehearsal::RecordedTool`. Scenarios run in a workspace of the bench's own that nobody belongs to, created with the first run and found again through the scenarios that ran there. Its model calls are ledgered against the result and left out of Halon's health and spend in the console.
- **Scoring** (`Conversation::BenchScore`), each from 0 to 1. **Right**: the outcome the scenario describes reached (`FirefightAi::ReplayJudge`, one call on Firefight's own `CITATION_CHECK` model, reached, partly or missed), halved when no reply cites the scenario's evidence (usually a link a tool returned). **Moved forward**: the judge's view of whether it proposed and took the next step unprompted, with the share of the calls taking that step means (`calls`) and a call it should never reach (`never_calls`). **Asked only when needed**: of every time it stopped for the person, a confirmation or a question, the share that was needed. A confirmation for a call that only read, or a question the judge says it could have answered itself (including asking permission to read), was not. **Cost**: Halon's own model calls from the inference ledger (the judge's call is grading and left out) against the scenario's `max_cents`, full marks within it and half at twice it. A replay never starts a sandbox, so model spend is its whole cost. The total is the mean of the four. `notes` says what took marks away, naming tools but never what a call was given. A real chat's answer and the judge's reason are encrypted, like the chat.
- **Running it.** `bin/rails 'halon:chat_bench[MODEL,PROVIDER]'` replays every scenario here and now, four at a time (`SCENARIOS` picks some, `LABEL` names the run, `OUT` writes the scores to a file), and fails when a scenario could not finish. `bin/rails 'halon:chat_bench_compare[BASE,HEAD]'` sets two runs side by side, by id or file, and fails when the total over the scenarios both scored dropped by more than `Conversation::BenchComparison::TOLERANCE` (0.05, the noise between two replays), unless the two used different models. `bin/rails 'halon:chat_replay[CONVERSATION_ID,MODEL,PROVIDER]'` replays one real chat and scores it. `bin/rails 'halon:chat_capture[CONVERSATION_ID]'` prints a chat as a scenario file to start from, which holds the customer's words and data until they are replaced. The operator console runs the bench through `HalonBenchCaseJob`, four at a time, and compares two runs (docs/operator.md). Each scenario is claimed once and settled once with a guarded update, and `HalonBenchWatchJob` (hourly) settles one whose worker was lost after `BenchResult::STALE_AFTER`.
- **In CI** (`.github/workflows/halon-bench.yml`) the bench runs when Halon's prompt, tools, loop or scenarios change. A run on main is kept as an artifact and is the baseline a pull request is compared with, failing when its total dropped. It needs the repository variables `HALON_BENCH_MODEL` (and `_PROVIDER`) for Halon and `HALON_BENCH_JUDGE_MODEL` (and `_PROVIDER`) for the judge, and a key in `HALON_BENCH_ANTHROPIC_API_KEY`, `HALON_BENCH_OPENAI_API_KEY` or `HALON_BENCH_OPENROUTER_API_KEY`. Until all three are set the job passes without benching, with a notice and a job summary naming what to add, so no other pull request is blocked. A pull request from a fork has no key and is not benched either. With no baseline yet, nothing is compared, and the run on main after the change merges becomes the first.

## The agent loop

`FirefightAi::AgentLoop` drives one run over the saved chat, and `FirefightAi::Investigator` holds the prompts and the model choice. The app hands over a `Chat` record, the tools and the budget, and gets back why the run stopped. `Investigation::Runner` is the app half: it makes the chat, builds the tools, writes down what each turn spent, and turns the outcome into the run's status.

The rules:

- **Evidence points at steps, it is never a sentence on its own.** Every tool result in a run is handed over with the number its `Investigation::Step` was recorded under (`step="7"` in the frame). `conclude` takes evidence as claims, each with the step numbers it rests on, and `Investigation#conclude!` writes one `Investigation::Evidence` per claim with an `Investigation::Citation` per step. A claim that cites nothing, a step that does not exist or a step that failed raises `Investigation::Evidence::Refused`, nothing is written, and the tool hands the reason back so the agent fixes it before the run can end. Naming a cause needs at least one claim, and concluding that nothing explains it needs none. `record_hypothesis` takes steps the same way, and a theory cannot be marked supported or refuted without them, so a ruled out theory carries its why. A citation's source is polymorphic and has a `locator`, so a file range, a pull request or an Issue can be cited later without a new shape. A step also keeps its `tool_name` and a `label` such as "Get form declare", which is what the Slack message shows after each claim.
- **A cause comes with its fix.** `conclude` takes a `fix` (a summary, how to tell it worked, and ordered steps), and naming a cause without one is refused (`Investigation::RemediationPlan::Refused`), so the agent always says how to fix what it found, whether or not anything here can apply it. `Investigation::RemediationPlan.propose!` writes the plan on the finding with its `Investigation::RemediationStep`s. A step is a `pull_request` (a code change in one named repository), an `action` (one of the workspace's integration tools, named the way the agent calls it, with its arguments) or `manual` (for a person, saying in `missing` what Firefight would need). The whole fix is checked (`RemediationPlan.check!`) before the citation re-read, so a fix that will be refused never pays for one. An action's tool has to be switched on in this workspace, change something and sit on a working connection with an environment (`Integration::Tool#configured_for?`), and a step that fails is sent back telling the agent to make it manual and say what is missing. A fix that is not shaped as asked, or holds what looks like a credential (`Chat::SecretFree`), is refused rather than breaking the run. Who may run a step is the gateway's question when it is applied, not when it is written. Steps carry how to undo them and which earlier steps they wait on. The prompt asks for one pull request per repository, an action for a change to a provider, and a pull request instead of a direct change when what would change is defined as code (Terraform, Pulumi, Helm, a manifest). The run page shows the plan under How to fix it, the Slack answer lists its steps, and `get_investigation` returns it without the step's arguments, which the agent wrote to run the tool. The unused `remediation_type` and `proposed_solution` columns on findings are gone, since the plan holds the fix.
- **A code change is written by a coding agent and opened by Firefight.** A code host's pack names the tool that writes a change in the registry (`code_fix_tool`, `fix_code` for GitHub), so `RemediationStep#code_tool` names no provider. GitHub's `fix_code` (`Packs::Github::Fixing`, not read only, so a member needs a grant for it) runs OpenCode, installed in the sandbox image, in runner's writable copy of the repository at the base branch, after the repository's own preparation, which now writes what it installs to `.git/info/exclude` so cleaning keeps it and a change never carries it. The copy is a real git repository on the change's branch, and the agent may use any git command on it (commit, merge, rebase, cherry-pick, resolve conflicts). The script (`Fixing::RUN`, tested for real against repositories) records the commit the copy started at and its `.git/config`, fetches the base and the branch through Firefight's git gate (`Integrations::GitGate`, below) so the newest of each is there as `refs/remotes/firefight/<name>`, checks out the branch, runs the agent, commits what it left with the title, keeps the result as `refs/halon/<branch>`, and measures everything from where the result leaves the base (`FROM`, the merge base of `refs/remotes/firefight/<base>` and the result, as the code host's three-dot compare shows a pull request): the checks, each file's counts and the patch are what the pull request will change against its base, so a merge of the base adds nothing to check, review or list. `TOUCHED` names what this run changed since the copy's commit, `MERGED` says it merged another branch in, and a file still holding a conflict marker is named, and puts the commit, the branch and the config back on exit. Nothing is pushed until the review passed, then `Fixing::PUSH` pushes `refs/halon/<branch>` through the gate with `--force-with-lease` on the head the change began from (absent for a new branch), so a branch someone pushed to meanwhile is refused rather than overwritten. The agent cannot push itself: the gate takes a push only with a token `CodeAgentSession#open_push!` makes for Firefight's own push, good only while that push runs (`push_open_until`, `close_push!` after), never with the session's token the agent holds. `PUSH` ignores git's global and system settings, which the agent could have written. The agent's config is written outside the copy: its provider points at Firefight's model proxy, its key is a `CodeAgentSession` token opened once the copy is ready, and it may edit and run commands but never fetch the web. Outside the copy it may use only a temporary directory of the run's own: the script makes `$dir/tmp`, runs OpenCode with `TMPDIR` set to it, and removes it with the rest of `$dir`, and the config allows it as `permission.external_directory` `{env:TMPDIR}/*`, which OpenCode fills in from its environment. OpenCode asks before touching any other path outside the project (`agent/agent.ts` at 1.18.34), and `opencode run` answers every such question with no, so before this a real run could not read the log of a server it had started under `/tmp`. The config and every git credential reach the scripts on stdin (the sandbox's `exec` takes `stdin`), never as arguments, since any process in the box can read another's arguments, and git gets the credential from `GIT_CONFIG_*` set on that one command. A change is refused when the agent exited with an error, the box's answer was cut short, it left a conflict marker, or it is over 4 MB. A refusal never quotes the box's raw output. Seen in a real chat, the agent's log quoted in a refusal carried a provider's error whole, response headers and body included. Now it says what failed in a sentence: the provider's reason as one line (`SandboxAgentEvents#stop_reason`, also the progress's Stopped line), the agent's last words when it changed nothing (`#last_words`, read from the log tail when the box never said what the agent did), and a plain sentence for a fetch or a push that failed. The log tail, or git's own words, go to the Rails log redacted (`code_fix.agent_failed`, `code_fix.agent_changed_nothing`, `code_fix.fetch_failed`, `code_fix.push_failed`), and every `Integrations::Error` a native pack raises loses credentials in `NativeExecutor` (`Redactions.message`) as its answers do. A change that touches a path the connection keeps out of code changes is refused before anything is pushed, saved work of a pause included (`Fixing#kept_out!`, from what the box reported: all of a new branch, and of a branch that had work only what this run changed). After the push Firefight reads from GitHub what it changed (`Fixing#landed!`: the compare against the base, less what a merge brought from the base, through the compare against the head the change began from), and a change that touches a path the connection keeps out of code changes (see docs/integrations.md, Code changes) or over 100 files is taken back, a new branch deleted and an existing one moved back with a forced update to where it was, and nothing opens. Any other file may change, `.github/` included, since every change is a pull request a person reviews. A change touching a CI workflow (`CodeChange::CI_WORKFLOW`) carries `CodeChange::CI_WARNING` right after what it does in its pull request body, or its comment when it adds to one, and in the tool's answer, which Halon passes on in the chat. A new change goes on a `halon/fix-` branch, and `GithubApp.open_pull_request` opens a pull request from it into base, ready for review, through the installation token, which never enters the box. **The git gate.** `GET /code_agent/git/change.git/info/refs` and `POST .../git-upload-pack` and `.../git-receive-pack` (`CodeAgentGitController`) are git's smart HTTP for the box, rate limited per token and kept out of the request log, like the model proxy. A fetch signs in with the session's token as the password. A push, and the advertisement git asks for before it (`info/refs?service=git-receive-pack`), sign in only with the push token (`CodeAgentSession.authenticate_push`), which holds while the push is open even after the agent's own session time ran out, so a long review never loses a reviewed change. The gate refuses a push when no push is open. `Integrations::GitGate` reaches the code host through its pack's `code_remote` (the git address and the connection's credential, the same contract the box's copy is fetched with) and `Integrations::GitHttp`, which streams the request and the answer both ways. A fetch can only read the session's repository. A push is read only as far as its ref update commands, the pkt-lines before its flush, and is refused unless every one updates the session's own branch (`CodeAgentSession#git_branch`): creating, moving and forcing it pass, deleting a ref, a tag, the base or any other branch is refused with a 403 before anything reaches the code host. The pack behind the commands is passed on as it came and never unpacked, at most 200 MB, and a fetch's request at most 10 MB. A code host reached through a checked address (GitLab on its own server) is not reached through the gate yet. The pull request carries the step and the finding's summary, never the evidence read from logs, and is redacted with `Chat::SecretFree::SECRET_PATTERNS`, since a repository can be public. A code step's arguments are written onto the step when it starts, so an approval still matches when it resumes. An agent that changed nothing opens nothing and says what it said. **What the agent does shows as it happens.** The script tees OpenCode's `--format json` output to the box's progress file (`SANDBOX_PROGRESS`, see docs/integrations.md, Code sandbox) and to its log, so the change is read at the end exactly as before. `Integrations::SandboxAgentEvents` reads each event (OpenCode 1.18.34's `tool_use`, `text` and `error`, documented in the class against `packages/opencode/src/cli/cmd/run.ts`, with fixtures from real output under `test/fixtures/files/opencode/`) into a `Chat::CodeFixProgress`: one short line per thing it did (Read, Searched for, Edited, Created, Ran with passed or failed for a test command, Thinking for its prose cut to a sentence, Stopped for a provider's refusal), the files it changed so far and the tests it ran. Only paths, patterns and commands are read, never a file's content or a tool's output, and every line passes `Chat::SecretFree.redacted` plus a value set under a name that says it is secret. The newest `LINES_KEPT` lines are kept and every one counted. The pack reports it through `NativePack#report` on every read of the box, then once more when it opened the pull request (each file's lines added and removed from `git diff --numstat`, the link) or failed (the reason's first line). In a chat the turn hears it (`Conversation::Turn#progress_listener`, handed to the executor by `Chat::Tools::Connection` under the call's id): the runner keeps it with the chat every `PROGRESS_SAVED_EVERY` seconds at most and always at the end (`Chat::StepProgress`, encrypted, read back by `AgentChatMessageSerializer`), the dashboard gets the step again with its `progress` at most once a second (`LiveDelivery#progress`), and a Slack thread gets the step's one line of details (`Chat::CodeFixProgress#headline`, the latest thing and the counts) at most every `agent_step_update_interval` seconds (five on Slack), never every line. `Chat::CodeFixProgress::Pace` decides: the first word and the end always go, news between at most once an interval, a repeat never. A fix step keeps it the same way (`RemediationStep#track!`, encrypted, only while running), the run page reads it from the step, and the thread's fix message shows the headline in place of the result while it runs. A sentence of progress from a connected coding agent is unchanged, and still not shown in a chat. A box from an older image never says what the agent does, so the step shows only that it is writing the change and for how long. The GitHub App needs Contents and Pull requests write for this. A workspace can choose a connected coding agent instead (Devin, Cursor or Factory, under Settings, Workspace, `Workspace#code_fix_agent`), and then the step hands the change to that agent's `fix_code`, which writes it in the provider's own environment, opens the pull request itself and is followed until it does, for at most 30 minutes, with its progress shown on the step. Firefight's own agent stays the default, and a chosen agent that cannot run leaves the step to a person rather than falling back. See docs/integrations.md, Coding agents.
- **The coding agent works with what Halon has.** Seen in a real chat, Halon planned with all its tools and handed OpenCode a short brief, and the agent, with only the repository, wrote a CI change that sent a release's commit in a request body the provider ignores. So:
  - **Halon's read tools, as the person.** The code agent tools server (`POST /code_agent/tools`, `CodeAgentToolsController`) is always in the agent's config, not only with web search on, and serves `CodeAgent::ReadTools`: `list_tools`, `describe_tool` and `call_tool` over every tool `Chat::Tools.catalog` makes ready for `CodeAgent::Reader`, plus `list_skills` and `read_skill` for the connected providers' skills and their guides, and `search_docs` and `read_doc` over the docs store (`CodeAgent::ReadTools.docs`, the same `Chat::Tools::Docs` Halon holds, scoped to the connected providers unless one is named, answered behind `Chat::Tools::Docs::NOTE` and framed as evidence, each call counted against `MAX_TOOL_CALLS`). The brief and the tool's description tell the agent to search the store before the web, since a live run reached for the web for Northflank's webhook parameters the store already held. Listing and calling by name keeps every schema off the agent's model calls. `CodeAgent::Reader` is an agent run like `Chat::StateCheck`: it acts as the session's principal (`CodeAgentSession#principal`, the person who asked in a chat, whoever applied the fix, or an outside agent over MCP), only reads (`reads_only?`, so a tool that changes something is never ready, and a guarded one only reads through its guard as in an investigation), never confirms or holds a call, and ledgers each call through `Chat::ToolCall.run!` with `SOURCE_CODE_AGENT` and "Coding agent for owner/repo". Firefight's own tools are offered from the groups that help with code (`Reader::FIREFIGHT_GROUPS`: incident history, alerts, catalog, map, resources, follow-ups and postmortems), never permissions, access or setup. A machine principal reads only what it was granted, as everywhere. At most `CodeAgentSession::MAX_TOOL_CALLS` per change (claimed in SQL), each result framed as evidence and cut at `ReadTools::RESULT_LIMIT`. Reads that need the sandbox share the run's box (`CodeAgentSession#box_key`). `fix_code` itself is never offered. Web search stays behind the workspace's own switch, with its daily cap and its checks.
  - **The person's words and what Halon read.** A code tool call (`Integration::Tool#writes_code?`, the registry's `code_fix_tool`) is handed a `CodeAgent::Request` through the executor (`request:`), so the pack knows who asked and what they said. A chat builds it in `Conversation::Turn#code_agent_request`, with the person's messages verbatim and the results of the chat's reads before the call (`CodeAgent::ChatEvidence`), a fix step in `RemediationStep#code_agent_request`, with what the run was asked, the notes people added and the results the finding's claims cite. Both are trimmed to the newest that fit (`Request::WORDS_LIMIT`, `EVIDENCE_LIMIT`) and redacted with `Chat::SecretFree`. The brief quotes the words, oldest first, and frames the results as evidence. Devin, Cursor and Factory get the same two sections in their handoff.
  - **Questions.** Where the change was asked for (a chat or a fix step, `CodeAgentSession#place`) the agent also has `ask_question` and `wait_for_answer` (`CodeAgent::QuestionTools`). A question is a `CodeAgentQuestion`: the question, written for someone who does not know the code with a concrete example and what happens today (`QuestionTools::PLAIN`), two to four options each with a label and a one-line consequence, and the option the agent recommends with a one-sentence reason (`recommended`, `recommended_reason`), refused with words when any of it is missing. The tool's description and the agent's brief tell it to read how the code already behaves before asking, and to recommend what matches that and the person's words. One is open at a time (a partial unique index, `index_code_agent_questions_one_open`, since the agent can call tools in parallel), at most `MAX_PER_CHANGE` per change (claimed in SQL on `CodeAgentSession#questions_asked`), encrypted, and due in `ANSWER_WITHIN` (five minutes). A call waits up to `WAIT_IN_CALL` seconds and says to wait again, so no request outlives the agent's MCP client. `CodeAgentQuestionJob` posts it to the same thread as the change's pause and pull request notice (`PullRequestFollowing.destination_of`, `post_code_question`, Answer opening a form) with an option per line, the recommended one marked with why, a button per option (`Identifiers::CODE_QUESTION_CHOOSE_IDS`, `ChooseCodeQuestionOptionHandler`) and Something else opening the form, and lets Halon try first (`FirefightAi::QuestionAnswerer`, one call on the investigation's model that answers only what the person's words or the evidence settle, from `CodeAgentQuestionService.known`, and picks an option by its label, whatever its case, when they settle one, recommended or not). Otherwise the person the change runs as picks an option in one click (`choose!`, kept as `chosen`) or writes something else, under the step in the dashboard (`POST /app/code-agent-questions/:id/answer` with `option` or `answer`) or from the thread, and anyone else is told who can (`answer_blocked_reason`, shipped to the page as `questionBlockedReason`). Answering, expiring and withdrawing are each one guarded update from open. The pack reads the latest question on every read of the box and shows it on the step, live, with "Waiting for an answer" as the headline while it is open. A question past its time settles there or in the agent's wait: with the recommendation (`STATUS_DEFAULTED`, the agent told to carry on with it and say so in its summary), or, for one asked before questions had options, expired, and the change stops with the question as its reason. Waits in a row are one progress line that says how long so far (`CodeFixProgress#waited!`, "Waiting for your answer, 2m"), since the agent waits again every few seconds. Halon's answers and the review are ledgered (`code_question`, `code_review`).
  - **Changing an answer.** Halon's answer is used at once, with no grace period, so a settled answer (`CodeAgentQuestion::CHANGEABLE`, answered or defaulted) can still be changed by the person the change runs as while its session is running (`CodeAgentSession.running`: not closed, not expired, not pushing). `change_answer_blocked_reason` says why not (still open, ended, finished, someone else), shipped as `questionChangeBlockedReason`. The question's `changeable` (`CodeAgentQuestion#changeable?`) says whether Change answer is offered at all, so anyone but the person the change runs as sees it disabled with "Only <name> can answer, since the change runs as them." rather than not at all. Change answer on the card in the chat and on the run's fix step opens the options and a free-text box (`POST /app/code-agent-questions/:id/change` with `option` or `answer`, ledgered as `investigations.create` like an answer), and in the thread it opens a form (`Identifiers::CODE_QUESTION_CHANGE`, `OpenCodeQuestionChangeHandler` declares a read, `ChangeCodeQuestionAnswerHandler` the write). `change_answer!` is one guarded update from a changeable status on a running session and from the `changed_at` it read, so two changes at once leave one and none lands once the change finished. The change is kept beside the first answer (`changed_answer`, `changed_chosen`, `changed_by`, `changed_at`), both surfaces show "Changed to <option or words> by <name>", and the step's question is read from the database when served (`CodeFixProgress#with_current_question`) and on every report, so a change shows before the agent next prints anything. The agent hears it as a correction (`correction_words`, which says it replaces the earlier answer) through three paths, each claimed once against `correction_sent_for`: `wait_for_answer` and `ask_question` return it, `CodeAgent::QuestionTools.with_corrections` appends it to whatever Firefight tool it calls next, and an agent that finished without reading it gets the change sent back with it before the review, again after the review if it landed then, and once more if it lands as the push opens, when the change stops instead (`Fixing#corrected`, `push!`). Continue in place passes any unread correction with its words, and a handover carries the current answer. When the session closes, settled questions are redrawn without the button (`CodeAgentQuestion.changes_closed!`).
  - **A database or a cache of its own.** The code agent tools server also serves `start_service` (`CodeAgent::SandboxTools`) when the change has a box: Postgres or Redis started in that box the way `run_tests` starts them (`CodeReading.start_services`, the box's `POST /services`), answering the variables that reach it, so the agent never builds a database by hand. The brief names it in one sentence. A service the sandbox cannot start is answered in a sentence naming the ones it can, and a box that is not running starts nothing. Each start goes through the gateway as Halon's agent under `Ability::Action::SANDBOX_SERVICE`, an open action like `web.read` (it reaches nothing of the workspace's, so no grant, never held by an approval rule, never on a permission screen), with `SOURCE_CODE_AGENT` and "Coding agent for owner/repo". The change's box is prepared with the repository's setup from its CI (docs/integrations.md, Code sandbox), and the agent runs with its services and variables.
  - **Checks and a review before anything opens.** After the agent, the run script stages the change and runs `Integrations::CodeChecks::SCRIPT` on the files the pull request changes against its base: actionlint for GitHub workflows, the repository's rubocop, eslint and `tsc` where it installed them, the tests it changed and the tests beside a changed file by the repository's layout (`app/models/user.rb` by `test/models/user_test.rb`, a `.test.ts` beside a `.ts`, `test_<name>.py`, go test for a package with tests), ruff or a compile for Python, gofmt and go vet for Go, shellcheck for scripts, and a parse of JSON and YAML, each cut off at `CHECK_TIMEOUT` and skipped when its tool is missing. A check stopped by something the box lacks is `CodeChecks::COULD_NOT_RUN` with the reason (`MISSING`: a database, Redis, unset secrets or settings, a refused connection, or a command that is not installed), read from what it printed, so it is said apart from the checks that ran and never as a failure or a doubt about the change. The agent's brief asks it to write the change first and then verify its own work the same way, and to check the change against any rule the evidence or the documentation states. Seen in a real chat, the agent tried to build Postgres by hand to run the tests (initdb, pg_ctl), failed, and stopped having changed nothing. So the change never depends on the sandbox being able to run the repository's tests: running them is best effort and never a reason to stop, the agent never builds an environment, a database or a service by hand and uses what the sandbox provides, and its summary lists what could not run under a line reading `CodeWriteUp::NOT_RUN`. `SandboxAgentEvents#could_not_run` reads that list into `Change#not_run`, after what preparing the copy said the sandbox lacks (`CodeReading.not_run`, a service it cannot start or a Postgres extension the setup names), and the write-up adds it to Could not run here after the checks that could not run. The heading and the rule that a check that could not run is never called blocked or a blocker, or listed under Blocked, are `FirefightAi::Copy::NOT_RUN_HEADING` and `FirefightAi::Copy::NOT_RUN`. The rule is part of `Copy::RULE`, so every Halon prompt and the review carry it, and the agent's brief and an outside coding agent's handoff carry it too. Nothing in the pack refuses a change because tests could not run, the review's prompt says a test that could not run is never a finding or a reason the change is wrong, and the repository's own CI runs it on the pull request, which Halon follows. The change's patch comes back too. `FirefightAi::ChangeReviewer` then reads the diff against the person's words, the brief with the contracts Halon cited, the evidence, the checks and the agent's own summary (`SandboxAgentEvents#last_said`), on the change's model and inside its budget (charged to the session), and answers whether it does what was asked, what it found, what it verified against the material and how, and the questions still open, which are only what the material cannot answer and matters. A diff over `DIFF_LIMIT` is never cut inside a file: the files the person's words or the brief name are shown whole, then the rest whole while they fit, smallest first, and the review lists every file it was not shown (`Review#unreviewed`). On an update to an open pull request it is also told which of the pull request's files this update changed. Its prompt tells it that Firefight commits and pushes only after the review, so that nothing is pushed yet is never a point, and that a check that could not run is not a finding. A change it finds wrong goes back once (`Fixing#send_back`): the agent starts from the earlier result's commit with the findings, for `SEND_BACK_TIMEOUT` within what is left of the session, and is reviewed again. Still wrong, or no time left, nothing is opened and the findings are the reason. A review that cannot run opens the change saying nothing was verified beyond the checks. Protected paths are checked after every pass.
  - **What Firefight writes about it.** `Integrations::CodeWriteUp` builds the pull request's body, the comment on an open pull request it adds to, and the tool's answer Halon tells the person from, in the same order: what the change does and why (the body leads with the review's own `summary`, else the title, and the comment with the `summary` argument, else the title), the CI warning, then Verified (the checks that passed and what the review checked), Could not run here (each with why), Checks that did not pass, Found in review, Open questions, Not reviewed when the diff was too large, then the files the pull request changes with their lines. The comment says what this update changed instead: the pull request's files it touched (`Change#updated_paths`), or that it changes none, and that it merged the base when it did. Everything is redacted with `Chat::SecretFree`, and nothing names how the work was done.
  - **The write-up reads like a person's pull request.** `Integrations::CodeWriteUp` writes the body from the change, its checks and its review only, never from the brief or the `context` Halon handed the coding agent, since a repository may be public and those hold instructions and what was read of live systems (seen on a real pull request, which carried "Open the PR from that existing branch" and production rows). `ChangeReviewer::PUBLIC_RULE` tells the review the same about its own lines. The body is: what the change does and why (the review's `summary`, or the title), the CI warning when there is one, then Verified (the checks that passed and what the review checked), Could not run here, Checks that did not pass, Found in review, Open questions (what the review could not verify) and, for a change too large to review whole, the files it did not review, each only when it has something, then Files and the footer. The comment on a pull request a change was added to and the tool's answer, which the chat prompt tells Halon to pass on, carry the same sections. The step shows the review, the checks and the question once it ends.
  - **A pull request Halon opened is described again on every update.** Adding to an open pull request that a code change of this workspace opened (`CodeAgentSession.opened_pull_request?`) writes its description again for the whole change as it now stands (`Fixing#describe_again`), so a line an earlier version made true is gone, and reads it back: the answer says the description describes the whole change only when GitHub shows exactly that, and says it still holds the old words otherwise. Someone else's pull request keeps its own description and gets only the comment.
  - **A change to a pull request is said as GitHub shows it.** `update_pull_request`, `label_pull_request` and `comment_on_pull_request` read the pull request back after writing (`PullRequests#updated_words`, `labels_shown`, `comment_shown`) and say only what GitHub shows, ending with `PullRequests::READ_BACK`. A title, description or base GitHub does not show is said to be unchanged. `Responder::PULL_REQUEST_CHANGE_RULE` tells Halon to say a pull request changed only when such an answer showed it, never because it meant to or a coding agent's summary says so (seen on a real pull request, whose comment said the description was cleaned when nothing had changed it).
  - **Halon reads the contract first.** `FirefightAi::ContractRule` is in the chat and run prompts: before designing a change to another system's interface, read its documented contract and its live setup with the tools it has, cite both in the brief and mark what it could not verify. The `github_fixing` skill and the coding agents' handoff skills say the same.
  - **Written on the newest code.** Seen in a real chat, a fix written minutes after another was merged opened on the commit the box had been handed earlier and conflicted at once. A new pull request is written on its base branch's head as GitHub says it is now (`Fixing#head_of`), so `prepare` and the run use that commit, and the box fetches the repository again when it lacks it (`CodeReading`'s missing commit refetch). The gate's fetch brings the newest base and branch into the copy as well.
  - **A conflict is resolved by git, and only the host says it is.** Seen in the same chat, `fix_code` on a conflicted pull request wrote a commit on its old head, so it stayed conflicted, and Halon said it was resolved without reading it. Now the agent merges `refs/remotes/firefight/<base>` into the branch and resolves the conflict with git like any developer, the result is a real merge commit with both parents, and it reaches GitHub through the gate as it is, so GitHub sees the conflict as resolved. Nothing per kind of change is coded: a fix that should merge the base says so in its brief (Fix it's does, `PullRequestFollowing.fix_brief`). After opening or pushing, the answer ends with what the code host says (`Integrations::PullRequests::Status#words`, read with `settle` while GitHub works out mergeable), and the skill and the answer tell Halon to repeat only that. `pr_lookup` says a conflict on a pull request Firefight opened is Halon's to fix with the person's yes (`PullRequests::OWN_CONFLICT`), and on anyone else's offers `fix_code` with that pull request.
  - **Halon owns the pull requests it opens.** The change's `CodeAgentSession` keeps the pull request it opened (`CodeAgentSession::PullRequest`: number, address, base, branch, the connection, and `pull_request_state` open while followed), only when someone can be told (a chat a person reads, or a fix step). `PullRequestFollowing.check!` reads it through `Integrations::PullRequests.status` (the code host pack's `pull_request_status`: open, merged or closed, mergeable, conflicted or blocked, failing checks and the reviewers whose latest review asks for changes) right after it opens, at once on a code host delivery that names it, its branch or its base (`MapEvents.nudge_pull_requests!`, the event source's `pull_request_nudges`), and on `PullRequestSweepJob` every five minutes for one not read within ten minutes, or an hour once it is a day old. Each read is claimed with a guarded update. A conflict, failing checks or changes requested become one `CodeAgentSession::Notice` per set of problems on the same commits (a unique index on the session and the fingerprint), so the sweep and a live update never say it twice and a base that moves again while still conflicted says nothing new. A newer notice replaces an offer nobody took, problems gone clear it, and a merged or closed pull request ends following and the offer. The notice is said in the chat (`PROP_PULL_REQUEST_NOTICES`, live through `LiveDelivery::EVENT_PULL_REQUEST`), in its thread or the asker's direct messages (`post_pull_request_notice`), and Halon hears it once at its next turn (`PullRequestFollowing.untold_note`). Fix it (dashboard `agent_chats#fix_pull_request`, Slack `Identifiers::PULL_REQUEST_FIX`) is the only yes: only the person the change runs as may press it (`Notice#fix_blocked_reason`), one guarded update claims it, and `ConversationReplyJob` runs the code host's code change tool with that `pull_request` at the start of a turn, through `Chat::Tools::Connection` as them, so grants, approval rules (a held call waits for its approver) and the ledger apply, then Halon reads what it answered and says how it went. A fix step's notice whose run was not started from a chat goes to the run's thread, and Fix it opens the thread's conversation.
- **Reading the public web.** `search_web` and `read_web_page` (`Chat::Tools::Web`) are in every chat and run. They read through `Integrations::WebSearch` on Firefight's own keys, so a workspace sets nothing up, and say so when the deployment has none. Two providers answer the same shapes (`Result`, `Page`): Tavily (`TAVILY_API_KEY`), whose search returns each page's text in one call, and Firecrawl (`FIRECRAWL_API_KEY`), which scrapes each result and reads a page in a browser, so a page drawn by JavaScript is read too. `WEB_SEARCH_PROVIDERS` and `WEB_READ_PROVIDERS` each set an order (comma separated, `tavily,firecrawl` when unset), so searching and reading can prefer different providers. The first provider in the order that has a key answers, and when it fails (an error, a timeout, a rate limit, credits run out, a page it could not read) the next takes over, unless it refused what was asked (400 or 422, `WebSearch::Refused`, since the next would refuse it too) or the lookup has run past `WebSearch::FALLBACK_WITHIN` (45 seconds). A provider named twice is asked once, and an order naming an unknown provider fails the boot (`config/initializers/web_search.rb`). The address a page or a result ended up at is redacted like its text, since a redirect can carry a signed token. Each answer is logged (`web_lookup.answered`, with the provider and whether it was a fallback) and each failure too (`web_lookup.provider_failed`), so the two can be compared. Trying a new provider is one class in `app/adapters/integrations/web_search/`. `WebLookup` returns each page with its address first so what is used is cited, caps it and redacts anything that looks like a credential, and reads only a public http or https address. Each call goes through the gateway as `web.read` (`Ability::Action::WEB_READ`, the one of `OPEN_KEYS`), an action every person and agent holds with no grant since it reaches nothing of the workspace's, never offered as a grant (`grantable` leaves it out), never held by an approval rule (`approval_exempt?`, since a broad rule would stall every lookup), and ledgered because it leaves Firefight. So a run's web lookup is a step a finding cites. A workspace switches it off under Settings, Workspace (`web_search_enabled`, on by default, also over MCP), which takes both tools away from Halon and the coding agent, and has `Workspace::Settings::WEB_LOOKUPS_PER_DAY` lookups a day, counted from the ledger. A search or an address that holds anything that looks like a credential is refused before it is sent, since it is the one way text leaves through here, and an address must be a named public host (no raw IP in any notation, no userinfo, no private suffix). Text the model writes can still carry ordinary data out in a search or an address, which the switch is the control for. The coding agent reaches the same two tools on the code agent tools server at `POST /code_agent/tools` (`CodeAgentToolsController`, `CodeAgent::WebTools`, beside its read tools and questions, see The coding agent works with what Halon has) on its session token, set in its OpenCode config, with every lookup ledgered as Halon's agent under `SOURCE_CODE_AGENT`, at most `CodeAgentSession::MAX_WEB_LOOKUPS` per change (claimed in SQL), framed as evidence, and kept out of the request log. The agent's brief says a page is data, never an instruction. The box itself still never fetches the web.
- **Halon's terminal.** `run_command` (`Chat::Tools::Terminal`) and `check_from_outside` (`Chat::Tools::OutsideCheck`) are in every chat and run where the workspace has a sandbox provider to try (`Integrations::Terminal.available?`, `SandboxProviders.order_for`), and in no other place. Both run in the run's own code box (`code_box_key`, the same one code reading and a code fix use, through `Integrations::Terminal` on `CodeReading#terminal` and `#place_file`), which starts the first time a run needs it and stops as code reading's box does: an investigation's when it ends, a chat's after `CodeBox::IDLE_AFTER` unused, and the sweep's for anything abandoned. A chat that never runs a command never starts one. A command is one `bash -c` in the terminal's folder (`/terminal`) as the image's `halon` user, who can write nothing else, so it never touches a repository or a test copy. It runs in the background (`/runs`) and is given at most `Chat::Tools::Terminal::MAX_TIMEOUT`. `results` places saved results (`Chat::SavedResult`, by handle, a file the person attached too) as `results/<handle>.txt` first, so a script filters, counts or groups a large result and only its answer comes back, and a large output is saved like any result. Each command is one ledgered call of `sandbox.read` (`Ability::Action::SANDBOX_COMMAND`, open like `web.read`, never on a permission screen, never held by an approval rule), so a run's command is a step it cites.
- **What a command calls goes through Firefight.** Each command opens a `Chat::TerminalSession`: a token kept only as a digest, good until the command's limit plus `MARGIN` and removed when the command ends, which the box is handed as `FIREFIGHT_RELAY_TOKEN` beside `FIREFIGHT_RELAY_URL` (`Chat::Terminal.relay_base`, `CODE_AGENT_PROXY_URL` or the app's own address). It is the only credential the box ever holds. `ff` (`sandbox/bin/ff`) lists, describes and calls the connected tools on it at `/sandbox_relay` (`SandboxRelayController`), and `Chat::Terminal::Relay` runs each call as the tool Halon would have called, on the run that started the command (`TerminalSession#agent_run`: the conversation's turn as the asker, or the investigation as the investigator), so grants, packs, approval rules, the read contract and the activity log apply as to Halon's own call, and Firefight adds the key. Its run has no chat, so an answer comes back whole rather than saved, and a held call is kept with the chat as any held call. It offers connection tools, capabilities and Firefight's own tools that read, at most `TerminalSession::MAX_CALLS` per command (claimed in SQL). `ff` exits 1 on a refusal or a failure and 3 on a call waiting for approval, so a script can tell.
- **A command that changes something is confirmed like any change.** A call that changes something (a connection tool that is not read only and whose read guard cannot show the call reads, or a capability that writes) runs only when the command was asked with `changes` true, which only a chat can ask: the tool then waits for the person like any change (`requires_approval?`, with `approval_resolver` letting a command without `changes` through at once, and an intent), Allow for the rest of this chat stops covering it once anything outside was read (`Chat::Tools::Provenance.allowed?`), and an approval rule still holds each call. A read through a general tool is a read by its read guard, so the gateway never holds it. A change with a safeguard of its own (`Chat::Safeguards`: a data write, a call that stops something, a mitigation, or any capability that writes) is never made from a command, confirmed or not. The relay refuses it and says to call the tool directly, so the person is asked about that call with what it touches and its safeguards run. Without it the relay refuses the call in a sentence that says to ask again with `changes`, and an investigation, or a turn that only reads, refuses it as reading only. Confirming the command confirms the changes it makes, so an approval the person may give themselves is given, as a runbook's steps are.
- **A provider's own command line tool reaches it the same way.** A provider whose definition names a `cli` (`Integrations::Clis`, see docs/integrations.md) has its command in the image, pointed at `/sandbox_relay/api/<connection>` with the command's token as its key. With one connection for that command its settings are set on every command, and `ff with <connection> -- <command>` picks one of several. Each request becomes one call of the connection's relayed tool with `relayed: true`, and the provider's answer goes back in the API's own shape (`Telemetry::RELAYED`), secrets still hidden. Northflank's (`northflank`, inside a project, through `api_request`) and Kubernetes' (`kubectl`, through `api_read`, reads only, wrapped in the image so it takes the relay's address and token) are wired. doctl cannot be, since it drops a base address's path. GitHub's and GitLab's CLIs take a host and no path, Fly's and Railway's speak GraphQL by POST, which no read maps onto, and AWS, Google Cloud and Azure sign each request with their own credentials, so none of them reaches the relay.
- **An address from outside, and from where.** `check_from_outside` runs `sandbox/outside_check.rb` by argument list, never through a shell: DNS (A, AAAA, CNAME with TTLs), one GET or HEAD as a browser makes it (status, redirects, the address reached, and DNS, connect, TLS, first byte and total timings from curl), and the certificate (subject, issuer, expiry and days left, the names it covers, whether it is trusted). The answer names the region of the box it ran in (`Sandboxes.region`, per provider): Northflank's boxes project's region, boat's EU, and for Docker the deployment's `SANDBOX_REGION`, else that the install does not name one. A box sees from one place, so it names the connected uptime monitors that check from several regions (`Capabilities.outside_checkers`, a provider whose adapter observes status for endpoints, such as OpenStatus) and that `resource_status` reads theirs region by region. No provider today lets a box choose its region.
- **A library at the version in use.** GitHub's `library_source` (`Packs::Github::Libraries`, read only) asks the repository's own ecosystem where a library is installed and at what version (bundler, node_modules, the package's own files in the venv's metadata, go list), then lists its files, searches it without following links, or reads one file whose real path is inside it, never outside. The coding agent is told the dependencies are installed in its copy and to read a library there and its docs before relying on how it behaves, and the investigator prompt says the same.
- **The model proxy.** `POST /code_agent/:provider/*path` (`CodeAgentController`, rate limited per token, every parameter kept out of the request log) takes the session's token as the provider's key header. `CodeAgentSession` holds a digest of it, the model chosen for `AiPurpose::CODE_FIX` (its parent is the investigation's, and a model the registry cannot price is refused, since the budget is counted in cost), the repository, a budget (`DEFAULT_BUDGET_MICROS`, two dollars, which the review of the change is charged against too), at most three calls at once (claimed in SQL) and an expiry (30 minutes, which a change sent back after its review shares), whoever asked for the change, where, and the run's box, and closes when the change ends. `CodeAgent::Relay` refuses a spent budget or a full session, then `FirefightAi::ModelProxy` pins the request (the session's model, output capped at `MAX_OUTPUT_TOKENS`, only the agent's own tools, never a provider's server tools such as web search, OpenAI streams asked to report usage), forwards only the paths a coding agent calls (Anthropic `messages`, OpenAI `chat/completions` and `responses`, OpenRouter `chat/completions` with its fallback `models`, `route` and `plugins` removed so a call never reaches another model or the web) with the payer's own key and address (the session's `paid_by` and `workspace_ai_account`, whose `llm_context` configuration the proxy reads, or the deployment's configuration) and streams the answer back, reading usage off it as it goes (a JSON body read whole, Anthropic's cached tokens folded into input). The run page polls while anything can change without the person looking (`RemediationPlan#moving?`: a step running, a step Firefight runs ready, an approved step Halon is checking, or a step waiting for approval, since an approver can decide in Slack or elsewhere), not while a step waits for a person to press it. Nothing is undone automatically, and whether the fix worked is not checked yet.
- **A fix being applied can be cancelled.** Cancel fix, on the run page while it applies (`InvestigationsController#cancel_fix`, with the plan's id, so an undo is cancelled the same way) or on its progress message (`Interactions::CancelFixHandler`, behind Slack's confirm), calls `FixRunner.cancel!`. `RemediationPlan#cancel!` moves it from `applying` to `cancelled` with one guarded `update_all`, recording who and when. Every step that has not run is moved to `skipped` saying who cancelled it (`FixRunner.stop`), and an approval one was waiting on is expired, from pending only in one statement so an approval given at the same moment stands, and its messages redrawn as withdrawn (`ApprovalNotificationService.mark_resolved!`). A step only starts through `RemediationStep#claim!`, whose statement also requires the fix to still be applying, so a worker that chose a step before the cancel never starts it. A step that asks for approval as the fix is cancelled, or is approved after, is stopped and its approval withdrawn rather than run. Undo waits until no step is running or waiting. A step already running finishes, since a call cannot be taken back halfway, and the page keeps polling until it does. `settle!` never moves a cancelled fix, and a cancelled one with a step through can be undone.
- **An applied fix can be undone, by a person.** Undo fix, on the run page under the fix (`InvestigationsController#undo_fix`) or on the thread's progress message once the fix ended (`Interactions::UndoFixHandler`, behind Slack's confirm), calls `Investigation::UndoWriter.request!`, which claims the writing with a guarded `update_all` (`RemediationPlan#request_undo!`, recording who asked) and enqueues `InvestigationUndoJob`. `RemediationPlan#undo_blocked_reason` allows it only on an applied or partly applied fix that is not itself an undo, where at least one step went through, that has none written or being written (a writing older than `UNDO_WRITING_STALE_AFTER` counts as lost and can be asked again), and only while the workspace may use Halon (`Investigation.unavailable_reason`). `FirefightAi::UndoWriter` asks the investigation's model, with no tools and every step's result framed as evidence (`Evidence.frame`, `Evidence::RULE`), for the steps that put back what each step changed, newest first, from each step's kind, what it was called with, what came back and its undo note, and the workspace's tools that change things. Its answer is checked like any fix (`RemediationPlan#propose_undo!`, `check!`) and saved as a plan on the same finding with `undoes_id` set (a finding's fix is the plan with none, enforced by a partial unique index), then posted in the thread with its own Apply undo (`post_undo_plan`), and the fix's progress message is redrawn without its Undo fix. An undo reads as one everywhere (`is_undo`): Apply undo, and progress that says Undoing the fix, Fix undone or Fix partly undone. Every tool step, of a fix or an undo, shows what it sends (its arguments) folded under it on the run page and cut short in Slack, so a person sees exactly what runs as them before applying it. `get_investigation` returns the undo under the fix. A refused answer is kept as `undo_error` for the person to see and ask again. The undo is applied exactly like a fix, through the same endpoints with its `plan_id`, so it runs as whoever applies it and approval rules hold its steps. The run page shows it under How to undo it and polls while it is being written.
- **The first answer is argued with before it is recorded.** The first `conclude` of a run is answered with `FirefightAi::Investigator::CRITIQUE` instead of being written: try to prove it wrong, run only a check that can be named, and let only a result change the answer. `Investigation#ask_for_critique!` is a guarded update on `critique_asked_at`, so a resumed run is not asked twice, and a run whose budget is spent (`Investigation#budget_spent?`, read from the row) skips it, since its last turn has no room for another. The checks it runs are ordinary steps.
- **Citations are re-read before an answer is recorded.** `Investigation::Rereading` hands each claim and the full text its cited steps returned to `FirefightAi::CitationCheck`, one call with no tools, and a claim the text does not show is dropped. If every claim behind a named cause is dropped, `conclude` refuses with the reasons, so the agent cites what shows it or names no cause. A re-read that cannot run keeps every claim, since dropping them would pass our failure off as the agent's.
- **Only `conclude` ends a run.** It writes `Investigation::Finding` unpublished. A plain reply does nothing: the agent is reminded once, and a second one ends the run as stalled with its hypotheses kept. Theories are written as the agent goes, through `record_hypothesis`.
- **Spend is the budget.** Each model reply's cost is added to `spent_micros`, the ledger's unit and never rounded, so many small replies cost what they cost rather than a cent each. At `max_spend_cents` the agent gets one last turn to conclude with what it has, which may go slightly over. Tools the agent already asked for run before that notice and before any stop, since a provider refuses a chat with anything between a call and its result, and a chat saved that way would refuse its next question too. `max_turns` is only a runaway guard, and the only stop for a model whose price is unknown. A tool call id repeated in the chat ends the run, since RubyLLM would skip the tool and pay for another turn forever.
- **A model call is billed, running its tools is not.** The loop wraps only the generate move in `Inference.track`.
- **The provider is asked to cache what the agent has read.** One agent holds one growing context and resends all of it every turn, so `Investigator` and `Responder` call `with_caching` on the chat. Like tools and thinking, it is a setting on the in-memory chat, so every job applies it after loading. For Anthropic this is the automatic cache that moves forward with the conversation, and providers that cache on their own are unaffected. Opening a group changes the tool list, which sits in front of everything else in the cached prefix, so each one costs one uncached turn.
- **Every turn is written down as it happens**, so a killed worker's successor starts from what was already spent.
- **One worker per run.** `Investigation#claim!` takes a run whose lease has expired and stamps a new `lease_token`, and `record_turn!` renews that lease in the same statement that writes the turn. A worker whose token no longer matches raises `Investigation::Runner::LeaseLost`, and that job is discarded rather than retried.
- **The job that holds a run takes it back at once.** `claim!(by: job_id)` records the holder, and the same job is let in whatever the lease says. Solid Queue never runs one job in two places, and hands a job out again only once its worker is gone, so the same job coming back is proof the first worker is dead. That is what a deploy does: workers get `SolidQueue.shutdown_timeout` (five seconds) to finish, are killed, and their jobs go back on the queue, far too early for a lease to have run out. A different job, which only the sweep creates, still waits out the lease, since the first worker may only be slow. Every claim counts in `attempts`, and a run taken more than `Investigation::MAX_ATTEMPTS` times is given up on, since a run that kills every worker would otherwise be picked up forever.
- **A run is never left held by nobody.** The queue retries within seconds, far inside the lease, so `InvestigationJob` calls `Investigation#release!` before it re-raises and the retry can claim the run. An error no retry can fix (`FirefightAi::TerminalError`, such as a context the model cannot hold) ends the run at once. When a run is given up on, its thread is told, since Slack would otherwise hold a spinner over it, and offered one button to run it again, the same `Identifiers::START_INVESTIGATION` button the incident message carries. A spent budget or a person's stop gets no button, since running again would end the same way. The precise cause (`FirefightAi::Error#reason`, or the error's class) is kept in `error_summary` for debugging and is never shown in Slack or the dashboard. The recovery sweep (`RecoverySweepJob`, every minute, docs/architecture.md, Deploys) enqueues a job for every `Investigation.abandoned` run: one whose lease ran out, or one that was never claimed because its job was lost. A second job for one run is harmless, because the claim decides.
- **The agent starts with a few tools and opens the rest.** `Investigation::Tools.for` hands over `open_tools`, `use_skill`, `read_result`, `record_hypothesis`, `conclude`, the memory tools from `Chat::Tools.memory`, the web tools and the terminal's two tools where there is a sandbox, and nothing else. `use_skill` is the chat's own tool, so a run loads a provider's skill and reads the guides it lists the same way. Common tasks load a skill, below, says how.
- **The agent reads a map of groups and opens the one it needs.** There is no search, so our code never guesses which tool the model means and a miss cannot pass for "I cannot check that". `Chat::Tools::Open` carries the map in its own description, one line per group, about five hundred tokens, built once per run so the front of the request stays the same. Its `group` argument is an enum of the group keys. Opening a group lists each tool with one line and offers the ones whoever acts may use, so full tool details enter the context only for groups that were opened. A group over `Open::LARGE_GROUP` tools lists first and loads only the tools the agent then names. A tool named in `tools` that sits in another group is loaded from there when whoever acts may use it, and the answer names the group that holds it, or says no group has a tool of that name (`Open#elsewhere`). Seen in a real chat, Halon opened Coding agents for the code host's own code change tool, read that nothing was connected there and twice told the person no pull request could be opened. An empty or switched off group also says it is only that group (`Open::OTHER_GROUPS`), so Halon checks the others before saying something cannot be done.
- **A group is the question its tools answer, never the vendor.** `Chat::Tools::Groups::FIREFIGHT` places every Firefight tool in exactly one group, and a test fails when a new tool is in none, so it cannot be left unreachable. A connected provider sits under its category from `config/integration_providers.yml`, so Datadog and Grafana share Observability and the agent does not need to know which one a workspace uses. A category with nothing connected still has its line and says what could be connected. A category's line is its gallery tagline unless the registry gives it a `group` line (`IntegrationProvider::Category#group_line`), for when the gallery's words would send Halon to the wrong group: Code says Firefight's own coding agent writes code changes there with `fix_code` and opens them as pull requests, and Coding agents says it is only for outside agents a workspace chose instead. A connection the registry does not know, or one in the Custom category, is its own group under the name the admin gave it, described by its tools' names. A tool has no kind of its own yet, so a provider that answers several questions sits whole under its one category.
- **The map answers in four ways**, so a gap is explainable rather than invisible: ready, exists but not granted to whoever is acting, connected but with no tools switched on, or nothing connected. A connection whose tools are all switched off is never called nothing connected, since that sends the person to connect what they already have. Grants still decide, and opening a group never widens them.
- **A connection with every tool off is named beside the others.** In a group where one connection's tools are on and another's are all off, the off one has nothing to list, and Halon once used the first connection's tools for the second's project. The group's line in the map says which connections have no tools switched on (`View#idle`, by `Integration#display_name`), opening the group adds "Faylee (Northflank) is connected, but none of its tools are switched on. An admin can switch them on in Integrations." for each, and `use_skill` names a connection of the skill's provider whose tools are all off, or that has a tool the skill needs off while another connection has it on (`UseSkill#off_elsewhere`), with what it reaches.
- **Another system's words are cleaned.** `Chat::Tools.clean` strips control characters and caps the length of every description that came from a connection, one line in a listing and `FULL_DESCRIPTION` on the tool itself. A custom connection's line in the map uses the admin's name for it and its tool names, never what the server says about itself.
- **What the agent found is remembered on the chat.** `Chat::Tools.offer_to` writes each found tool's name to `chats.found_tool_names` as it offers it, and both runners start a turn with `Chat::Tools.known`, so the next question in a chat and a resumed run do not pay for turns searching again. The tools are rebuilt from the catalog for whoever acts now, so a grant taken away since is not handed back. The order is the order they were found and never changes, because the tool list sits at the front of every request and a provider can only reuse what it has read when that front stays the same.
- **A connection that changes while a chat or run goes on is told to the agent.** It would otherwise keep the tools it remembered and tell the person a tool is missing that an admin has just switched on. `Chat::Tools::Changes` keeps what each connection looked like on the chat (`chats.connections_seen`: its `display_name`, its `reach`, whether it is on, its group and its switched on tools) and compares it at the start of every turn and between a tool's result and the next model call (the loop's `take_messages`). A connection added, removed, renamed, pointed somewhere else, switched off or on, or with tools switched on or off, is told once as a nudge nobody reads, naming each change and the groups to open again. Remembered tools the catalog no longer has are dropped from `found_tool_names`, and a connection's newly switched on tools are remembered and offered at once when the agent had already opened their group. A chat that never looked is only recorded. A call to a tool switched off since the agent was handed it is refused with that, not with a missing grant.
- **Firefight's own tools are the same classes the MCP server exposes**, so a tool never means two things and a new one reaches the agent as soon as it exists. A write the workspace granted is offered like any read, since the gateway decides. A system read leaves an `Investigation::Step` but no ledger row, which is how the gateway already treats system reads. A refusal, a pending approval or a provider failure comes back as a result the agent reads and works around, never an exception that ends the run.
- **The map is read with the reach of whoever acts.** `get_resource_map` and every capability's lookup by name find resources through `ResourceMap::Resource.visible_to(acting_principal, workspace)` (docs/integrations.md, Who reads the map), so in a chat Halon sees only the environments the person who asked may read, and a run sees what the investigator's grant reaches. A resource outside them reads as not on the map, and a link to one is left out of a fact sheet and only counted.
- **The map has a group of its own** (`Chat::Tools::Groups::MAP`, "The resource map"): `get_resource_map`, `search_map`, `find_resources`, `get_resource`, `get_resource_links`, `get_resource_neighbours`, `traverse_resource_map`, `blast_radius`, `resource_map_stats` and `suggest_resource_link` (docs/mcp.md, The map tools read alike). They answer where something runs, what it depends on and what fails with it, which is not the catalog's question of who owns what, so they left the catalog group.
- **Capabilities.** Halon reaches logs, metrics, deploys, status and the changes rollback, restart and scale for anything on the resource map through one tool each (`Chat::Tools::Capability`, group `resources`, "Anything on the resource map"), routed to the provider that holds the resource (docs/integrations.md, Capabilities). A resource is named by its name, its provider's id or the map id `search_map` and `get_resource` give, and `connection` lists every connection whose provider answers the capability, its tools on or not. It is not offered the provider tools a capability wraps, and a provider's skill names the capabilities instead (`UseSkill` makes a capability callable when the skill lists it). `run_key_query` (`Chat::Tools::KeyQuery`, in the same group) runs one of a resource's key checks (`ResourceMap::KeyQueries`) through the capability it names, so it is authorized and ledgered as that capability's call, and its answer starts with how the reading compares with the resource's normal, from the baseline the connection that answered read. A fact sheet lists the checks with their normal (`key_checks`), so Halon can start an investigation from the readings most likely to show what changed. `new_log_patterns` (`Chat::Tools::LogPatterns`, in the same group, offered beside `search_logs`) reads a resource's recent logs through the logs capability, so it is authorized and ledgered as that call, and answers the patterns it did not print in the last week and its usual error patterns, never the raw lines (docs/integrations.md, Usual log lines). The fact sheet lists the ten patterns it prints most (`usual_log_lines`). `FirefightAi::NormalRule::RULE`, in both the chat and the run prompts, says a log pattern seen all week is not the cause by itself: lean on what is new or changed, such as a new pattern, a reading above normal or a deploy, and name a usual pattern as the cause only when something shows it changed.
- **An investigation only reads.** `Investigation#reads_only?` is true (a chat's turn is false), so `Chat::Tools.connection_entries` offers a run only read-only tools and the ones whose provider has a read guard (`Integrations::ReadGuards`), and `Chat::Tools::Connection` passes every call to such a tool through its guard first, refusing one that would write with a reason the agent can act on. Northflank's `api_request` passes only GET. No check of a script's text can prove it only reads, so for an investigation Cloudflare's `execute` is offered with the guard's own schema (`ReadGuards::Cloudflare::SCHEMA`): one GET with a path and query, a GraphQL Analytics query as POST `/graphql` (a query naming a mutation is refused), or a Workers log query as POST to `/accounts/<id>/workers/observability/telemetry/query` with its body as data (`ReadGuards::Cloudflare::LOG_QUERY`, the one other POST that only reads), and Firefight writes the script itself with every value as a JSON literal, so the model's words never become code. One read per call while investigating, full scripts in a chat and in a fix. Any other tool that can write, and any of Firefight's own tools that is not `read_only_hint`, is never handed to a run whatever its principal was granted, and is listed as `STATE_READS_ONLY` so the agent is told it is not used while investigating rather than that it lacks a grant. A fix is applied by a person.
- **Reads never wait, in a run or a chat.** No approval rule holds a read and no read asks the person (docs/integrations.md, Reads through a general tool). The investigator holds each connection's read pack from the moment the connection is made, which covers the reads through its general tool too, so a run reads through Northflank's `api_request` or Cloudflare's `execute` by design, each call made a read by the guard's `reading`.
- **What a tool said reaches the model inside a frame.** `FirefightAi::Evidence.frame` wraps every result from one of Firefight's own tools or a connected one in `<tool_result trust="untrusted">` and neutralises any closing tag inside it, so a file or a log line cannot end the frame early. Both prompts carry `Evidence::RULE`, so the wording and the frame live in one place. They also carry `Evidence::REFUSAL_RULE`: a call the provider failed, or that found nothing, says only that one call did not work, so the model reads the error and the provider's skill and tries another way before saying data is out of reach. A permission refusal or a pending approval from Firefight is final, and the model never reaches the same data or change through another tool. A refusal or a pending approval is Firefight speaking and is not framed. A call one of Firefight's own rules refused (`Integrations::PolicyRefusal`, raised by a pack's `fail_policy!` or a read guard), such as a protected branch, a path the connection's Code changes setting keeps out, a statement that would write to a database Firefight only reads, or a pull request that is not ready to merge, is final too. Its reason can name what a provider holds, such as a fork's branch, so it is framed, and `Evidence.refused` follows the frame with `Evidence::REFUSED_BY_RULE`, the line `REFUSAL_RULE` quotes. The model stops pursuing what was refused, tells the person that a Firefight rule refused it and why, with where it is changed when the reason says, and never tries another tool, branch or reworded call. `Chat::Tools::Connection` catches it inside the gateway block, so the step is numbered and cited, the call is marked with the failure kind `refused` (shown as **Refused**, neutral rather than red, in the dashboard and as a complete Slack task with the word Refused), the ledger row is finalized as `refused`, and a capability never falls back to another connection in its place. A read guard's refusal is made before anything runs, then sent through the gateway with `holdable: false` (so no approval is asked for a call that would not run) and recorded the same way. Over MCP an outside agent gets `REFUSED_BY_RULE` then the reason as an error answer (`Mcp::ToolDispatcher.refused`), the ledger says `refused`, and a capability does not fall back. A provider that answers its own failure (`isError`, as a remote server does) fails the call, whether a connection tool was called directly or through a capability, since a capability's reading of the answer keeps an error an error. The chat marks the call failed, the ledger row is finalized as an error with the provider's first line (docs/integrations.md, Ledger), and the model reads the provider's words whole. A capability whose observability tool answered with an error still falls back to the platform, and the call fails only when the answer it ends on is an error, or under `connection: all` when no connection answered. One of Firefight's own tools that answers with an error response is marked and ledgered the same way. The run's `Investigation::Step` keeps what the tool said as a succeeded step, so it is still cited and replayed as before, and the operator console reads the failure from the ledger row. A parser's `^` under the line it read gains a line naming the character it points at and what comes before it (`Evidence.pointed`), since a model cannot count a thousand spaces. The chat prompt also carries `Responder::FAILED_CHANGE_RULE`: a change the provider rejected for something in what Halon sent, such as an expression it could not parse, is Halon's to fix and send again, through the same confirmation as the first, and a message the person adds meanwhile does not cancel it. Halon then says why the first try failed, quoting the provider, and what it changed. The frame is a second layer, and the permission model stays the real defence.
- **Memory** (`Chat::Memory`, table `chat_memories`, text encrypted). A memory is one lasting fact about the workspace's setup. It is about a map resource, a catalog entry (`subject`, polymorphic) or the whole workspace (no subject), and keeps where it came from (`source`) and who taught it (`added_by`, the asker in a chat, nobody in a run). States: `unconfirmed` (what Halon learned, used at once), `confirmed` (a person vouched for it), `disputed` (a live result, a postmortem or a newer memory contradicted it, not used until a person decides), `outdated` (what it is about changed, still used but flagged), `expired` (nobody confirmed it within the workspace's window, not used) and `rejected` (kept so the same wrong idea is refused if learned again). Every state change is one guarded update, and `confirm_blocked_reason` and `reject_blocked_reason` say why a decision is refused. Text that matches the transcript scrubber's secret patterns, or a connection string carrying a password, fails validation (`Chat::SecretFree`, shared with instructions).
- **Who may change it.** Memory is its own gateway resource (`Ability::Action::RESOURCE_MEMORY`). Every member holds `create` and `update` without a grant (`WorkspaceMembership::PARTICIPATION`), like responding to an incident, and an API key or agent needs an explicit grant. The Memory page, the Slack buttons and a chat all ask the same question. In a chat the tools go through `Conversation::Turn#memory_change`, which authorizes as the asker and writes the ledger with ids and flags only, never the fact, since a fact holding a secret is refused only after. A run writes as the agent and never vouches. `Investigation#memory_change` authorizes the investigator through the gateway (`Chat::ToolCall.run!` with the run's `ledger_context`, so Activity shows each save and dispute under Firefight Investigator with the run as its source), on the default `memory.create` and `memory.update` grants. It is not a step of the run, since it checks nothing. An admin who revokes either grant stops it: `remember` or `dispute_memory` answers "Not allowed: this agent has no grant for memory.create in this workspace.", nothing is saved, and the refusal is in Activity. No approval rule ever holds Halon saving, correcting or disputing a memory, in a chat or a run (`holdable: false`), since a broad rule would stop Halon remembering what it was just told. Each change is still authorized and ledgered. The Memory page and the Slack buttons are a person's own change and keep every rule. What a run saves is unconfirmed, with the usual expiry and weekly reminders.
- **Memories follow the map's reach.** A memory about a resource outside the reader's map reach (`Chat::Memory.visible_to(principal, workspace)`) is absent for them: on the Memory page, where deciding on one finds nothing, in a chat's starting memories (the asker's reach), in a run's seed pack (the investigator's), in `recall`, `correct_memory` and `dispute_memory`, and in a decision, a correction or the Correct form from a posted message in Slack (`MemoryPostService`, whose `correctable` takes the presser, so Correct on one opens nothing, as for a memory the message does not show). `remember` about a hidden resource is refused as for a name not on the map. Memories about catalog entries and the whole workspace are unchanged.
- **One way in.** `Chat::Memory.learn!` is how a chat, a run and an ended incident all save a fact. It refuses a fact a person rejected before, skips one already known about the same subject, and saves the rest unconfirmed, or confirmed by the asker when they asked Halon to remember it (`from_person`). A run has no person, so it never vouches. A person writing a fact on the Memory page uses `Chat::Memory.written_by!`, confirmed by them. An unconfirmed memory learned again is touched, so its expiry wait starts over.
- **The same fact in other words is the same fact.** `learn!` compares `Chat::Memory::Words.signature`: the text lowercased, cut to words, filler words dropped (never a negation or a word of order), each stemmed, sorted. That catches a rewording of a known or a rejected memory. It is computed in Ruby over the subject's memories every time, so nothing derived from the text is stored unencrypted. An expired memory learned again goes back to unconfirmed. When no signature matches, the caller's judge (`FirefightAi::MemoryJudge`, one call with no tools on the quick `summary` model, ledgered as `memory_check`) reads the new fact against up to 30 memories about the same subject (whole workspace counts as a subject), in use, expired or rejected, and answers `same`, `contradicts` or `unrelated` for each. The engine gets ids and text and returns verdicts, and `learn!` writes the rows. Same as one in use is known, same as a rejected one is refused. A contradiction saves the new fact and moves each memory it contradicts to `disputed` in one guarded update (`contradicted!`), keeping the newer memory in `contradicted_by` and the reason the caller gave (such as `The deploy log of web shows "..."`, from `remember`'s `seen_in`, or `INC-12 showed "..."` at resolve). A judge that fails (out of credit, no model set up) leaves the fact saved as if nothing were remembered. The `remember` tool and `IncidentLearningService` pass a judge, and nothing else does.
- **A person settles a contradiction once.** Confirming the older memory (Still right) rejects the newer one. Rejecting it without a correction (Not right) confirms the newer one as the person's and records it as the replacement (`replaced_by`). A correction replaces both. This lives in `confirm!` and `reject!`, so the Memory page, a chat card, Slack and `correct_memory` all settle it the same way.
- **A contradiction is asked about where it was found.** `remember` and `dispute_memory` call `Chat::Tools.raise_dispute`: the incident's channel hears it as any dispute (`MemoryNoteJob`, kind `disputed`), and a dashboard chat gets a card at once (`MemoryPostService#ask_in_chat!`, a `Chat::MemoryPost` with the conversation and the evidence as the person read it, then `Conversation::LiveDelivery.memory_asked`). The card (`AgentChatMemoryQuestionSerializer`, prop `memoryQuestions`) says what Halon remembered, where it came from and who confirmed it (`origin_for`, `trust_for`), what showed otherwise, and offers Still right, Not right and Correct, which post to the Memory page's own actions and come back to the chat (`redirect_back_or_to`). Once settled it says how (`decided_for`). The tool's answer tells the model which memory is disputed. A contradiction found at resolve posts a `disputed` message for each before the new lessons. The extractor is also handed the workspace's memories on the incident's subjects and the workspace wide ones, rejected ones marked (`LessonExtractor::Remembered`), so the model does not relearn them in the first place.
- **What is never learned is refused in code.** `Chat::Memory::Screening` refuses a live value (a date with a time of day, a number said to hold now, or text mostly made of readings such as 850ms and 4.2%) and a fact about a person (an address, a mention, a member's full name, or a first name as written and not opening a sentence), with a sentence the agent reads. It leans towards saving, and its test lists setup facts with numbers in them that must pass. It reads the text with credentials redacted, so a secret is still refused as a secret.
- **Naming what a memory is about.** `Chat::Memory.subject_named` answers a subject or a refusal: a resource by name, provider id or id, or a catalog entry by name, slug or id. A name nothing has is refused (remember says so and saves nothing, offering the whole workspace by leaving `about` out), and a name several share lists each id. Recall also looks among resources gone from the map when nothing present has the name, and says the resource is gone.
- **Search finds confirmed memories.** `search_map` and the dashboard's search (docs/integrations.md, Searching the map) match the reader's visible confirmed memories at search time, in Ruby, with the same word scoring as recall (`Chat::Memory.matching`), since the text is encrypted and nothing derived from it is stored. Memories are never written to `search_documents`. A memory is searched only with `memory: read` and while Halon is available, since its result opens the Memory page.
- **Using memory.** Every chat and run holds `remember`, `recall` and `dispute_memory` (`Chat::Tools.memory`), and a chat also holds `correct_memory`. A chat starts with up to 20 memories about what its incident touches (`Chat::Memory.subjects_for`, the incident's catalog services and the resources they run on) plus the workspace wide ones, confirmed first, in `Conversation::Runner#context`. A run gets the same in its starting facts under `memories`. Being handed one at the start counts as a use once for each chat or run (`Chat::Memory.handed_to!`, one `Chat::MemoryUse` row each, unique), however many turns it takes, and so does each recall. A rehearsal never counts. `FirefightAi::MemoryRule::RULE` in both prompts says a memory is a hunch to check, never proof, and to say so when relying on an unconfirmed one. `CHAT_RULE` is only in the chat prompt, since only a chat has `correct_memory` and a person to vouch. Recall matches text in Ruby over one workspace's memories, because the text is encrypted: every asked word counts, stemmed, a rarer word more, the whole phrase found as written adds a boost, then confirmed first, then newest. It answers with at most 20 and says how many more matched. When a person says a memory is wrong or asks to forget it, `Chat::Memory#reject!` keeps it as rejected with who (`rejected_by`), when and why, and a correction they gave replaces it as confirmed by them (`replaced_by`). In Slack this works wherever Halon already answers a mention, meaning incident channels and their threads.
- **Learning at resolve.** The close workflow's last step queues `IncidentLearningJob`. `IncidentLearningService` hands `FirefightAi::LessonExtractor` the investigations' findings (not one the team marked wrong), what Halon got wrong (an answer the team marked wrong, with its cause, and a fix that was applied and then undone), which the extractor turns into a lesson about what the symptom really meant only when the other sources show it, the incident summary and the last 300 transcript messages, with the names of what the incident touches, and gets back at most three lessons, each 0.7 sure or more. The service saves each through `learn!` with the incident as its source, and `MemoryPostService#post!` asks the channel about the new ones. It posts only when something new was learned.
- **Every message asking about memories is a `Chat::MemoryPost`.** It keeps the memory ids it first showed, so a redraw after a decision shows those and nothing learned since (a deleted one drops out). Kinds: `incident` (at resolve and a late mistake), `postmortem`, `learned`, `disputed` and `reminder`. A post sits in a channel (`channel_id`, the direct message's channel for a reminder to a person, kept from what the platform answered so a redraw finds it) or in a dashboard chat (`conversation_id`), and the database holds that one of them is set. A decision's reason names the place (`MemoryPost#place`: the incident, a reminder or a chat). `Slack::Messages::LearnedMemories` gives each memory the actions its state allows: Confirm, Not right and Correct while it waits, Still right in place of Confirm for a disputed or outdated one, and a line saying who decided once decided, with the corrected wording when there is one. Buttons carry `post id:memory id` (`MEMORY_CONFIRM`, `MEMORY_REJECT`, `MEMORY_CORRECT`, all `memory: update`). Correct opens `Slack::Modals::CorrectMemory` synchronously, and its submission (`Interactions::CorrectMemoryHandler`) rejects and replaces the memory as whoever wrote it. A button on a message posted before posts were kept names its incident instead, and redraws every lesson the incident has, as it did then. A channel archived since leaves the memories on the Memory page, and no post row is kept.
- **A chat or run on an incident tells its channel.** When `remember` saves a memory or `dispute_memory` disputes one, `Chat::Tools.tell_incident` queues `MemoryNoteJob`, which posts a `learned` or `disputed` message in the incident's channel, in the run's or the Slack chat's own thread when it has one there, at the top otherwise. Outside an incident nothing posts, and the Memory page's count is the sign.
- **A postmortem never overrules a person.** A postmortem marked completed (`Postmortem#update_status!`, after the change is recorded) queues the job again with the postmortem as a source and the incident's lessons listed. Its decisions are credited to whoever marked it completed (`Postmortem#completed_by`, read from its history), never the draft's author, and to no person when that was a key or an agent. Every decision keeps the postmortem (`decided_by_postmortem`), and Halon's line reads "confirmed by a postmortem" when no person stands behind it. It confirms what it agrees with only from unconfirmed, outdated or expired. What it contradicts is rejected and replaced when no person confirmed it, and disputed with the postmortem's correction in the reason when a person did, for a person to decide. New lessons are posted like resolve lessons, titled "What Halon learned from the INC-x postmortem". The extractor runs on the `lessons` purpose (`LESSONS_AI_MODEL`), which falls back to the citation re-check's model.
- **Learning from a late mistake.** When a finding's settled outcome becomes `wrong` after its incident closed (`Finding#relearn_after_mistake`, from `settle_outcome!`, once per finding through a guarded `relearned_at`, never for a rehearsal), `IncidentMistakeLearningJob` runs `IncidentLearningService#learn_from_mistake!`, which asks the extractor (`only_mistakes`) for at most one lesson about what Halon got wrong, read against every lesson the incident has, rejected ones too, and the completed postmortem when there is one, and posts it for the channel to confirm. An archived channel keeps the lesson on the Memory page instead. The extractor never restates a lesson learned before, in any words. A fix that was undone is described as possibly wrong or only temporary.
- **Past answers carry their outcome.** A past incident in the seed pack gives its run's answer with `finding_outcome` (confirmed, partial, wrong, or not rated), preferring a confirmed answer, and the investigator prompt reads a confirmed one as a worked example and a wrong one as a mistake not to repeat.
- **When what it is about changes.** A sweep that renames a resource writes a `renamed` change, and one that stops seeing it writes `removed`. A catalog entry renamed or archived (alone, or with its type) does the same. Each time `Chat::Memory.flag_outdated!` moves the subject's unconfirmed and confirmed memories to `outdated` with the reason and the cause, keeping what each was (`outdated_from`), in one update. A rejected, disputed or expired memory keeps its state. A removed resource the map sees again lifts only the flag its removal set (`clear_outdated!`), and a memory a person decided on since is no longer outdated, so it is never touched.
- **Expiry is the workspace's choice.** `workspaces.memory_expiry_days` is off by default, so an unconfirmed memory is used until a person decides. An admin can pick 30, 60, 90 or 180 days under Settings, Workspace (or `update_workspace_settings`), and the hourly `MemoryExpiryJob` moves an unconfirmed memory unchanged for that long to `expired`, out of use. Learning it again counts as a change, so the wait starts over. A person can still confirm it.
- **Reminders reach the person who should know.** `MemoryReminderJob` runs on Mondays at 15:00 UTC (`config/recurring.yml`) in each workspace with a chat platform where Halon is available. `Chat::Memory::Reminders` picks unconfirmed memories at least three days old: one a person taught goes to that person by direct message, about their own knowledge only, and what runs and incidents taught goes to the incident's channel, or to every admin by direct message when there is no channel or the channel could not take the message (archived since). Each person or channel gets at most one reminder in six days, only when something waits, at most five memories, and never a memory its last reminder showed. An admin's own memories come first. `MemoryPostService#remind!` posts each as a `reminder` post, in a channel through `post_learned_memories` and to a person through `post_learned_memories_to_user`, whose opening line says how many wait and why (`LearnedMemories.intro`), with Confirm, Not right and Correct on each memory and a link to the Memory page. Members without a platform account are left to the Memory page.
- **A run's starting memories are encrypted, and a change reaches the run.** `Investigation#seed_notes` (encrypted, JSON) holds each starting memory's id and the line the run read, and the instructions. `seed_pack` keeps only facts from the incident and the map. `Investigation#starting_facts` is what the agent, a rebuild and the operator console read: the pack with the notes put back, each memory that was since disputed, rejected, corrected, expired or deleted marked in place. At the run's next step `untold_memory_changes!` hands the agent a short note for each such change, once, as a nudge nobody is shown. A rehearsal reads what its original read and is told nothing.
- **The Memory page** (`/memory`, `MemoryController`, `pages/memory/`, only while Halon is available) lists every memory with its state, source, who vouched and how often it was used, filtered to in use, unconfirmed, possibly outdated, disputed, expired or rejected. Confirming, correcting (`reject!` with a correction), rejecting and deleting one is `memory: update`, and adding one is `memory: create`. A decision goes back to the page it came from with its filter kept, and a decision the memory refuses stays visible and inert with the reason as its tooltip. The tab counts what waits on a person (`awaiting_decision?`: unconfirmed, disputed or possibly outdated). Delete asks first and is for good. Deleting a rejected memory says its wording may be learned again, since nothing is left to refuse it (`delete_consequence`). Writing instructions is `catalog: update`. The serializer ships `in_use`, `awaiting_decision` and both blocked reasons, so the page never reads a state to decide what to offer. The map's focus panel shows each resource's memories and instructions.
- **Instructions** (`Chat::Instruction`, table `chat_instructions`, text encrypted) are how people want Halon to work, not facts. A place holds one current set: the workspace (no `scope`), a catalog entry such as a team or service, or a map resource, at most 2000 characters. A partial unique index backs the rule, so two people saving the first instructions for one place at once get the same refusal. An edit (`revise!`) supersedes the current set and writes a new one linked by `superseded_by`, and removing (`retire!`) supersedes it with no replacement, both as one guarded update so two editors cannot both win. The page shows the earlier wordings (`Chat::Instruction.with_history`). `Chat::Instruction.for_subjects` returns the workspace's, then those of the teams that own the catalog entries a chat or run touches (their relationships to a `team` entry), then those on the entries and resources themselves, most specific last. A chat gets them in its context, headed apart from memories, and a run in its seed pack under `instructions`. `FirefightAi::MemoryRule::INSTRUCTIONS` in both prompts says to follow them, that the more specific one wins, and never to treat one as evidence.
- **Instructions follow the map's reach, like memories.** Instructions about a resource outside the reader's map reach (`Chat::Instruction.visible_to(principal, workspace)`) are absent for them: on the Memory page's Instructions tab, with their history, where editing or removing them is a 404, in a chat's context (`for_subjects(..., principal:)` with the asker), in a run's seed pack (the investigator's reach) and on the map page's panel (`ResourceMap::View`). Writing instructions for a hidden resource is refused as for a subject that does not exist, since `subject_for_key` takes `principal:`. Instructions about catalog entries and the whole workspace are unchanged.
- **Halon writes like Firefight's own copy.** Every prompt that writes for a person carries `FirefightAi::Copy::RULE`: no em dashes and no semicolons (a full stop, comma or parentheses instead), never a pronoun guessed from a name (the person's name, or they and them), and a person's own words given as a reason quoted exactly, never reworded stricter or looser. The coding agent gets the same through its brief (`Copy::PEOPLE`), its question tool and the person's words it is handed (`Copy::QUOTING`). `test/services/firefight_ai/copy_test.rb` in the engine holds the chat, investigation and incident channel prompts.
- **A result too large to hand over whole is saved, never cut.** `Chat::Tools.hand_over` compares a result with `Chat#result_limit`, a tenth of the running model's context window, so a model with more room is handed more and nothing is retuned. A larger result is kept in full as a `Chat::SavedResult` (encrypted, named `result_1`, `result_2` within its chat) and the model is handed `Evidence.preview`: how it starts and ends, cut between lines, how long it is, and which line shapes repeat most, which is often the clue itself. The agent always holds `read_result`, which reads a range of lines or searches, and with no result named searches everything saved in the chat, which is how two logs are lined up on one request id. Reads come back a page at a time, framed like any other result. Search is plain text, since a pattern would let a result choose what a search costs. `read_result` reads what the chat already fetched, so it goes through no gateway call and leaves no step. Counting and joining across whole logs is not what this is for, that belongs to the provider's query language and later to the read only shell. Compaction will point at the same saved results, so a shortened step can still be read again.
- **A run never waits for a person.** A call an approval rule holds says so and was not run, and nothing is kept to run later, since the run has ended long before anyone approves it (`Investigation#hold!` returns false). A chat keeps such a call and asks the person to run it once approved (Conversations, Approved, ready to run). A fix's steps follow the same pattern (docs/integrations.md, Approvals).
- **No environment is chosen.** A tool call passes no scope, so a connection with more than one environment cannot resolve one and the call is refused. Per run environment scoping lands with the approval work.

## Making room in a long run

One agent holds one context, and a real investigation reads more than a window holds. `FirefightAi::AgentLoop::Room` decides when a chat has to make room, and the chat's own record does it (`Chat::Compacting`). The loop is handed the saved chat as `memory:`, and the engine only ever calls `context_window!`, `clear_old_results!` and `rebuild!` on it.

The rules:

- **The window is known or the agent does not run.** `Chat#context_window!` reads the model registry and raises `Chat::UnknownWindow` when it holds none. Nothing is assumed in its place. `Investigation.unavailable_reason` checks it up front, so a chat, a run and a Slack mention all refuse with "not fully set up" while the log names the model (`ai.model_without_context_window`), and `RefreshModelRegistryJob` warns nightly (`ai.models_without_context_window`). A model the library does not know gets a registry row with its window, the same place it gets its price.
- **How full it is comes from the provider.** Each reply reports what the model read, fresh and cached, and what it wrote. Before a turn `Room` adds an estimate, four characters to a token, for the tool results that arrived since, which the provider has not seen yet. After a compaction the last count no longer describes the chat, so the estimate covers the whole chat until the next reply.
- **Stage one, at half the window, clears old tool results.** No model call. `clear_old_results!` keeps the newest `KEEP_RECENT` whole and moves each older one into a `Chat::SavedResult`, leaving a framed line that keeps its tool and step and names where the full text went. The agent reads it again with `read_result`, which is free and never touches the provider it came from. A result that was already saved because it was large is pointed at, not saved twice. A clear that would free under `MIN_FREED_SHARE` of the window is skipped, since every clear costs one uncached turn.
- **Stage two, at three quarters, rebuilds.** Only when clearing did not free enough. The agent first gets one turn with no tools to write itself a note with everything still in view, billed like any turn. `rebuild!` then saves every remaining result, marks the working messages `archived_at` and starts again from one message: `owner.memory_brief` (for a run the seed pack, each theory with where it stands and the steps it rests on, and every step), the saved results, the note, and the last `RECENT_IN_FULL` results whole. The instructions are applied again word for word, never summarised.
- **A conversation is never put away.** `Conversation#keeps_in_memory?` keeps what the person and the agent said to each other and puts away only the work in between. The note is marked like a nudge, so it is never read back as something the agent said to the person.
- **Nothing is deleted.** `sent_messages` is what the model is sent, `messages` is everything, which is what a person reads and a replay needs. Step numbers never change, so a citation made before a rebuild still means the same step after it.
- **The backstop.** A provider that still says too long gets the chat rebuilt without a note, since the model cannot be asked, and one more try. A second refusal ends the run.
- **Every event is a `Chat::Compaction`** with the stage, the tokens in use before, what was freed and how many messages it touched, so the two thresholds are tuned from what really happened.
- **The dashboard shows each one, Slack does not.** Both stages read the same to a person, `Chat::Compaction::SHOWN_AS` with its time, as a quiet line of step kind `room` (`Chat::Compaction::STEP_KIND`) that is never counted as a step. A chat's page gets them as the `compactions` prop (`ChatCompactionSerializer`) and places each ahead of the reply written after it, using each message's `createdAt`. While a turn runs, `Chat#on_making_room` tells the runner, and `Conversation::LiveDelivery#made_room` broadcasts `made_room` so the line lands where it happened. A run's story gets them on `InvestigationDetailSerializer#compactions`, placed before the first step that started after it, and the page's poll picks up new ones. A Slack thread (`Conversation::Delivery#made_room`) and an MCP chat show nothing. The note is never sent to a page, since it is the agent talking to itself about what it read.
- **Not used: the provider's own compaction.** It differs per provider, cannot point back at our steps, and does not exist on an open source model.

## Helpers

Halon hands reads that do not depend on each other, such as the logs, the recent deploys and the error rate of one service, to helpers that run at the same time, rather than reading them one after another. A chat and a run both hold `run_helpers` (`Chat::Tools::Helpers`), and both prompts carry `FirefightAi::Helper::RULE`, which says when to use it and what to keep for itself.

| Piece | Holds |
|---|---|
| `Chat::Helper` | one handed off check: its title and brief, `deep`, status (`running`, `reported`, `failed`, `stopped`), the report (encrypted) or why it ended without one, the model, what it spent, and a chat of its own (`own_chat`) |
| `Chat::Helpers` | runs one call's checks together and answers the asking loop. `Share` is what the asking turn or run lends them |
| `Chat::Helpers::Run` | one helper on its own thread: its chat, its tools, the loop |
| `Chat::Helpers::Agent` | what the shared tools ask of whoever they run for, for one helper |
| `FirefightAi::Helper` | the prompt and the loop, in the engine. It names no app model |
| `FirefightAi::AgentLoop::Purse` | what a run has spent, shared with its helpers across threads |

The rules:

- **A helper only reads, as whoever the chat or run acts for.** `Chat::Helpers::Agent#reads_only?` is true, so the catalog offers it only tools that read and those whose provider has a read guard, never one of Firefight's own that writes. It never confirms or holds a call: a read an approval rule holds says it needs an approval and was not run, and the helper says so in its report. Every call goes through the asking turn's or run's own `tool_call`, so it is authorized as the same principal, ledgered under the same source (`conversation` or `investigation`) and, in a run, recorded as a numbered `Investigation::Step` the answer cites. A helper never reaches further than the person, key or agent it reads for. It gets its own copy of the turn or run (`Share#fresh_parent`), since a record is never shared between threads.
- **Its tools.** `open_tools`, `use_skill`, `search_docs` and `read_doc`, `read_result` over its own chat's saved results, `recall` and the web tools where the workspace has them on, plus every tool the asking chat already found that it may read with (`Chat::Tools.known`), so it does not pay for turns finding them again.
- **Its model.** The side jobs' model (`AiPurpose::HELPER`, a child of `SUMMARY`, and in `AiPurpose::QUICK` so a workspace's own account runs it on its fast model). A check marked `deep` runs on the main model, for one that reasons across several results such as reading code. When the registry knows no context window for the side model, helpers run on the main one (`Chat::Helpers.side_model`), since a helper makes room from its window like any agent run. A rehearsal runs helpers on the deployment's account, and one comparing models runs every helper on the model it compares.
- **One budget.** The asking loop's spend is a `Purse` it passes to the engine (`purse:` on `Responder#run` and `Investigator#run`). Each helper is given an equal part of what is left, with one more part kept back for the loop that asked, never less than `Chat::Helpers::MIN_SHARE_CENTS`, and every turn it takes is added to that purse as it happens. The loop counts the purse when it decides whether the budget is spent, and reports the helpers' spend to the runner as soon as the tool answers (`AgentLoop#report_spent_beside`), so a conversation's running totals and a run's `spent_micros` include it. A helper takes at most `FirefightAi::Helper::MAX_TURNS` (12) turns.
- **Limits.** At most `Chat::Helper::MAX_AT_ONCE` (4) checks in one call, all run at once. At most `MAX_PER_QUESTION` (8) for one question to a chat, counted from when the turn began, or for one run. At most `MAX_RUNNING_IN_WORKSPACE` (12) running in a workspace at once, across every chat and run, claimed under a per workspace advisory lock so two chats handing off together cannot pass it. At most `Chat::Helpers::THREADS_PER_PROCESS` (6) helper threads in one worker process, so the database pool sized for the worker's own threads always has room, and a helper past it waits for another to finish. Over a limit the call answers why, and Halon reads the rest itself.
- **A helper's report is its plain reply**, at most five lines, ending each finding with the steps it rests on when results carry step numbers. The asking loop reads one line per helper (`Chat::Helper#line`), framed as evidence. A helper that runs out of its share, takes too many turns, fails or is stopped ends with a sentence saying so (`Chat::Helper::OUT_OF_BUDGET`, `OUT_OF_TURNS`, `COULD_NOT`, `STOPPED`), and never takes the others with it. A call where no helper reported is marked failed.
- **Stopping.** A person's stop reaches every helper through `Share#canceled` (the chat's stop flag, or the run's `cancel_requested`), checked between its turns. A helper still running when its asking call is closed as interrupted (a worker that died) ends as interrupted (`Chat::Helper.interrupted!`, from `Chat#close_unfinished_calls!`). Every move out of running is one guarded update.
- **Shown in the dashboard chat.** The `run_helpers` step reads "3 checks at once" with the checks' titles, and opened it lists each check's brief. It carries the `helpers` card (`Chat::Tools::CARD_HELPERS`), which, unlike other cards, is sent while the step runs (`Card#shown_while_running?`). The page draws each helper of that call under the step (`helper-runs.tsx`, from the `helpers` prop, `AgentChatHelperSerializer`) as a trace of its own, open while it works and collapsed after, with every step it took and what it reported, or why it has no report, always in view. A share's `moved` is `Chat::Helpers.teller(delivery, chat)`, called with the run_helpers call's id when the helpers start, at most once a second per helper while they take steps, and when each ends. It reads that call's helpers again and hands them to the delivery's `helpers`, one call at a time under a lock, since helpers tell it from their own threads.
- **Each delivery shows them its own way.** The dashboard chat (`LiveDelivery#helpers`) broadcasts `helpers`, and the page reloads only that prop and the charts. A Slack thread, for a chat (`Conversation::Delivery#helpers`) or a run (`Investigation::Delivery#helpers`), shows each helper as a task of its own right under the step, titled with the check and with details such as "2 steps, reported" (`Chat::Helpers.line`), redrawn in place by its key no more often than `agent_step_update_interval` except when it ends (`Chat::CodeFixProgress::Pace`). A helper with no report is marked as an error. An MCP chat and a rehearsal show nothing.
- **A run's page groups each helper's steps.** A step a helper made keeps it (`investigation_steps.chat_helper_id`, through `Investigation#tool_call(helper:)`), and `InvestigationDetailSerializer` ships the run's `helpers`. The story (`components/investigations/story.ts`) takes those steps out of the run's own order and places one entry per run_helpers call where its helpers started, drawn by `helper-groups.tsx`: each helper folded to its title, how it ended and its step numbers, with its report or why it has none always in view, and opened to its steps as ordinary step rows. Step numbers stay the run's own, so a claim still cites them, and a helper holding the step a link points at opens itself. A theory settled by a helper's step is told right after the group.
- **Long chats.** A helper's report is a short tool result, so the asking chat stays small. A rebuild (Making room in a long run) carries the newest `Chat::Compacting::HELPERS_REMEMBERED` (12) reports in the fresh start, so what helpers found outlives the work that was put away. A helper's own chat makes room the same way, and starts again from its brief (`Chat::Helper#memory_brief`).

## Similarity search

`SearchEmbedding` holds one vector per record, and `search_similar` is how the agent asks what looks like a situation rather than what matches its words. Incidents, findings and postmortems are embedded, and pgvector does the ranking. Catalog entries are embedded too, from their name, type, what they are for and their written attributes, once they have a description (`CatalogEntry::Searchable`), so a search of the map can find a service by what it does.

The rules:

- **Every incident is searchable, open ones included**, since a live incident that reads like a past one is the point. A match says whether it is still open, so an unfinished one is not presented as an answer.
- **An incident is embedded from what people wrote**: its name, summary, alert titles, the summaries it had along the way and its milestone notes. Not its status changes, which say nothing about what happened.
- **The embedding model is its own purpose** (`AiPurpose::EMBEDDING`, `EMBEDDING_AI_MODEL`) and deliberately not overridable per workspace. Every vector in a workspace must come from one model, so changing it means writing them all again.
- **A record is embedded again only when its words change.** The row keeps a digest, and `WriteSearchEmbeddingJob` writes nothing when it matches.
- **Asking for a vector is a call to another system, so it lives in `SearchEmbeddingService`.** `write!(record)`, `similar_to(query)` and `query_vector(query)` are the only places `FirefightAi.embed` is called. `query_vector` is the map search's (`MapSearchService`), asked for only when a catalog entry could be found by meaning (the reader may read the catalog, the query is four characters or more and the workspace has catalog vectors from the current model), and the same words reuse it for ten minutes, since a search box asks again as each word is typed. A failed call leaves the search answering by words. The models say what to embed (`search_text`, `search_embeddable?`) and rank a given vector (`SearchEmbedding.nearest`), and never call the engine.
- **Nothing is backfilled**, except catalog entries. Incidents, findings and postmortems written before this landed have no vector until they change. A catalog entry is embedded once when `SearchDocumentBackfillJob` first indexes it for search (docs/integrations.md, Search rows), since a workspace's catalog is small and searching it by meaning needs every description.
- **pgvector is required**, and the column is fixed at 1536 numbers wide.
- **A postmortem is embedded once it is completed**, not on every save while someone is still writing it.
- **The search is authorized as an incident read**, so a finding is left out unless the caller also holds `investigations.read`. The types a caller may see are decided per call.
- **Rows written by an older embedding model are ignored**, since a vector from one model says nothing about a vector from another. Changing the model makes search quiet until records are written again.
- **The tool is an MCP tool**, so our agent reaches it through its grants and an outside agent gets the same thing.

## Conversations

A `Conversation` is a person talking to the agent, which does the work a question needs itself, however deep. An investigation is the saved record of a run someone asked for. Both run on `FirefightAi::AgentLoop`, share `Chat::Tools` and save their chat in the same table. `FirefightAi::Responder` holds the prompt, `Conversation::Runner` is the app half, and `Conversation::Delivery` is what it says while it answers.

The rules:

- **A mention is the entry point.** `@Firefight` in an incident channel always reaches the agent, in a conversation on the mention's thread. There is no one-off reply to a mention any more. `IncidentResponder` only answers `/ff catchup`.
- **Asking is the same permission everywhere.** A mention, the dashboard chat and `ask_halon` all need `investigations.create`, which every member holds without a grant until an admin narrows it (docs/integrations.md, A default a grant narrows). A mention goes through `Conversation.ask_from_thread!` (`AbilityGateway.authorize!` with `holdable: false`) before it opens a conversation, so it is in Activity like the others but never held by an approval rule (nothing in a thread could resume it), and a refused member is told the dispatcher's sentence, only them. Service keys and agents need a grant.
- **One conversation per thread.** `Conversation::Opener` joins the one already there, so a second mention continues rather than starting over, and the unique index on workspace, channel and thread is the guard.
- **A reply ends the turn.** `reply_is_answer` is the only difference in the loop: in a chat the person is waiting, so plain text is the answer, and in a run only `conclude` ends it.
- **An answer that rests on a connected system is checked before it goes out.** Once a question has read from a connection (`Workspace#reading_tool_names`), `Conversation::Runner` hands the loop `FirefightAi::Responder::CHECK`. The loop does not stream a reply while a check is owed, holds the first answer (`Chat#hold_last_reply!` marks it like a nudge, so the person never reads it), asks the check once, and the reply after it is the answer. The check only runs new tool calls for a claim that goes beyond what a result showed, such as a cause, a diagnosis or a recommendation. A draft that only repeats results comes back unchanged with nothing run, so a plain lookup costs one short extra model call instead of repeating its queries. Answers from Firefight's own records, and the last turn a budget buys, go out as written.
- **The chat does the work itself.** There is no line between a lookup and an investigation. The prompt tells it to check only what the question needs and to stop once it can answer. `start_investigation` is called only when the person asks for an investigation. In an incident's chat the run is on the incident, anywhere else it is on the person's question and answers in the chat.
- **A message sent while the agent works joins that turn.** `Conversation#ask!` queues it as a `Chat::QueuedMessage` while an answer is owed, and the loop's `take_messages` hook adds it to the chat between a tool's result and the next model call, the only place a new message keeps the chat valid for a provider. Only the asker's own messages join a turn, since the turn acts with their permissions. The job queued behind the turn takes whatever is left and does nothing when the turn before it already answered. The page shows a waiting message under the turn (`AgentChatsController::PROP_WAITING_MESSAGES`) until it is read.
- **The dashboard places what streams by when it was sent.** Action Cable hands broadcasts to a pool of threads, so a turn's events can reach the page in any order. `Conversation::LiveDelivery` stamps each with `seq`, microseconds since the epoch and never repeated within a turn, and `pages/agent/lib/stream-order.ts` places text and steps by it: an older status never overwrites a newer one, and a late start of the turn drops only what was sent before it.
- **A run started from a chat is recorded as one.** `Investigation::TRIGGER_CONVERSATION`, not the command trigger, so the record says where it came from.
- **A tool that takes a whole form is shown as the form's fields.** `Chat::Tools.shown_arguments` flattens an argument whose value is a flat hash, such as `answers` on `declare_incident`, into one row per field, so the headline is the incident's name and a reader never sees a Ruby hash. Any other nested value is one line of JSON.
- **A call is never left without its result.** A provider refuses a chat with anything but results between a call and the next message, so one call left open makes it refuse every later question. A call is left open by a worker killed while it ran, or by a person asking something new while a call waited for them to confirm it (a question asked then is saved after the call, since no answer is owed). Both runners call `Chat#close_unfinished_calls!` (`Chat::UnfinishedCalls`) before the loop starts, so only the run's holder does it: the reply job under its per conversation lock, a run under its lease. It gives each open call a result placed right after the call's own results, under a row lock that makes a second close add nothing. A call nobody is waiting on is `INTERRUPTED`, marked failed, so its step shows that it did not finish rather than spinning, and the model reads that it did not complete and that a change it was making may or may not have taken effect. A confirmation the person moved past by asking something else is withdrawn: the model reads `NOT_CONFIRMED` and the call's approval becomes `Chat::APPROVAL_WITHDRAWN`, so the confirm card goes and its step shows as cancelled. In a thread the confirmation message is redrawn saying it was withdrawn, with no buttons (`Conversation::Delivery#withdrawn!`, from `conversations.confirmation_message_id`, kept when the confirmation is posted). A call still waiting for the person, or confirmed and about to run, is left while nothing was said after it. A run also fails each `Investigation::Step` still running when it is taken up (`Investigation#close_interrupted_steps!`), with the same words.
- **A reply whose worker died is run again once or ended.** The queue fails a job whose worker was killed (a deploy, a crash) and never retries it, so nothing would answer. The recovery sweep (`RecoverySweepJob`, every minute, docs/architecture.md, Deploys) calls `Conversation::Recovery`, which looks at each conversation owed an answer for between `SETTLING` (a minute, while its job is being queued) and `REPLY_CEILING`, MCP chats aside since they answer inside the request. A conversation with a reply job queued, waiting behind the per conversation lock or claimed (`Conversation::ReplyJobs`, by the job's concurrency key) is never touched. Otherwise, when a reply job failed since the turn began, nothing in the turn called a tool that changes things (`Chat::Tools.kind`) and the turn was not run again before, the same job is retried (same asker, same held call) after `Conversation#rerun_lost_reply!` stamps `reply_recovered_at`. Every other lost turn is ended by `Conversation#end_lost_reply!`: its open calls are closed as interrupted, and "I was interrupted before I finished. Ask me again." is saved and said in the chat and its thread, which also clears the thread's working status. The answer the lost turn was writing is ended where it stopped: a thread's open answer (`conversations.answer_message_id`, kept from `thinking!` until the answer is finished there, with `answer_shown` once anything showed in it) gets "Interrupted here." as its last line, or is removed when nothing showed (`end_interrupted_answer`), and the dashboard's empty saved reply is removed, since the page never keeps streamed text. Both transitions are one guarded statement on `answer_owed_since` as it was read, so a turn started since, or taken by another sweep, is left alone and a turn is run again at most once. `InterruptedJob`, which runs again every other job a stopped worker failed, leaves reply jobs to this (`ConversationReplyJob.runs_again_when_interrupted` is false), since a turn that may have changed something is never run again. A run whose worker died is taken up again by the same sweep once its lease runs out, and given up on with its thread told after `Investigation::MAX_ATTEMPTS`.
- **A call that refused or errored is marked failed.** The words still go to the model, but `ruby_llm_tool_calls.failed` is set by the wrappers (`Chat::Tools.mark_failed`) on a denial, a tool error or an error response, and both the live step event and the saved serializer report `STATUS_FAILED`, so a card says Failed rather than Completed.
- **What a step got back.** An opened step shows, below what it was given, what came back, built by `Chat::StepOutcome` from what is already kept for the call and never a second copy: the tool's answer (`ruby_llm_tool_calls.result`, out of its frame, or the `Chat::SavedResult` a preview or a cleared result names) and how it failed (`failed` with `failure_kind`). A failed call shows the provider's words, without Firefight's `<action> failed: ` or a server's `Error: ` before them, on at most two lines. An answer shows its first four lines (JSON laid out over many lines as one compact line), how many lines and characters it holds, and the page it came from when its text names one (`Integrations::SourceLinks.cited_in`, https only). Everything shown passes through `Chat::SecretFree.redacted` again. The saved step (`AgentChatMessageSerializer`) and the live `step` event (`Conversation::LiveDelivery`, read by `Conversation::Runner#outcome_of` once the loop reports the step done, after the wrapper marked the call and RubyLLM saved its answer) carry the same `outcome`. A run's step reads the same way from `Investigation::Step` (`InvestigationStepSerializer#outcome`), where a call that raised keeps its reason in `error_summary`, shown without the error's class name.
- **A not found answers a check, it does not break it.** When a call that reads is answered by the provider saying the thing named is not there, the call is kept with `failure_kind` `not_found` and shown as Not found with a neutral mark, not a red cross, and it does not hold the trace open. It is decided only from what the provider answered, never from the agent's words: `Integrations::Outcomes.not_found?` takes an error marked `Integrations::NotFound` (every client's 404, docs/integrations.md) or a remote server's own answer read by its provider's `error_reader`, and only for a call shown to read (the tool is `read_only`, or its provider's `read_guard` answers `reads?`, so a Cloudflare script that is one GET counts and any other script does not). A run only reads, so a run's raised not found is settled by the error alone (`Investigation::ToolCall`). Anything else that failed is `failure_kind` `error` and stays red with its reason: a 5xx, a refusal, a bad request, a timeout, a change the provider answered not found. The ledger is untouched by this: the call is still an `error` with the provider's first line (or the exception's class for a raised error), exactly as before, so the two say the same call failed and only the step's look tells a not found apart. The model reads the same words either way.
- **A run's step keeps its status.** A call whose provider answered an error ran, so its `Investigation::Step` stays `succeeded` and can still be cited, while `failure_kind` (set by `Investigation#mark_step_failed!` once the step is numbered) makes the story show it as failed or not found. A raised error fails the step as before, with the kind beside it, and a replay copies the kind with the result.
- **An outside agent asks over MCP.** `ask_halon` runs one turn synchronously as whoever the credential resolves to, on a `KIND_MCP` conversation kept per principal, with `Conversation::QuietDelivery` so nothing streams. `start_investigation` and `get_investigation` do the same for runs. See docs/mcp.md, Halon, the agent.
- **A step through a connection is named by the call and the connection.** `Chat::Tools.step` with a workspace titles a connection tool "Api request · Faylee (Northflank)" (`Chat::Tools.title_for`), the tool's own name and the connection's `display_name`, never the slug made into words, which reads like the provider's name. The dashboard's steps, a run's story and its Slack progress, and the label a run's step is kept under all read it that way. Firefight's own tools and the capabilities keep their names.
- **A step is told apart by what its tool was given.** `Chat::Tools.headline_for` takes an argument named for what is being looked for (`query`, `name`, `identifier`, `title`), and otherwise the first argument the tool's own schema requires, so four reads of four forms show as "Get form declare", "Get form update" and so on rather than four identical rows. A tool with nothing required has no headline rather than a guessed one, and `incident` is the headline of last resort, since it is where a step happens rather than what tells it apart, so it names a step only when nothing else does (`Chat::Tools::LAST_RESORT_HEADLINE`): "Assign incident role incident_lead", but "Resolve incident INC-001". The dashboard keys each row by the step's own key, never by its words.
- **Some results are cards.** A step carries a `card` (`Chat::Tools.card_for`), a reference to what to draw and never the data, on the live step event and the saved step alike, and only once the step is done. The page draws it after the answer (`AgentCard` picks the component by `AGENT_CARD_KINDS`) and reads the rows from its own props, so a card tells the truth after the person acts on it. In a Slack thread `Conversation::Delivery` posts it under the answer through `post_integration_card`. The first kind is a category of integrations, from `list_integrations`.
- **Setting up happens in the chat, connecting does not.** The chat prompt walks someone who asks to set up Firefight through it one step at a time, most useful missing piece first, and changes a setting only once they agree. Integrations are only ever shown as a card: the prompt says never to ask for, accept or repeat a key, token or password. The start page offers "Set up Firefight" to whoever may change the workspace.
- **A connection tool is offered the same way in a chat and over MCP.** `Integration::Tool#offered_schema` is the provider's schema plus `environment`, listed as an enum when the connection is wired per environment (`Integration#environment_choices`), and both `Chat::Tools::Connection` and `Mcp::ConnectionToolFactory` hand it out. The named environment resolves once, on the model (`Integration#environment_entry_for`), and becomes the gateway scope the grant is checked against, so a per environment connection is reachable from a chat and an unknown name is refused with the same words everywhere. The refusal names what the connection has (`Integration#environments_named`: its environment slugs, that it has one environment so the argument is left out, or both when it also has a default), and the argument's description lists the same slugs (`Integration::Tool#environment_description`) rather than an example such as production, which a model would then send to a connection that lacks it.
- **Common tasks load a skill.** A skill is a short recipe at `config/skills/<source>/<domain>/<name>.md`: front matter with its `name`, `when` it is used and the `tools` it needs, then numbered steps. The source is whose tools it drives (`firefight` for Firefight's own, a provider's skills later sit beside it) and the domain is the tool group it belongs to (`incident_response`, `follow_ups`, `workspace_setup`), which a test holds for Firefight's own. `use_skill` lists them grouped the same way. `Chat::Skill` reads them. A chat starts with `use_skill` beside `open_tools`, and its description lists every skill a line each, so the prompt does not grow with each recipe. Loading one returns its steps and makes the tools it names callable for whoever is acting (through the same `offer` as opening a group), and names any they may not use. The first set covers Firefight's own tasks: declaring, updating, ending incidents, roles, inviting, runbooks and setup. A declare loads the skill and reads the form, where it used to open two groups first and sometimes read the workspace config for choices the form already lists. `test/models/chat/skill_test.rb` fails when a skill names a tool that does not exist or is not offered to Halon, or sets a name in code that is not one of its tools, their parameters, a form or a form field, so a skill cannot drift from the tools. A run holds `use_skill` too, so the provider's skills and their guides, such as Northflank's API reference, are read while investigating rather than guessed at or searched for on the web. Loading one in a run goes through the same catalog as opening a group, so it offers only the tools the investigator's principal was granted, and names the ones an investigation does not use since it only reads. A rehearsal loads skills and reads guides as well, and that changes nothing. Loading writes no memory and no ledger row, only the found tool names on the rehearsal's own chat. Firefight's own skills are listed in a run too, and their tools that change things are named as not used while investigating. The run's prompt says to load the skill that fits before reading a connected provider. Opening a group also lists the skills whose tools it just opened and tells the agent to load the one that fits first, because the skill list in `use_skill`'s description alone was skipped (a Cloudflare question went straight to `execute`). A group too large to open whole (PlanetScale's) lists them too, since loading a skill also loads the tools it names. Tools opened for an earlier question stay open, so a later one never passes through `open_tools`. `Chat::Tools::SkillReminder` covers that: the first call in a chat to a tool a skill covers adds the skills for it to the result, unless the chat still holds one of them loaded (a `use_skill` call among `Chat#calls_in_play`, so a compacted chat is reminded again) or already named it, through an earlier call to one of its tools or an `open_tools` result that listed it. It applies to a run as well as a chat.
- **A provider's skills name its tools as the provider does.** `config/skills/<provider>/<category>/` holds them, `search_logs` rather than `northflank_search_logs`, since the name the agent sees depends on the connection. `Chat::Tools::Entry` carries each tool's `source` (a provider's key, or `firefight`) and `handle` (the provider's own name), so loading a skill finds the tools across every connection to that provider and rewrites the names in its steps to the ones the agent calls, joined with or when two connections both have one. A provider's skills are listed only once the workspace has connected it (`Chat::Skill.available_to`). A tool the skill needs that is not switched on is named, so the agent says why a step cannot run. A test holds a native pack's skills to the tools and parameters the pack declares. A connected server's tools can change without a release, so `SkillCheckJob` runs daily and records a skill naming a tool no connection to its provider still offers as a `Chat::SkillProblem`, which the operator console lists under Needs attention until the check finds it fixed. A provider nobody has connected is not checked. The first provider skills are Northflank's, one per kind of incident (triage, errors, crashes and restarts, resources, what changed, builds, jobs, databases), and `northflank_workflows` for workflows and release flows and what starts them (Git push, pull request, a GitHub release, a label, a check suite, cron and webhook triggers, the query parameters a webhook takes, reading triggers and runs, adding a webhook trigger with `add_workflow_webhook`, rolling back), written from Northflank's own documentation, PlanetScale's (triage, slow queries, failing queries, connections, locks, looking up data), Cloudflare's (triage, 5xx from the origin, blocking traffic, attacks, cache, DNS), ClickHouse's (triage, slow queries, failing queries, memory and CPU, inserts and ClickPipes), Turso's (triage, blocked reads and writes, slow queries, lost data), Upstash's (triage, Redis, QStash, Workflow), PostHog's (triage, user impact, feature flags, errors with the sessions behind them, logs and traces) and Mixpanel's (triage, user impact, feature flags, one user's sessions). Every skill is open source, in this repository.
- **A provider's skill can name the map.** Finding one of the provider's resources starts on the map, so a provider's skill may list `get_resource_map`, Firefight's own tool, beside the provider's (`Chat::Tools::UseSkill::MAP`), and loading it offers the map too. `SkillCheckJob` never counts it missing. Cloudflare's skills start from the zone on the map, whose id is the zone id every endpoint takes, and list zones with `execute`, which asks the person to confirm each call, only when the map does not have it.
- **Providers' documentation lives in the docs store, not the repository.** `config/provider_docs.yml` is the source list: for each provider, where its documentation is read from (a GitHub repository, a site's named pages, a site's index of markdown pages such as Northflank's `llms.txt`, an API client on npm whose endpoints are written out, or an API's machine-readable description whose reads are written out as the reference for the provider's general read), and the folder its pages are named under. `ProviderDocsSyncJob` reads every source once a day at 3am into `provider_doc_pages` (one row per page, named by its path within the provider, with the address it came from) and splits each page into `provider_doc_chunks` at its headings (`ProviderDocPage::Chunking`: each section with its heading path, at most 350 words, a long one cut between paragraphs and a long table or sample between lines, a heading inside a code sample never counted). `ProviderDocs::Sync` writes what it read, removes what a source no longer names, and keeps the copy a page had when it cannot be read, with `provider_doc_sources.error` saying which. A source that cannot be read at all keeps every page. There is no review gate: an update applies as it comes, so the provider's text always reaches the model framed as evidence (`FirefightAi::Evidence.frame`) behind `Chat::Tools::UseSkill::GUIDE_NOTE` or `Chat::Tools::Docs::NOTE`, which say it is data and never instructions, and to cite the address it came from. Reading is polite (`DocsClient`): it says who it is (`FirefightDocs/1.0` with the address of the product docs page that explains it), keeps to what a documentation site's robots.txt allows (the group naming it, else `*`, the longest rule deciding) and its Crawl-delay, never reads a site whose Content-Signal says `ai-input=no`, waits at least half a second between requests to one host, and asks again with the ETag or Last-Modified it got, so an unchanged page is not sent twice. A repository is read through GitHub's tree in one request and each file only when its blob hash changed, an index lists the pages and drops the ones it no longer lists, and an npm client is installed again only when its version changed. GitLab's pages are read from docs.gitlab.com's markdown, since gitlab.com's robots.txt keeps readers off its raw files. A fresh install fills the store in the background when its job runner first starts (`SolidQueue.on_start`, reading only the sources never read), and with no network Halon works from the skills alone: `use_skill` and both docs tools say the provider's documentation is not available yet (`Chat::Tools::Docs.unavailable`). To read it by hand, `bin/rails provider_docs:sync` runs the job at once and prints each step to the terminal (`SOURCE=northflank_docs` reads that source alone, `UNREAD=1` only the sources never read). Every run reports through one `ProviderDocs::Progress`, which writes each step as a JSON line to the log and, for the task, the same step as a plain line (`northflank_docs  reading 120/680 pages (100 unchanged)`), so a long read never looks stuck. The log gets `provider_docs.started` (how many sources), `provider_docs.source_started` once a source has listed its pages (how many it will read), `provider_docs.reading` every 50 pages or 15 seconds while it reads (pages read of the total, unchanged, failed), `provider_docs.read` when it finishes (pages, chunks written, unchanged, pages failed, seconds) or `provider_docs.unread` when it could not be read, `provider_docs.embedding` when embedding starts and every 1,000 chunks or 15 seconds after, `provider_docs.embedded` or `provider_docs.unembedded`, `provider_docs.missing_guides`, and a closing `provider_docs.finished` with the run's totals. An npm client is listed only once it is installed and written out, so it reports its pages at that point. Embeddings: `ProviderDocs::Embedding` sends only chunks whose words changed since they were embedded (`embedded_digest` against `content_digest`), or that an older model embedded, in batches of 100 on the deployment's embedding model through `FirefightAi.embed_documents`, recorded in the ledger with no workspace (`Inference::FEATURE_PROVIDER_DOCS`, the one feature allowed none, paid as `AiPayer.deployment_only`). Re-chunking a page keeps the vector of every chunk whose words are unchanged. Without an embedding model the store is searched by words alone. Read in full on 8 October 2026 the store held 1,789 pages in 27,375 chunks, about 39 million characters or 10 million tokens, so a first embedding costs about 20 cents on text-embedding-3-small ($0.02 per million tokens) and a day's refresh only what changed, usually a few hundred chunks. A page over 3 MB is left out rather than counted as a failure (`DocsClient::TooLarge`). An API description is read up to 80 MB, since only its reads are written out as pages.
- **Searching the docs costs a few hundred words, not pages.** A chat and a run hold `search_docs` and `read_doc` (`Chat::Tools::Docs`) beside `use_skill`. Docs are never put in the prompt. `search_docs` finds sections in the documentation of the workspace's connected providers, or of the provider it names, connected or not, through `ProviderDocChunk::Search`: Postgres full text over each chunk's heading path and words (a generated `tsvector` with the `simple` configuration, so a dotted name such as `release.sha`, an endpoint path or an error message is one word on both sides, every word of the query an alternative, ranked by `ts_rank_cd`), and nearest by meaning over the chunks' embeddings, the query's vector from `SearchEmbeddingService#query_vector` and asked for only when some chunk of those providers has one from the current model, merged by reciprocal rank fusion (k 60). It answers the best five as snippets of about 320 characters starting at the first word asked about, each with its heading path, provider, page and address. `read_doc` reads one section and those under it, or a page whole when it is under 24,000 characters, and lists a long page's sections instead. Both read Firefight's own store with no call to the web, so neither goes through the gateway, and both read as thinking on the page (`Chat::Tools.kind`).
- **A skill's guides are pages in the store.** A skill lists the pages that back it under `references`, by their path within the provider, loading the skill names them, and `use_skill` with `reference` returns one framed as evidence, prefixed with `GUIDE_NOTE` and opening with `Source: <title>, <address>` (`ProviderDocPage#attribution`), so Halon cites where it came from. `Chat::Skill.reference` and `references_of` read the store, and only a page the store holds can be named. A listed page the store no longer holds says the provider may have moved it and points at `search_docs` (`Chat::Tools::Docs.gone`). `test/models/provider_doc_source/definition_test.rb` holds the source list to the kinds and keys the refresh reads, every source to a provider and https, and two sources of one provider to their own folders (`Definition#roots`), and `test/models/chat/skill_test.rb` fails when a skill lists a page no source of its provider can hold (`Definition#could_hold?`). Which pages a folder or an index holds is only known once read, so after each refresh the job logs `provider_docs.missing_guides` for a listed page the store does not hold (`Chat::Skill.missing_references`). PlanetScale's guides come from its repository (MIT, `planetscale/database-skills`: Postgres, MySQL and Vitess). - **Long running work has its own workers, and nothing else picks it up.** An investigation runs for minutes and a person is waiting on a chat answer, so `investigations` and `conversations` are separate queues with a worker each in `config/queue.yml`. - **One turn at a time per conversation.** `ConversationReplyJob` limits concurrency on the conversation id, so a second question asked while the agent works waits, then is answered after the first. Without it the two turns corrupt the chat. - **A reply the platform refuses is logged, never retried.** The answer is already in the chat and the turn is paid for, so a retry would buy a second model call for nothing.

It ends with `report_state`: one or two sentences and a change, `unchanged`, `changed`, `already_done`, `gone` or `unknown` (`Chat::CurrentState`). The card and the Slack message show the sentence under "Now:" and the change in plain words above it (`Chat::CurrentState::WORDS`), such as "This looks done already." When Halon is not available, errors or never reports, the call still becomes ready with `unknown`, which says nobody checked. Run is blocked with why while it checks.
- **Run runs it once.** Run (dashboard `agent_chats#run_held_call`, Slack `Identifiers::HELD_CALL_RUN`) is allowed to the asker and to anyone in the chat who may make the same call themselves (`Chat::HeldCall#run_blocked_reason`). It claims the call `ready` to `running` in one guarded update and queues `ConversationReplyJob` with the held call, so the run happens at the start of a turn and never lands inside another. `Conversation::HeldCalls.execute!` runs exactly the approved provider call (the approval's action key, params and scope) or Firefight tool, as the asker, through the gateway with `approval_id`, so the allow row carries the approval and the approval is consumed once. The ledger row decides ran or failed (`Chat::HeldCall#ran!`). Halon then reads what it answered as a nudge and says how it went, unless the chat is paused on a confirmation, when it is told at its next turn instead (`untold_note`). Dismiss moves it to `dismissed` and the approval to `dismissed`.
- **An approval of a chat call lasts an hour.** `Ability::Approval::RUN_WINDOW` from the moment it was approved, shown on the card as "Expires in 52 minutes". `ApprovedCallExpiryJob` moves an unused one to `expired` with one guarded update and the call says so, offering Ask again, which asks the gateway for a fresh approval of the same call (`AbilityGateway.request_approval!`, which never runs anything) and keeps it as a new held call. - **A statement that changes rows is counted, copied and checked.** A tool with `EFFECT_DATA_WRITE` (docs/integrations.md, What a change does beyond its risk: PlanetScale's `execute_write_query`, Supabase's `execute_sql`, Neon's `run_sql` and `run_sql_transaction`) always goes through its `approval_resolver`, which `Chat::DataRepairs.settle`s each call before anyone is asked. `Integrations::DataWrites::Statement` reads the statement, skipping strings, quoted names, comments and dollar quotes: a read runs as it would have (asked about unless the tool was allowed for the chat), a schema change is asked about as before, and one UPDATE, DELETE or INSERT on one table is counted. Anything Firefight cannot count first (a join, `UPDATE ... FROM`, `DELETE ... USING`, an upsert, a WITH that writes, TRUNCATE, several statements, `EXPLAIN ANALYZE` of a write) is refused before anyone is asked, with how to write it instead. A row write needs `check`, one SELECT returning the rows still wrong, which `Chat::DataRepairs::CHECK` adds to the tool's schema. Every read runs through the provider's own read tool with the write's other arguments, as the asker, through the gateway with `holdable: false`, so it is in Activity and never waits for an approval rule. The pause keeps a `Chat::DataRepair`: the rows it touches (`count_sql`, a count read back as `halon_rows`), five of them (redacted, encrypted), and the check's count. A write over `Integrations::DataWrites::COPY_LIMIT` rows (1,000) is refused, asking for batches. A transaction (Neon's `run_sql_transaction`) is settled statement by statement, each counted as the rows stand before it runs, sampled and copied through `run_sql`, with the one check for the whole transaction and the limit over all its rows. One statement that cannot be counted refuses the whole transaction, named by its place. The confirmation shows the rows before what the tool was given, and never offers Allow for the rest of this chat, since each write touches other rows (`Confirmation#allowable?` is false for it, as for a call asked after something outside was read). A write a scheduled plan's person approved ahead (`Conversation::Turn#approved_ahead?`) runs without asking and is still counted, copied and checked. Right before it runs, `Chat::Safeguards` counts again, refusing a count that moved since the person saw it, and copies the rows a page of 100 at a time (`ORDER BY 1`), encrypted on the row. After it ran the check is counted again and Halon reads both counts and until when the copy is kept. The chat shows a card per write that ran, with Download the rows as they were (`agent_chats#data_repair_copy`, authorized through the gateway on the read tool as the viewer, `SOURCE_WEB`). `DataRepairCopyCleanupJob` drops a copy after `Chat::DataRepair::COPY_KEPT_FOR` (30 days), keeping the counts. The PostgreSQL pack only reads, so it has no write tool to guard.
- **A change customers feel is undone unless someone keeps it.** A call through a tool with `EFFECT_MITIGATION`, a call a general tool's provider tells is one (`Integrations::Mitigations.call?`, such as a Cloudflare rule created through `execute`), or a `scale` to fewer instances than the map last read the resource running (`details["instances"]`), is a `Chat::Mitigation`, proposed at the pause (`Chat::Safeguards.prepare!`) or as it runs when nobody was asked. Its time starts when it ran, and Halon is told when it ends. `MitigationUndoJob` then writes its undo with `FirefightAi::UndoWriter` from what the call returned, each step checked by `Investigation::RemediationStep.checked`, and one only a person can do leaves it by hand with what to do. `MitigationSweepJob`, every minute, reminds `REMIND_BEFORE` (15 minutes) ahead once (`claim_reminder!`) and queues `MitigationExpiryJob` for each one due, which claims it `active` to `undoing` with one guarded update and runs each undo step through the same connection tool as the asker, so grants, approval rules (a held undo waits in the chat for Run) and the ledger apply. One left `undoing` past `CLAIM_LAPSES` is ended saying it may or may not be undone. Every line is said where the chat is (its thread, the asker's direct messages, the dashboard card) with Keep it, One more hour and Undo now while it is in place (`Identifiers::MITIGATION_*`, `agent_chats#keep_mitigation`, `#extend_mitigation`, `#undo_mitigation`, each with a toast), allowed to the asker and, in a channel or thread chat, anyone there (`Chat::Mitigation#*_blocked_reason`). Halon hears once, at its next turn, how each ended. A change made while a plan step runs is kept with that step (`plan_step_id`), so it and the plan are undone once between them. One Firefight already undid is left out of the plan's Undo (`Chat::Mitigation.undone_steps`), and pressing Undo on the plan hands one still in place to the plan's undo (`STATUS_WITH_PLAN`), so its time stops. A step of a plan's undo is never itself counted down.
- **Stopping what someone else started asks them first.** A call through a tool with `EFFECT_STOPS` always goes through its resolver, which reads who started it from the pack (`NativePack#owner_of`, recorded in Activity as a read the call made) before anyone is asked, and keeps a `Chat::OwnerAsk` when it is someone else. A member matched by the address the provider gave, who has Slack, is named on the confirmation and asked once the person confirms: the call's approval becomes `Chat::APPROVAL_OWNER_ASKED`, which RubyLLM reads as undecided, so the turn stays paused, and `OwnerAskJob` sends them Agree and Say no in their direct messages (`Identifiers::OWNER_AGREE`, `OWNER_DECLINE`), answered by them alone. Either answer approves the call and resumes the turn as the person who confirmed, and a no is the call's refusal when it runs, so nothing is stopped and Halon is told who said no. The usual approval rules apply after that. An owner Firefight cannot match or reach is named on the confirmation for the person to check with, and nobody is asked. A call whose owner is the asker, or whose provider does not say, runs as it would have, allowed for the chat included. A scheduled plan's approved stop still pauses for the owner, who is asked at once since nobody is there to confirm. Moving on while the owner is asked withdraws it (`Chat::UnfinishedCalls::NOT_AGREED`) and their message says it is no longer needed.
- **A saved runbook is run by name.** A runbook becomes one Halon can run once a step names a `tool` (as Halon calls it: a capability, one of Firefight's tools or a connection tool, never a provider in app code) with `arguments`, or it holds a `watch` (`Runbook::Procedure`). Its `inputs` are asked each run and fill `{{key}}` placeholders in the arguments and the watch (`Runbook.filled`), and `aliases` are the other names it is found by (`Runbook.named`, slug, name or alias, any case). A step without a tool is a plain incident step exactly as before, so attaching, claiming and the Slack checklist are unchanged. The Runbooks settings dialog edits all of it without JSON: a step picks its tool from every tool Halon can be asked to run, grouped as a person finds it (Firefight's groups, Anything on the resource map, each connection), and gets a field per parameter of that tool's schema (`Chat::Tools::Choices`, sent as optional props when the dialog opens, so the page loads none of it otherwise). A shape a form cannot hold, and anything saved the fields do not show, is listed and kept as it was, and a field nobody touched sends back exactly what was saved, so a runbook Halon saved round trips unchanged. The watch is picked the same way: what to check (`Choices.reads`), the resource from the map, what counts as done, and an optional time limit. A watch is checked when the runbook saves, from any surface, by the rule a watch starts with: every step names what to check and the resource, and a step that does not follow a run says what counts as done (`Chat::Watch::Step.undecided?`). An item's name (`label`) is optional. The dialog's placeholder says what it is named after when left empty, and `Runbook#filled_watch` names it so when the runbook runs: the read it makes as the picker shows it (`Chat::Watch::Step.default_label`, Run history, Status), or the read tool it names as the chat titles it (`Chat::Tools.title_for`, which `Conversation::Tools::RunRunbook` hands to `filled_watch`). Every watch error is a whole sentence (the `format` for a runbook's `watch` in config/locales/en.yml), the same on the dashboard, the API and MCP, and names each item to fix by its name ("Watch 'Deploy finished': needs ...") or by its number when it has none ("Watch 2: ..."), as the dialog numbers them, never as a step. The dialog lists each sentence under the watch and asks for its pickers' choices again, since the page comes back without them. Its keys are `Chat::Watch::SPEC_KEYS`, generated for the page as `WATCH_SPEC_KEYS`. Halon saves one with `upsert_runbook` (skill `saving_runbooks`), finds one with `search_runbooks`, which marks it `runnable`, and runs it with `run_runbook` (`Conversation::Tools::RunRunbook`, skill `running_runbooks`), a chat tool handed to every conversation beside `start_investigation`. It always waits for the person (unless they allowed it for the rest of the chat), and the confirmation lists each step's tool with its arguments filled in and what it watches after (`Chat::Tools.planned`), read from the runbook rather than Halon's words. A request that would be refused anyway (unknown runbook, nothing to run, an input with no value and no default) is let through by its `approval_resolver`, so Halon hears why and asks for the input. Once confirmed, each step runs in order through the very tool `Chat::Tools.catalog` offers the asker, so grants, packs, approval rules, self approval of a confirmed call and the ledger apply as if Halon had called it. The turn is wrapped in `RunRunbook::Recording`, which hears a refusal or a failure through `Chat::Tools.mark_failed` (`call_failed!`) and a held call through `hold!`, since a step has no tool call of its own to mark. The first step refused, held for approval or failed stops the run and the answer names it and why. When every step went through, the filled watch is started with `Conversation::Watches.start`. Over MCP there is no direct tool: an outside agent asks `ask_halon` ("release Firefight"), the turn pauses on the confirmation and `ask_halon` answers waiting, as for any change it confirms.
- **Halon can watch something and report back later.** Asked to be told when a run, a build or a deploy finishes, Halon calls `start_watch` (`Conversation::Tools::StartWatch`, skill `watching`) rather than saying it cannot follow in the background, and the prompt has it offer one when someone starts something that takes a while. A watch (`Chat::Watch`, on the chat that asked, with `Chat::Watch::Step` per thing it follows and `Chat::Watch::Update` per line it said) only ever reads, through the capabilities that read, as the person who asked with exactly their permissions: `Conversation::Watches::Reader` routes each read with `Capabilities.resolve` among the tools that principal may call and runs it through `AbilityGateway.authorize!` with `SOURCE_WATCH` ("Halon watch" in Activity). A read an approval rule covers is never made, since nobody is there to approve one each minute. Nothing in the app names a provider: a step names a capability and a resource on the map, or a read tool by the name Halon calls it.
- **Halon writes its own watches.** A watch is "keep checking X until Y": each step is any read Halon holds and `goal` is the condition in plain words, such as every instance of web runs the new version, or the error rate stays under 1% for ten minutes. A watch is named for what it waits on (`title`, such as Deploy finished), shown as Watch "Deploy finished" (`Chat::Watch::Shown.name`) on the card, each line it says, Slack and MCP. A step whose provider gave the page of its run keeps it (`run_url`, from the run, or from a reading through the judge's `link`, kept only when the reading holds that address word for word, never one the model made up), and the card's step and each Slack line offer Open the run.
- **A step is a run or a reading.** A `run_history` step follows one run in the resource's history (docs/integrations.md, Capabilities): the run the person named by id or number, or the first of its name (release, build, deploy) that started from ten minutes before the watch began. Its state comes from the provider's run, in Firefight's words, so done and failed are decided without a model. Any other read (`resource_status`, `search_logs` and so on) ends on `done_when` or `failed_when`, text its answer holds, and when no text decides it the condition (`goal`) is judged by `FirefightAi::WatchJudge`, one call on the workspace's quick model: on each reading that changed (times stripped), and on one that stayed the same every `Step::JUDGE_STEADY_EVERY` (five minutes, `judged_at`), told how long it has stayed so (`steady_since`), so a condition that names a time is decided without a model call every minute. A step that cannot be routed for the asker, or whose provider keeps no run history (the registry's `history_note`, `Capabilities.history_notes`), is named in what Halon says, and with nothing left to follow nothing starts. A step may instead name any read tool Halon holds, by the name it calls it (`tool`) with its `arguments`, such as Northflank's `api_request` with GET for one workflow run, which run history does not hold since it only reads builds. `Conversation::Watches::Agent` is the read only agent run that reads it: `Chat::Tools.catalog` for the asker with `reads_only?` true, so a tool that changes things is never offered and one with a read guard only reads through it, every call through the gateway as the asker with `SOURCE_WATCH`, and a call an approval rule covers is refused rather than asked. The step is kept with capability `read_tool` and `tool_name`, read once when the watch starts so a refusal or a failing read is said at once, and ends on `done_when`, `failed_when` or `goal` like any reading. A reading no text decides is judged by `WatchJudge#reading` into not started, running, done, failed or nothing (`Schemas::WatchReading`, nothing when the reading cannot show the thing at all, such as an empty list or another run), against the condition or, without one, against the label and the words it was given, with each job or step the reading lists and the page it links. Running moves a waiting step to running with its start time (`started!`), so the card stops saying it waits to start. Seen in a real chat, a GitHub run with two jobs passed and a Northflank run that existed were both shown as waiting to start. Seen in a real chat, a watch on a Northflank workflow run said waiting to start for ten minutes while the run went, since run history only listed builds.
- **A job or step that fails inside a run is said at once.** `History::Run` carries `parts` (`History::Part`: a job or step with its status, times, where it failed and `log`, the provider's own read tool and arguments that read its log) when the run was read by its id: run history takes `run`, which the code hosts pass on (GitHub's `ci_runs` reads the run and its jobs, GitLab's the pipeline and its jobs, a job allowed to fail left out, Bitbucket's the pipeline and its steps). Once a step follows a run it reads it by id, and the first time it matched a run whose list carried no parts it reads it again by id when the adapter passes `run` on. The first part that failed is claimed once (`Step#part_failed!`, guarded on `failed_part_told_at`), its log read through `Reader#read_log` (the named tool on the connection that answered, only when it is switched on, reads only and no approval rule covers it, ledgered under `SOURCE_WATCH`), explained by `WatchJudge#why_failed`, and said while the run goes on as a `KIND_PART_FAILED` line (a red cross on the page, :x: in Slack): "GitHub Release workflow: trigger-northflank failed at Notify Northflank of the release, 4 seconds in." with why and the job's page. The card shows the step as running with that part failed, and a run that then fails is explained from the same part's log. Seen in a real chat, a release's webhook job failed 4 seconds in and nothing was said for 7 minutes.
- **Progress is said as it happens.** Each job or step a check sees start or pass, inside a run (`History::Part`) or in a reading's parts, is said once (`Step#progress!`, kept in `parts_told`), and everything a check saw move is one `KIND_PROGRESS` line, a step per line: "Release run: tag passed, trigger-northflank running." A failed part is said on its own with why, and a step that ended in the check says its end instead. The card shows a running step's passed parts ("Running. Passed so far: tag, trigger-northflank.").
- **The exact run, by its id.** A history step given a run (`run`) reads it by id from its first check, and the list of recent runs only while no run by that id is there yet. `start_watch` and the watching skill tell Halon to give the run's id whenever it started the run or can identify it, to read one run by its address for a read tool step (`workflows/release/runs/<id>`), never a list, and to prefer `run_history` for a code host's CI since it brings the jobs.
- **A watch keeps the goal.** `start_watch` takes `purpose`, why the person wants it in their words (`Chat::Watch#purpose`). Every milestone that a part failed or a step succeeded, and every end but a person's stop, is followed by `WatchJudge#standing`: one sentence on where this leaves the goal and the next step offered as a question, never claiming the goal met or a fix that what happened does not show, or "This was for:" and the purpose when Halon is not available. The card shows it under the headline, `list_watches` and `untold_note` carry it, so Halon can say later why it ran something. Seen in a real chat, a manual deploy was reported as a success when the goal was the webhook path, and Halon later could not say why it had run it.
- **A read that finds nothing to follow is repaired, never followed blind.** Two things hand a step back: a history step still waiting `HAND_BACK_AFTER` (three minutes) after it could have started, from when the watch began, the step before it ended or its last repair (`Step#waiting_since`), and a reading step whose first judged reading is nothing. The step moves to `STATUS_REPAIRING` once (`Step#repair_asked!`, a guarded update from waiting or running, keeping why in `repair_reason`), is not read meanwhile and keeps the watch going, is said as a `KIND_HANDED_BACK` line, a warning mark ("I could not find a run of Web deploy in its history after 4 minutes. I am finding a better way to follow Web deploy."), and `ConversationReplyJob` is queued with the step. `Conversation::Runner` with `handed_back:` adds `Conversation::Watches.hand_back_note` as a nudge (what the read found, the purpose, to find a read that shows it, try it once and call `repair_watch`, changing nothing) and runs a turn whose `Conversation::Turn` is `reads_only?`, so nothing can change without the person. `repair_watch` (`Conversation::Tools::RepairWatch`, `Conversation::Watches.repair!`) plans the new read exactly as `start_watch` would, keeping the step's done and failed words unless given new ones, and swaps it into the same step with one guarded update from an open status (`Step#repaired!`, counting `repairs`, starting the step over), and the watch says what changed as a `KIND_REPAIRED` line ("Changed how I follow Web deploy: I now read northflank_api_request GET workflows/release/runs/46 instead of Run history of web. Run history only lists builds, not workflow runs."). Halon also repairs a step a fresh reading shows is following the wrong thing, and passes `give_up` when no read can show it. A step is repaired at most `MAX_REPAIRS` (two) times, then a step handed back again is no longer followed, and one Halon has not repaired within `REPAIR_WITHIN` (fifteen minutes, such as while the chat waits on the person) is let go too, each said. Either way the note is told once (`Chat::Watch::Step#hand_back_noted!`, a guarded claim on `hand_back_noted_at`). A chat paused on the person's confirmation is left alone, since running a turn would withdraw their question, and their next turn tells Halon the whole note (`Chat::Watch::Step.hand_back_untold`). A watch's first check is queued as it starts, so something that fails the moment it starts is said within seconds. Seen in a real chat, a watch on a Northflank release picked a read that showed nothing and followed nothing until its time ran out.
- **Fresh beats remembered.** A call Halon makes in its chat with the very read a watch in that chat makes (the same read tool with the same arguments, or the same capability on the same resource, `Conversation::Watches.reads_the_same?`) is handed to the watch when the call returns (`Conversation::Runner#hand_reading_to_watches`, `Conversation::Watches.observe!`): a reading step judges Halon's reading itself, with no read of its own, and a history step reads its run again at once. Seen in a real chat, a watch's remembered state contradicted a fresh read and Halon repeated the watch.
- **A ceiling on reads.** Each watch keeps to `reads_per_hour` (`Chat::Watch.ceiling_for`: `READS_PER_STEP`, 120 an hour, for each step unless Halon passes `reads_per_hour` from a provider's documented limit, between `FEWEST_READS` and `MOST_READS`). The card shows it: "Reads at most 120 times an hour. 14 reads so far." (`Chat::Watch::Shown.reads`), and `start_watch` tells Halon to say it.
- **The time limit is learned.** The person's own limit wins, at most 24 hours. Otherwise it is twice the usual duration the history read at the start showed (the middle of the newest finished successes, `History.usual_seconds`, summed over the steps that have one), rounded up to whole five minutes and between ten minutes and a day, then twice what Halon remembers (`expected_minutes`, which the skill fills from memory only when history has nothing), then an hour. Halon says it: "This usually takes about 18 minutes, I will watch for up to 40." (`Conversation::Watches.limit_sentence`).
- **Checked about every minute, at once on a live update.** `WatchSweepJob` runs every minute and queues `WatchCheckJob` for each active watch not checked within the minute and not held back by its ceiling. `Integrations::MapEvents.receive!` wakes the watches with a step reading through the connection an event arrived for (`Conversation::Watches.wake!`), so a provider's webhook or change log reaches a watch through the same interface as the map, never a hook of its own. A check claims the watch with one guarded update (`Chat::Watch#claim_check!`, lapsing after `CLAIM_LAPSES` for a worker that died), each milestone is claimed the same way on its step (`started!`, `finished!`, `slow_told!`) and the end on the watch (`finish!` from active), so two workers or a restart never say anything twice, and all state is in the database.
- **What it says, and where.** A step the person asked to hear start says "Web deploy started.", one that succeeded says how long it took, one running past one and a half times its usual (and two minutes over) says it is taking longer than usual once, and the end is one line: done, failed with the reason, the time limit with the last known state, or stopped. A failed run is looked into read only before it is said: the end of its build log for a repository or a build, its app log then its build log otherwise, through `search_logs`, explained in a sentence or two by `WatchJudge#why_failed`, or the log's error lines when Halon is not available. Each line is kept as a `Chat::Watch::Update`, drawn on the dashboard chat where it was said (`AgentChatsController::PROP_WATCH_UPDATES`, live through `LiveDelivery::EVENT_WATCH`), posted in the chat's Slack thread when it has one, and sent to the asker's Slack direct messages, unless the thread already is a direct one with them (`direct_conversation?`), with Open the chat for a dashboard chat. While the watch goes each message also offers Stop (`Identifiers::WATCH_STOP`, `Interactions::StopWatchHandler`), which asks first as the card does and is the same stop as asking Halon in words: whoever may stop it may press it (`Chat::Watch#stop_blocked_reason`), anyone else is told who can in an ephemeral, and the end is said where the watch reports. `Conversation::Watches.stop_pressed!` then redraws the pressed message without Stop (`update_watch_update`), also when the watch had already ended, which the presser is told. A line said once the watch is over carries no Stop. It never joins the model's own chat, which a turn may be writing. Halon hears each line once, at its next turn (`Conversation::Watches.untold_note`), and reads `list_watches` when asked how one is going.
- **Stopping and limits.** The card (`PROP_WATCHES`) shows the watch's name, its limit and why, its ceiling on reads, each step with Open the run where there is one, and Stop, which asks first and ends with a toast (`agent_chats#stop_watch`). Halon stops one with `stop_watch`, a person in Slack with Stop on any line it said, an outside agent with the MCP tool of that name, and gives one more time with `extend_watch`, at most a day from when it started (`Chat::Watch#extend_to!`, from active only). The asker may always stop it. In a channel or thread chat anyone there may too, since the asker may be away while it runs on. A personal dashboard chat is its owner's alone (`Chat::Watch#stop_blocked_reason`). A workspace keeps at most `Chat::Watch::ACTIVE_LIMIT` going, and a watch follows at most `MAX_STEPS` steps.

## Files a person attaches

A person can hand Halon an image, a PDF or a text file with a message, from the dashboard chat or in Slack, and Halon reads it as evidence. `Chat::Attachment` (table `chat_attachments`) is one file, `Chat::Attachment::Intake` works out what Halon will read of it as it arrives, and `Chat::Attachment::Reading` is what the model is handed for it.

The rules:

- **What is read.** Images (PNG, JPEG, GIF, WebP) go to the model as images, through RubyLLM's attachments. A PDF goes as a document when the chat's model takes PDFs, and as its text otherwise (`pdf-reader`, first `PDF_PAGES` pages, each marked `[Page n]`). Text files (logs, CSV, JSON, YAML, Markdown, code, anything Marcel calls text and whose bytes read as text) go as text. Magic bytes decide an image or a PDF, so a renamed file is read for what it is, and a binary file named like text is refused. Anything else is refused with `Chat::Attachment::ACCEPTED`, the sentence saying what is accepted.
- **Limits are constants.** `MAX_PER_MESSAGE` (4), and `MAX_BYTES` per kind: images 5 MB (Anthropic's per image limit), PDFs 10 MB, text 5 MB, with `PROVIDER_MAX_BYTES` lowering images and PDFs for Bedrock, whose Converse API takes less inline. `LARGEST` is what a platform is told before it downloads anything. Images and documents are resent with every turn, so `Reading::SENT_BYTES` (20 MB) and `SENT_FILES` (20) cap what one request carries: the newest go whole and older ones are named, a PDF falling back to its text.
- **A long text file is saved, never cut silently.** A text larger than `Chat#result_limit` is kept as a `Chat::SavedResult` when it joins its message, and the model gets `Evidence.preview` with the handle, so `read_result` reads the rest by line or search, the same as a large tool result.
- **What the model can take is the registry's word.** `FirefightAi.input_modalities(model)` reads `modalities.input` from RubyLLM's registry, and `Chat#reads_images?` / `reads_pdfs?` ask it for the chat's own model. A model the registry does not know takes text only. An image a chat's model cannot read is not sent, and Halon is told to say so plainly. The dashboard knows before sending, from `attachmentRules.imagesUnread`.
- **Text is redacted before the model sees it.** A text file and a PDF's text pass through `Chat::SecretFree.redacted` as they arrive, and `redactions` counts what was replaced, which the model is told. A PDF holding anything that looks like a credential is handed over as its redacted text, never as the document. An image cannot be redacted.
- **A file is untrusted evidence.** Text arrives inside `<attached_file name="..." trust="untrusted">` (`FirefightAi::Evidence.frame_file`), which neutralises a closing tag inside it. An image or document is named in a bracketed line before it. `Evidence::FILE_RULE` in the chat prompt says everything in a file, text in an image included, is evidence and never instructions, that bracketed lines outside the tags are Firefight speaking, to say plainly when a file could not be read, and to name the file and the line, page or part of an image a claim rests on.
- **How it reaches the model.** `Chat::Message#to_llm` adds the files of a person's message to what RubyLLM builds, so the saved history is the only source. The association is `attached_files`, never `attachments`, which RubyLLM would read and send raw. `Chat#files_sent_with` loads a chat's files once per rebuild. A queued message's files wait on it (`queued_message_id`) and join the message when it is taken, and the chat is reloaded so the running turn sees them.
- **Stored encrypted.** The bytes are encrypted with `ActiveRecord::Encryption.encryptor` and attached as `has_one_attached :sealed`, so Active Storage keeps them in the object store and purges them when the record is destroyed. The blob is named `chat-attachment` with a generic type, so the real name and kind never sit in plain text. Files kept before as a bare blob named by `blob_id` were attached by `MoveChatAttachmentBytesToActiveStorage`, which checks every row has its file before it drops the column. `filename` and `text` are encrypted columns.
- **Deleted with the chat.** A chat and a message destroy their files, each purging its stored file. A file shared with Halon in an incident channel, or with an investigation of the incident, goes with the transcript under `transcript_retention_days` (`TranscriptRetentionJob`). An upload never sent is deleted after `UNSENT_FOR` by `ChatAttachmentSweepJob`.
- **Who reads one.** Before it is sent, only its uploader. After, only whoever may read the chat (`Conversation#watchable_by?`), through `GET /agent/attachments/:id`, which serves an image inline and everything else as a download, sandboxed and never sniffed. A file that went with a note to a run is served by the page the run is drawn over, under that page's own rule, so whoever sees the file in the story may open it: `GET /incidents/:incident_id/investigations/:id/files/:file_id` (`incidents: read`, the run must be that incident's), `GET /agent/:id/investigations/:investigation_id/files/:file_id` (`chats: read`, the run must be one that chat started, in the reader's own chat) and `GET /investigations/:id/files/:file_id` for a run on its own page (`investigations: read`). Each controller hands `InvestigationDetailSerializer` the `file_path` it serves, and the file is found only among that run's notes (`Investigation#note_file`). All of them serve through `ServesChatAttachment`, so the bytes are decrypted and sent with the same headers. Nothing goes to MCP or the ledger: the ledger records the prompt's name and version, never a message.
- **A run reads files too.** `InvestigationService#start(files:)` queues what was shared with the ask on the run's chat as notes (`Investigation#hand_over_files!`, `MAX_PER_MESSAGE` to a note, worded `Investigation::Noting::FILES_WITH_THE_ASK`), which the run takes before its first model call, so they reach the model through `Chat::Message#to_llm` like a chat's, within the same limits, redaction and framing, and the investigator's prompt carries `Evidence::FILE_RULE`. A run started from a chat (`Conversation::Tools::StartInvestigation`) is handed copies of every file sent in that chat (`Chat#copies_of_sent_files`, `Chat::Attachment#copy!`, its own encrypted bytes), so each chat lets go of its own. A file that joins a message keeps its note (`queued_message_id`), and the run's story names a note's files (`InvestigationNoteFileSerializer`) without serving them, since only a chat serves a file.
- **The dashboard.** `POST /agent/attachments` uploads one file as it is added (`AgentChatAttachmentsController`, `investigations: create` like asking) and answers with the chip or the refusal sentence. `create` and `ask` take `attachment_ids`, which must be the asker's own unsent uploads (`Chat::Attachment.to_send!`). A message may be files alone, and the chat is then named after them.
- **Slack.** A mention's `files` go through `Conversation::SharedFiles`, which asks the adapter (`fetch_shared_files`, `files:read`, `files.info` for a file Slack only names) and takes each like an upload. A file too large, refused, past the count, or that Slack would not hand over is kept as `KIND_UNREAD` with why, so Halon says so rather than ignoring it. A mention with files and no words is a question. Every mention the agent takes reads them the same way: a question, a note added to a live run (files alone are a note) and a mention that starts an investigation, which carries the files' ids on its command (`Command::SHARED_FILE_IDS`) for `Commands::StartInvestigation` to hand on (`Chat::Attachment.handed_on`).

## Performance

Halon, Performance (`/halon/performance`, `HalonPerformanceController`, page `halon/performance`) shows every member how Halon has done for the workspace over the last 7, 30 or 90 days (30 by default), read by `Investigation::Performance` from what the team recorded, never estimated. It needs `investigations: read` and the agent to be available, like Chat and Memory. Rehearsals are left out.

- **Runs and answers.** Runs started in the window, how many ended, and how many reached an answer (an ended run with a finding that has a summary, since a run writes its finding before it ends), with the median time from start to finish of an answered run. Weeks are UTC weeks starting on Monday, and the page says the first and last are partial.
- **Right.** Confirmed answers out of rated ones, never blended with partly right, shown with how many answers were rated at all, so a small sample is plain. Partly right, wrong and not rated sit beside it, and a weekly stacked chart counts each.
- **Fixes.** Each fix of an answered run counts once: undone when its undo was applied or partly applied, otherwise applied, cancelled, or only proposed.
- **Where Halon was wrong.** The latest ten answers from runs in the window that were marked wrong, with the cause they gave and the in-use lessons sourced from their incident.
- **Over MCP.** `get_halon_performance` returns the same numbers for a window (and says why when the agent is not available, as the page does), and Halon holds it under Incidents and what happened before, so it can answer how it has been doing.

## Where a run is read

A run is read where it was asked for, never on a screen of its own. There is no list of runs.

- **Over its incident.** `?investigation=<id>` on the incident page draws the run in a side panel (`IncidentsController::PROP_OPEN_INVESTIGATION`, filled by `InvestigationDetailSerializer` only when the address asks and only for that incident's own runs). The incident's timeline says when a run started and how it ended (`investigation.started`, `investigation.answered`, `investigation.stopped`, written by `Investigation::Timeline` from `Investigation::Delivery`, so a rehearsal writes none), and each entry opens the panel. These events are internal only, not webhooks.
- **Its own address.** `/investigations/:id` is what Slack's Open in Firefight button links to. A run on an incident is sent to the incident with the panel open. A run with nothing to be drawn over is shown on its own.
- **In the chat that asked.** A run a chat starts keeps `conversation_id` and the `tool_call_id` of the call that started it. The step's card (`Chat::Tools::CARD_INVESTIGATION`) finds its run by that id in the chat's `investigations` prop and draws it like the chat's own lookups, with its steps as they happen (`InvestigationCardSerializer#steps`) and then its answer and charts. The card opens the run over the chat (`AgentChatsController::PROP_OPEN_INVESTIGATION`) and offers Declare incident. `Investigation::Delivery` broadcasts `Conversation::LiveDelivery::EVENT_INVESTIGATION` on every step and whenever the run starts or ends, so the card moves with the run, and the chat's next turn is told how its runs went. The answer is never written into the chat's model history, where two assistant messages in a row would break some providers.
- **In the channel that asked.** A question from a channel keeps its `channel_id` and is announced by its own words. Where Firefight cannot post, a private channel it is not in, it is answered to whoever asked, directly.
- **The story.** `components/investigations/` is the same view wherever it is drawn: what was asked, the answer with each claim linked to the steps it rests on, the theories, and every step in order with theories placed where they were written down and settled after the last step they rest on. No cost is shown to people.
- **People see only the plain stop sentences.** `Investigation::PLAIN_STOP_REASONS` are the sentences a run stops with and `Investigation#stopped_because` returns one of them or `GAVE_UP`, so a technical cause in `error_summary` never reaches the page, the thread or an outside agent over MCP.
- **A run can be started from its incident's page.** Investigate sits beside the channel link (`POST /incidents/:incident_id/investigations`, `investigations: create`, recorded as `Investigation::TRIGGER_DASHBOARD`) and opens the run over the incident with a toast. It is there only when Halon is available and the person may start a run (`IncidentsController#investigation_start`), and it stays, disabled with why, while `Incident#investigation_start_blocked_reason` refuses: the incident ended, it has no channel yet, or a run is already working on it, which the tooltip opens.
- **A run can be stopped from the dashboard**, from its story or its chat card (`POST /investigations/:id/stop`), the same `Investigation#request_cancel!` as Slack's stop. Whoever may start a run may stop one, and `Investigation#stop_blocked_reason` refuses a finished run.
- **A running run keeps itself current** by reloading only the prop that holds it every few seconds, and stops once it has an answer or has stopped.

## Steering a run

A responder can add to a run while it works, and the run reads it at its next step rather than being stopped and started again.

- **A note waits on the run's chat.** `Investigation#add_note!` queues a `Chat::QueuedMessage` with its sender and any files, and `Investigation::Runner` hands the loop `take_notes`, which adds each waiting note as "Name added: ..." (or "Name added files." for files alone) between a tool's result and the next model call. Each note read is reported as a step ("Read what Name added"), so Slack and the chat show the run took it.
- **Two ways in.** A mention in a live run's Slack thread (`Investigation.live_in_thread`) is a note, through `Investigation#add_note_from`, which asks the gateway since no controller did, and opens no chat. Once the run has finished, a mention there is a chat as before. On the dashboard the run's story takes one while the run is live (`POST /investigations/:id/notes`).
- **Whoever may start a run may add to one**, `investigations.create`, which every member holds until an admin narrows it. `Investigation#note_blocked_reason` refuses a finished run and an empty note, and a note with files is never empty.
- **The story shows each note where the run read it**, and one still waiting last (`InvestigationDetailSerializer#notes`). A note's image opens full size over the story and any other file downloads, as a chat's do. A file Halon did not read has no address, since it was never kept.

## Plans

A request that takes more than one step gets a plan Halon keeps on the chat and updates as it goes, so the goal is carried from turn to turn rather than remembered. People see it as a checklist in the dashboard chat and in Slack.

| Piece | Holds |
|---|---|
| `Chat::Plan` / `Chat::Plan::Step` | one plan of a chat and its steps, each a read, a change or a check |
| `Conversation::Tools::MakePlan`, `UpdatePlan`, `FinishPlan`, `CancelPlan` | the tools Halon keeps it with, never shown as steps (`Chat::Tools.internal_names`) |
| `Conversation::Plans` | what a person presses on one, the scheduled run, what Halon reads each turn, and telling the page and the platform |
| `FirefightAi::PlanRule` | the prompt rules, in the engine |
| `ChatPlanSweepJob` / `ChatPlanRunJob` / `ChatPlanMessageJob` | the minute sweep for plans whose time came, one scheduled run, one Slack post or redraw at a time per plan |
| `Workspace::FreezeWindows` | the one place a plan reads freeze windows through. The handbook supplies them, and until it does there are none |

The rules:

- **A plan is a chat's record.** It belongs to `Chat`, as every agent run's data does, and the engine never names it. `FirefightAi::PlanRule` only says how to use the tools.
- **Every change carries its undo before it runs.** `Chat::Plan::Step.checked` refuses a change with no `undo`, and `update_plan` takes an exact one from what the change returned, as `Investigation::UndoWriter` uses what each step returned. Undo makes the undo plan at once from those notes, newest first, then a check (`Chat::Plan#undo_steps`), and hands it to Halon. Each change in it still asks as any change does. A stopped plan being undone is cancelled, so Halon never carries it on beside its undo.
- **A plan that changed something ends with a check.** `check_steps!` refuses a plan with no check after its last change, `move_step!` refuses a check marked done with no reading through a connection since the last change ended (`Conversation::Plans.read_since?`: the capability reads, `run_key_query`, `new_log_patterns` and every read only connection tool), unless its verdict is `could_not_check`, and `finish!` refuses until that check is done and a next step is given. The prompt points the check at `resource_status` and `run_key_query`, which compares error rate and p95 latency with the resource's normal.
- **A partial failure stops the plan.** A failed change, or a check whose verdict is `not_held`, moves it to stopped with why (`Chat::Plan#stop!`). The tool hands Halon done, failed with why and not started (`Chat::Plan#standing`) to report, and the card offers Retry and Undo. A failed read does not stop it. Marking a step running again takes a stopped plan up again, which is what Retry hands Halon.
- **A plan can wait for a time.** `make_plan` takes `run_at` as a local time and `time_zone`, which defaults to the asker's own as their chat platform has it (`Conversation::Plans.time_zone_of`). The turn's context names today's date only, so the prompt stays the same all day for the provider's cache. A plan with a time is proposed until a person presses Schedule on its card, and every change in it names its tool, so the person approves exactly those. A time in the past, more than 30 days ahead or inside a freeze is refused when it is made and again when it is approved.
- **At its time a scheduled plan reads first.** `ChatPlanSweepJob` queues each plan whose time came every minute, and `Conversation::Plans.run_scheduled!` stops it before anything runs when a freeze covers now, the agent is unavailable, or `Chat::StateCheck` (as whoever approved it, on a chat owned by the plan) reports anything but unchanged. The plan stays scheduled while Halon reads, so a lost worker leaves it to the next sweep, and the claim (`Chat::Plan#claim_run!`) hands it to Halon once. That turn acts as the approver, and `Conversation::Turn#confirms?` skips asking only for the tools its approved changes named. Approval rules still hold every one.
- **Who may press.** Schedule, Cancel, Retry and Undo are open to whoever a dashboard chat belongs to, and to anyone in the channel for a chat in one (`Chat::Plan#may_act?`), the same rule as stopping a watch, under `investigations.create`. Each has a `*_blocked_reason`, the serializer ships the offers with theirs, the controller says each with a toast, and Slack answers a press someone may not make privately.
- **Where it shows.** The dashboard chat draws each plan where it last moved (`moved_at`), reloaded on the `plan` stream event. A chat in a Slack thread posts it there when it is made and redraws it as it moves. A dashboard chat's plan goes to its person's direct messages once it has a time they approved, since it runs when they may not be looking. An outside agent's chat shows nothing and cannot schedule, since nobody there can approve.
- **Halon reads its plans every turn.** `Conversation::Plans.for_halon` lists each plan still in play with every step, its undo and what it said, so it carries each to its goal. `FirefightAi::PlanRule` replaced `TeammateRule::PLAN_RULE` and `GOAL_RULE`: the plan is said back in two lines and started, and each change asks when it runs, so the plan itself never waits for a yes.

## On call: when an alert starts Halon

The on-call module is the same agent pointed at the hours nobody is watching: a trigger (an alert), a skill and facts that say how to work, and permissions decided ahead. Halon, On-call (`HalonOnCallController`, `/halon/on-call`, admins only) holds the three workspace settings (`Workspace::OnCall`, also in `Workspace::Settings::KEYS` so `update_workspace_settings` over MCP takes them) and the unattended rules (`UnattendedRulesController`).

- **One start per alert group.** `alert_investigations_enabled` (off by default). `IncidentCreationWorkflow#start_alert_investigation` calls `Investigation::AlertStart.start!` once the incident's channel exists, checkpointed so a retried step never starts a second run. Only an incident with `Incident::SOURCE_ALERT` starts one, and grouping already makes one incident of every alert with the same signature in its window, so a group starts Halon once. The run is `Investigation::TRIGGER_ALERT`, acts as the investigator like every run, and is announced as started by the alert.
- **A spending ceiling per storm.** Separate groups firing together share `alert_storm_ceiling_cents` (default $20) over the last hour (`Workspace::OnCall::STORM_WINDOW`). `storm_committed_cents` counts a finished alert run at what it spent and a live one at its whole cap, under a per workspace advisory lock (`lock_storm_budget!`), so two alerts at once never count on the same money. A run gets what is left, up to the workspace budget (`InvestigationService#start(max_spend_cents:)`, whose insert sits in a savepoint for this). Under `MIN_ALERT_RUN_CENTS` left, nothing starts and the channel says so with an Investigate button (`post_alert_run_held`). A workspace Halon cannot run in is told why with no button. An incident whose run is already live is left alone.
- **The run is told it is unattended.** `Investigation::IncidentSeed` adds `on_call` (`Seeding::KEY_ON_CALL`) to an alert run's facts: that nobody asked, the enabled unattended rules that can act (each with the fix step to write), and whether it pages. The prompt sends a run carrying `on_call` to the `on_call_alert` skill first (`config/skills/firefight/alerts/`): read everything at once, tie it to a change, page with evidence, propose a fix someone can apply in one press. `paging_on_call` (incident_response) is the chat's version for "page whoever is on call".
- **Paging.** `on_call_paging_enabled` (off by default). `conclude` takes `page` (an email and the steps that showed it), refused unless the run may page and the email is a member (`Investigation#page_to`, `PageRefused`), stored as `Finding#page_member`. `OnCallFollowUpJob`, enqueued once an alert run answers, calls `Investigation::Paging.page!`, which claims `paged_at` once and escalates the incident to that member through `IncidentLifecycleService#escalate`, with Halon's summary and the fix, as the investigator. It is ledgered with `AbilityGateway.record_unattended!` (`Investigation#record_paging!`). Escalating is how a person is paged here, so the reminder and the acknowledgement are the existing ones.
- **Unattended rules.** `Ability::UnattendedRule`: a capability (rollback or restart), a resource on the map, a metric of `Integrations::Capabilities::METRIC_NAMES`, a threshold and minutes. It grants nothing. After an alert run answers, `Investigation::Unattended.consider!` claims the look once (`RemediationPlan#claim_unattended_check!`) and acts only when every step that runs itself is covered by an enabled rule (`covers?`: the step was written as that capability on that resource, which `RemediationStep#resource` records), no rule has a `blocked_reason` (the investigator lacks a grant of the routed tool, or the resource left the map), and a fresh reading of each rule's metric through the gateway as the investigator (`UnattendedRule::Reading`, never held for approval) averages above its threshold, the highest series deciding. Then `apply_unattended!` claims the plan from proposed in one guarded update with `applied_from: investigation`, records the rule on each step (`applied_under_rule`) and what Halon read (`unattended_reading`), and the fix runs through `FixRunner` as the investigator (`RemediationPlan#acting_principal`). A person who applied it first wins.
- **Safeguards still apply, by leaving the change to a person.** A chat wraps a stop, a mitigation and a data write in `Chat::Safeguards` (an owner ask, an expiry the person chose, a count and copy first), each answered by someone. Nobody is there to answer at 3am, so a fix whose step is any of these is left for a person (`Investigation::Unattended#safeguarded`, read per call through `Integrations::Mitigations.call?`), and a rule whose routed tool stops something or is a mitigation says so as its `blocked_reason`. A fix's undo stays the fix's own (Undo fix, `UndoWriter`), separate from a chat plan's step undo, so nothing is undone twice.
- **Approval rules still apply, answered ahead.** A step's call carries `unattended_rule_id`. When an approval rule would hold it, `AbilityGateway.approved_ahead` asks `UnattendedRule#admits?` (enabled, the investigator, a running step applied under that rule with exactly these arguments and scope) and writes an approved `Ability::Approval` with `approved_under_rule`, consumed by the call, so the Approvals page names the rule as the decider (`decider_name`). Anything else still waits.
- **The incident is told.** Acting is said in the channel (`post_unattended_note`, `Slack::Messages::OnCall`): the fix, each rule and who set it, what Halon read, each step's undo and Undo fix. Not acting under a rule that covered the fix is said under the run's answer with why, and that the fix waits. A fix no rule touches says nothing. The run page shows the reading under the fix, and the activity log names the rule on each call (`RemediationStep#triggered_by_label`).
- **Settings screen.** Delete is refused once Halon acted under a rule (`delete_blocked_reason`, the row says how many times from `with_usage_counts`), and a rule is turned off instead. Each create, edit, on, off and delete is a toast.

## What a run says in Slack

`Investigation::Delivery` is everything a run says while it works, and the adapter decides how it looks. A run posts "Investigating INC-001" in the incident channel, opens an agent session on that message's thread, reports each tool as a step, and closes with the answer or with why it stopped.

The rules:

- **Firefight is declared a Slack agent.** `features.agent_view` and the `assistant:write` scope in `config/slack_manifests/template.yml`. The declaration cannot be reversed, the scope forces a reinstall, and the features need a paid Slack plan.
- **The session status is ours to clear.** Slack holds its spinner for an hour unless the session is set back to `active`, so `finish_agent_answer` always clears it, including when the run failed.
- **A workspace without the agent features still gets the answer.** `start_agent_answer` returns no answer id when Slack refuses, and the finish posts one ordinary threaded message instead. A step against no answer id is dropped.
- **Steps come from the engine**, which reports a tool as the agent reaches for it and again when it answers. A finished step says how it went in a word under its title (the `task_update`'s `output`): a failure is Slack's `error` status with Failed, a not found completes with Not found, and an answer adds nothing. A chat in a thread (`Conversation::Delivery`) reports its steps the same way. `conclude` and `record_hypothesis` are not shown, since they are how the agent writes rather than what it looked at.
- **An answer is rated right, partly right or wrong**, three buttons (`Identifiers::RATE_INVESTIGATION_*`) since Slack's own feedback element holds only two, so whoever presses one is told what they said, privately where they pressed it (`answer_privately`, through the press's `response_url`). Answers posted before keep Slack's thumbs (`Identifiers::INVESTIGATION_FEEDBACK`), which still count and say nothing. The run's answer on the dashboard rates the same way (`POST /investigations/:id/rating`, `investigations: read` like Slack), showing the reader's own rating (`InvestigationFindingSerializer#my_verdict`). Every vote is kept as an `Investigation::Verdict`, one per person, changeable. The finding carries an outcome only while the room agrees, so a split leaves it blank, and `Finding#tally` is the count the Learner and the Performance page read.
- **Stop is Slack's own button.** It needs the `agent_session_stopped` subscription or Slack shows a dead spinner. The event sets `cancel_requested`, the loop sees it between turns, and `Chat#cancel` stops a model call already in flight. The run ends as canceled.
- **Blocks are attached when the stream stops**, never mid stream, since Slack may otherwise break them up.
- **The last post is recorded once the platform took it.** `answer_posted_at` is set after the answer, or why the run stopped, reaches the thread, and never when that post raised. A finished run with a thread and no `answer_posted_at` is one whose last post was lost, which the operator console lists.

## Saved chat

`Chat` and `Chat::Message` hold the agent's conversation with the model: messages, thinking text and signatures, raw reasoning and content blocks, tool calls and results, approval decisions. `owner` is polymorphic and unique, so an investigation has one chat and a conversation will too, and the owner decides who may read it. RubyLLM's `acts_as_chat` and `acts_as_message` write each move as it happens, and `chat.to_llm` rebuilds the `RubyLLM::Chat`. The engine only sees that `RubyLLM::Chat`.

The rules:

- **Resume from the chat.** Rebuilding from `Investigation::Step` loses the reasoning between tool calls and the thinking blocks providers need back unchanged.
- **Call `Chat#discard_interrupted_reply!` before resuming.** A worker killed mid tool call leaves an empty assistant row that RubyLLM reads as the final answer. Only the job holding the run may call it, since a live worker mid tool call has the same row. The interrupted tool runs again, so tools must be safe to repeat.
- **Tool call ids are unique per message**, not globally as RubyLLM installs them, since a model that numbers its calls (`call_0`) repeats ids across workspaces.
- **Everything the model read or said is encrypted**: `content`, `thinking_text`, `thinking_signature`, `citations`, `server_tool_calls`, `raw_content`, `raw_reasoning`. Tool call `arguments` in `ruby_llm_tool_calls` are not, like ledger `params`.
- **A chat belongs to its owner's workspace.**
- **Settings are not saved.** Tools, thinking and temperature live on the in-memory chat, so every job applies them after loading.
- **Always set the model**, from `FirefightAi.model_for`. Without one RubyLLM uses its `default_model`. The first chat ever saved copies RubyLLM's 1,669 models into `ruby_llm_models`, and `test/fixtures/ruby_llm_models.yml` keeps one row so tests skip that.
- **Model lookups never read `ruby_llm_models`.** RubyLLM's Rails support would point `RubyLLM.models` at it, a copy no gem upgrade refreshes, so the engine clears `model_registry_store` on `:active_record` load.
- **Spend is not read from here.** `ruby_llm_usages` records tokens and cost per attempt, but spend, permissions and audit stay in `Inference`, the gateway and `Investigation::Step`.
- Only Anthropic's thinking replay has been tested against saved rows, not OpenAI's or Gemini's.
- **Charts a tool returned are kept as `Chat::Chart`**, one row per chart with the tool call id, the run's step number, the title, unit, range, a summary, a link to the provider's live chart, and the series (encrypted, since they are the customer's data). The model never sees them. The dashboard chat draws them under the step that made them (card kind `chart`, the `charts` prop, reloaded when a step event carries the card). A run's side panel draws them under their step. In Slack, `Conversation::Delivery` and `Investigation::Delivery` post them in the thread after the answer through `post_charts`: `Chat::Chart::Image` draws each as a PNG with libvips' own drawing and text (never through an SVG, since `image_processing` blocks libvips' untrusted loaders for uploads), uploaded with the summary and the link as its comment. A workspace that has not granted `files:write` gets the comment as a message. A chart over more than a day marks its axis with dates and names both ends' days, and each series is listed on its own line under the plot, since container names are long. At most `Chat::Chart::POSTED_LIMIT` charts go under one answer, and a note says how many more there were. The production image ships `fonts-dejavu-core`, since the slim base has no fonts for the chart text.

## Postmortem generation state

`Postmortem#status` is the document's editorial status and nothing else. Whether an AI generation is writing the document lives in `generation_state` (`generating`, `failed`, or nil for nobody). Every entry point (the dashboard button, `/ff postmortem`, the Slack home menu, the button on the resolution message, the API and the MCP tool) calls `PostmortemGenerationService#start!(incident, by:)`, which creates the placeholder through `Postmortem.start_generation!` or re-arms a failed one and enqueues the job, and does nothing when a generation is already running, so two requests yield one job. The job runs only while the state is `generating`. A terminal failure marks the row `failed` with the error's reason instead of deleting it, and so does any error the engine did not classify, so the page never polls a placeholder forever. A failed placeholder blocks nothing: `Incident#postmortem_blocked_reason` ignores it, so Try again re-arms it and Start blank turns it into the empty document. `Postmortem.complete_generation!` clears the state when it saves the draft. A finished draft is recorded as `postmortem.generated` with a revision labelled Generated by AI. A blank start (`Postmortem.start_blank!`) is its own event, `postmortem.started`, with a Started blank revision, a timeline line saying the person started the postmortem and its own outbound webhook, and the onboarding checklist counts either. `LabelBlankPostmortemStarts` relabelled blank starts recorded before then, told apart by their empty document, since a generation always writes every section heading.

## Postmortem sections are honest

The model is asked for the sections in `FirefightAi::Schemas::Postmortem`, and every one of them is nullable. Nullable rather than optional because strict structured output (OpenAI refuses a schema whose `required` list does not name every property) wants every key present, so null is how the model says the record has nothing for a section. The prompt says to write only what the incident record supports and to return null rather than infer a cause, an impact or a fix from the title and the duration. A blank incident used to come back as nine confident sections of fiction. Now `Postmortem.complete_generation!` renders every heading in `Postmortem::SECTION_KEYS` regardless, puts `Postmortem::EMPTY_SECTION_PLACEHOLDER` under any the model returned as null, and builds the Timeline section itself from `Postmortem::TimelineSection` (the undismissed incident events, capped like the generator's own timeline input) so that one section is factual on every document. The placeholder is the app's copy, never the model's, so it cannot drift between runs.

**Action items starts with the follow-ups already on the incident.** `Postmortem::FollowUpsSection` lists every active follow-up as recorded, with its issue's link and its status, and the model's own `action_items` follows it. The schema and the prompt tell the model the recorded follow-ups are listed already, so its section holds only further items that follow from causes the record names. Actions stay where they were, as their events on the Timeline and in the model's Actions & Follow-ups input, each with its issue's key and link when it tracks one.

## What the postmortem model reads

`Incident#to_full_context` is the record every incident prompt reads (postmortem generation, section rewrites and `/ff catchup`). Its timeline events come through `IncidentEvent.with_update_history`, so an update (`IncidentEvent::UPDATE_MESSAGE_EVENTS`, updated and canceled) carries `message`, what the responder posted, and `changes`, each changed field's label with its before and after, from the snapshot before it in the incident's whole history. `FirefightAi::IncidentRecord` renders them the same way for every prompt. Each update gets a timeline line naming its changes and pointing at its message, and a `## Status Updates` section after the timeline quotes every message in full, in order.

The channel section says only what is known. With a narrative summary it is the summary. Without one, the prompt says either that Firefight holds no message a person wrote in the channel (its own posts, status updates among them, are never in the transcript) or that the messages could not be summarized, never that nothing was posted. An incident run entirely through posted updates, with nobody typing in the channel, used to reach the model as a row of "updated the incident" lines and the line "No messages were posted in the incident channel".

**The rendered prompt is kept with the draft.** `PostmortemGenerator::Draft#prompt` is the user prompt as sent, and `Postmortem.complete_generation!` stores it as `generation_prompt`, passed through `Chat::SecretFree.redacted` and encrypted, so a thin document can be checked against what the model was told. The system prompt is on the ledger already, as the `PromptVersion` its row names. Only the latest generation is kept. Nothing in the product shows it yet, so it is read from the Rails console.
