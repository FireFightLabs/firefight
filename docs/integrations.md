# Integrations & the Ability Gateway

One system seen from two ends. **Connections mint abilities; the gateway authorizes every use of one.** Enabling a capability on a connection card creates exactly one permissioned action, and from that moment it is grantable, approvable, and ledgered like anything else in the product.

## The chokepoint

Every privileged operation goes through one method:

```ruby
AbilityGateway.authorize!(principal:, action_key:, workspace:, scope: {}, params: {}, context: {}) { execute }
```

API controllers, MCP dispatch, Slack dispatch, and connection tools all route here. **Never check permissions inline** anywhere else; the convergence is the safety property. Each entry point has exactly one gate, at its own dispatcher: `Api::V1::ApiController#authorize!`, `Mcp::ToolDispatcher`, and `AuthorizedDispatch` for `CommandDispatcher`/`InteractionDispatcher`. The gate stays at the entry point rather than moving down into the services, because the approval digest is computed from the caller's params and that is what makes a retry match.

Three verdicts: returns normally, raises `Denied`, or raises `PendingApproval`. Four gates, in order:

1. **Permission** — an explicit grant covers `(action, scope)`, or the principal holds it implicitly
2. **Configuration** — `action.configured_for?(scope)` (tool actions only)
3. **Approval policy** — matched contextually, may park the call
4. **Ledger, then execute** — write-ahead row, finalized once

Block form wraps execution. Handle form returns an `Authorization` the caller finalizes later (the API layer does this from an `around_action`).

## Actions

| Kind | Scope | Origin |
|---|---|---|
| `system` | global rows (`workspace_id` nil) | seeded from `Ability::Action::RESOURCES × ACTIONS` |
| `tool` | workspace-scoped | minted by enabling a capability on a connection |

- Key format is `<integration_slug>.<tool_name>`, **per instance**. Two Datadog connections mint `datadog.logs_query` and `datadog_eu.logs_query`, so a grant is never ambiguous and the ledger always says which one ran.
- **The slug is immutable after creation.** Renaming would orphan every grant, approval policy, and ledger row referencing the old key.
- `risk_level` (read/write/destructive) drives approval matching and the ledger. `reversible` marks what a human should always confirm.

## Who holds what without a grant

| Principal | Implicit authority |
|---|---|
| Admin or owner membership | every catalogued action, tool actions included |
| Member membership | system reads outside `ADMIN_ONLY_RESOURCES`, plus `incidents.create`, `incidents.update`, `chats.update` and `chats.delete`. `map.read` is every environment until a grant narrows it |
| Personal token / OAuth connection | exactly what that human holds |
| Service key | nothing, explicit grants only |
| `Agent` | nothing, explicit grants only |

An `Agent` row is created under **Gateway → Agents**, which mints its first token in the same step, since an agent without a credential can do nothing and making that a second step is a step everyone forgets. It arrives with zero grants: it can authenticate and nothing else until someone grants it something on the Permissions screen, where it appears alongside members and service keys (`Ability::Principal.all`). Its tokens are managed on the Agents screen rather than on **Developer → API Keys**, which filters agent keys out (`agent_id: nil`) so an agent's lifecycle lives in one place. Disabling an agent leaves the row listed with a way back on, because a vanished row still holds its slug and its grants.

Enabling a capability **is** the admin's deliberate decision, so it takes effect without a second grant step. The rule that must not bend: **machines never inherit a human's reach.** A service key or agent reaches an external system only through a grant someone created for it.

**Incident participation is member-level authority**, because responding to an incident is what a member is for, and it has to read the same on every surface — a responder closing an incident from Slack, from the API with a personal token, and through MCP is one person doing one thing. `WorkspaceMembership::PARTICIPATION` is the whole list. It also holds `chats.update` and `chats.delete`, since a person's chats with the agent are theirs to rename, pin, archive and delete. Asking the agent in a chat is `investigations.create`, not a chat permission, because it spends money. It holds `memory.create` and `memory.update` too, so any responder can teach Halon a fact or confirm, correct and reject what it learned, from the Memory page, the lesson buttons in Slack or a chat. Configuring the workspace stays admin territory. This is deliberately *implicit* rather than a grant every workspace would have to hand out: making it revocable would mean deny-grants, and a permission system with a deny list stops being readable.

`Ability::Action::ADMIN_ONLY_RESOURCES` (integrations, api_keys, permissions, workspace) are the controls that decide access itself. Their actions exist as system rows so the gateway and the ledger treat them like everything else, but `Ability::Grant`, `Ability::RoleAction` and the API key matrix refuse them, `grantable_actions` hides them, and a member is refused even the read. Only admin access reaches them, on every surface.

Principals are workspace members, customer created `Agent`s, service `ApiKey`s, and `SystemAgent`s. The last are Firefight's own agents, global rather than owned by a workspace, so `Ability::Resolver.resolve` takes the workspace as a required argument and grants are filed per workspace. A default that read the principal's own workspace would be right for every other kind and silently wrong for these.

**A default a grant narrows.** `map.read` is in `WorkspaceMembership::NARROWABLE_KEYS`: a member holds it in every environment without a grant, until an admin grants it to them, directly or through a permission set. From then the grants decide where, so a grant scoped to Production narrows the member to Production rather than adding to what they had. An expired grant keeps narrowing and reaches nothing, so a lapse never hands the whole map back (`ResolvedGrants#granted_ever?` reads expired grants too, which is why the resolver's cache key is `v2`). Admins keep everything. A member's personal token and OAuth connection resolve to the membership and read the same.

**A read the scope filters rather than refuses** (`Ability::Action::FILTERED_KEYS`, only `map.read`). The page, `get_resource_map` and a capability's lookup cannot name an environment before reading, so a call to one with no environment in its scope is admitted when the principal holds the action in any environment, and the reader filters its rows by `AbilityGateway.reach(principal:, action_key:, workspace:)`: `{}` for every environment, `{ "environment" => ids }` for those, nil for none. A grant without the environment dimension reaches every environment. Every other action keeps the rule above that a scoped grant matches only a call that names one of its environments.

`Principal#implicit_authority` names what a principal holds before any grant, and `implicitly_allowed?` enforces it. **They are two halves of one rule, so change them together** — the permissions page explains the first and the gateway obeys the second, and a drift between them is a lie told to whoever is handing out access.

## Granting

Gateway → Permissions (`AbilityGrantsController`) is the only UI that writes grants, with one exception: choosing an issue tracker under Settings, Workspace grants Firefight issue sync exactly the tools keeping items in step needs, and takes them back when another is chosen (see Keeping items and issues in step). A grant carries an `Ability::Scope`: a hash of dimension to allowed catalog-entry ids, where a **missing dimension means unrestricted and an empty array is invalid**, never a way to say "all". The controller drops ids that are not the workspace's own environments rather than trusting the form, and a second grant of the same action retargets the existing row instead of duplicating it (one grant per principal per action **per workspace** is a DB invariant, because a principal can be global).

**Permission sets** (`Ability::Role`) bundle actions so a set is granted once instead of fifteen actions individually. Keep the set about *what* and the grant about *where*: one "Database read-only" set granted twice, scoped to Development for a contractor and unscoped for staff, beats two sets that drift the moment a provider adds a tool. `Ability::RoleAction#default_scope` pins a scope to one action inside a set and applies only when the grant carries none, so treat it as an override rather than the main mechanism. Editing a set changes what every holder can do immediately, and deleting one revokes it everywhere.

**Do not tie permission sets to `IncidentRole`.** Incident staffing is assigned mid-incident, often by the person taking the role, so letting it confer reach turns self-assignment into unapproved escalation. Temporary reach belongs to time-bound grants instead.

Environment scoping is the axis to reach for when the same connection serves dev and prod: one connection, one `IntegrationEnvironment` per environment, and grants scoped to each. Separate connections are for separate accounts, where the action keys should differ.

## Config ≠ permission

Both are required and they answer different questions. A grant says *this principal may*; a wired `IntegrationEnvironment` says *this connection can*. The gateway asks `action.configured_for?(scope)` and the action delegates to whatever minted it. **Never reach into `Integration::Tool` from the gateway** — new executor kinds must not add branches to the governance layer.

## Adding a provider

1. An entry in `config/integration_providers.yml`: `key`, `name`, `category`, `mark`, `color`, `description`, and `server_url` when the provider hosts an MCP server, or `regions` when it hosts one per region (see Regions and connect fields below).
2. A logo at `public/integrations/<key>.svg`, white-filled on a 24x24 viewBox (Simple Icons is the source for the existing set). `ProviderMark` falls back to the `mark` letters if it is missing, so this never breaks the page, but a test asserts every provider has one.
3. If the category is new, a line under `categories:` in the same file. Taglines are registry data precisely so this stays a config edit. A category no provider is in yet is left out of the gallery and of Halon's tool groups (`IntegrationProvider.categories`), so the list can name categories ahead of their first provider.
4. If its OAuth needs a pre-registered app: `INTEGRATION_<KEY>_CLIENT_ID` and `_CLIENT_SECRET`. Add `_APP_SLUG` when the provider gates access behind installing the app (GitHub). Providers whose authorization server offers dynamic registration (Linear, Jira) need none of these. PagerDuty's servers do not offer it, so `INTEGRATION_PAGERDUTY_CLIENT_ID` and `_CLIENT_SECRET` name an OAuth app made in PagerDuty. Without them, the token form still connects with a user API key sent as `Token token=<key>`.

Before adding one, confirm the endpoint rather than guessing it: `/.well-known/oauth-protected-resource<path>` should return the resource metadata and name an authorization server. If `scopes_supported` is absent there, read the note under OAuth below before assuming scopes can be requested.

**That is the whole job for a provider used through its own tools. No code.** A provider that does more (answers capabilities, goes on the map, links its results, reads baselines, checks its own health) brings code, and all of it plugs in the way the next section says.

## How a provider plugs in

A provider's code lives only in its own files, and the rest of the platform reaches it through a few small contracts. Nothing outside the integrations layer (`app/services/integrations/**`, `app/adapters/integrations/**`) names a provider's code or decides by which provider it is, so a provider's code can be rewritten without touching anything else. ArchSpec holds the constants (`provider_code.can_only_be_used_by :integrations_layer`, and `ProviderClientsStayHome`, which lets a provider's API client be used only by the files named for that provider and by other clients built on it). `Integrations::ProviderTest` holds the names. A provider's key where a provider is compared or chosen outside the layer (`provider == "x"`, `provider: "x"`, `find("x")`, `when "x"`) fails it, while the same word used for something else, such as Slack's `"modal"`, does not. Alert sources keep their own provider list, which is not this one.

**One definition per provider.** `app/services/integrations/providers/<key>.rb` defines `Integrations::Providers::<Key>`, an `Integrations::Provider` naming the provider's parts by class name. It is the only place a provider is registered, so adding one touches no shared list. `Provider.for(key)` finds it, and a provider without a file has no parts. The parts, all optional:

| Part | Contract | Read by |
|---|---|---|
| `pack` | an `Integrations::NativePack` subclass, for `kind: native` or a provider whose registry entry names Firefight's own `app`: its `tool` declarations, one method per tool, and optionally `check_health!`, `map_of` (with its services' settings as `uses` and its stores' addresses as `endpoints`, see Resource map), `map_refresh`, `baselines_of`, the credential methods below and `halon_sentence` | `NativeExecutor`, `Credentials` |
| `adapter` | a module that `extend`s `Capabilities::Adapter`: `SUPPORTS` or `OBSERVES`, `TOOLS` (one tool per capability, or a list with the usual one first), `WRAPPED` and `route(key, resource, given, tool:, settings:)` returning a `Route` whose `tool_name` is the tool that runs, optionally `accepts?(key, given, settings:)`, `reaches?(settings, key)`, `subject(name)` and `phrase(key)` | `Capabilities` |
| `map_reader` | an `Integrations::RemoteReader` answering `map` with a `ResourceMap::Snapshot`, optionally with `EVERY`, and narrowed to one scope when `map` takes `scope:` (Live updates) | `McpExecutor.map_of`, `McpExecutor.map_refresh` |
| `baseline_reader` | a `RemoteReader` answering `baselines(resources, window)` with `ResourceMap::Baseline::Found` readings, or nil when the tool that reads them is off | `McpExecutor.baselines_of` |
| `health_probe` | a `RemoteReader` answering `check!`: raises an `Integrations::Error` (`RemoteReader::Refused`) in the provider's words when the server cannot reach the account behind it, and returns what it learned to keep, or nil | `McpExecutor.check_health!` |
| `source_links` | a class made with `ConnectionSettings` answering `link(tool_name:, arguments:, text:)` with a `Telemetry::Link` or nil | `SourceLinks.attach` |
| `read_guard` | a module answering `guards?(tool_name)`, `schema` and `reading(tool_name, arguments)`, for a tool that both reads and changes | `ReadGuards.for` |
| `issue_tracker` | a `RemoteReader` answering `report(tool_name:, arguments:, result:)` with an `Integrations::Issues::Report` (`change` opened or closed, `key`, `title`, `url`) or nil, and, for a tracker items can be kept in step with, `create`, `update` and `read` plus the class side `CREATE_TOOL`, `SYNC_TOOLS`, `TARGET_FIELDS`, `setup_steps`, `verify` and `event` (see Keeping items and issues in step). A pack registering the tracker's webhook answers `register_issue_webhook`, `remove_issue_webhook` and, where it lapses, `refresh_issue_webhook` | `Issues.report`, `Issues.session`, `Issues.register_webhook` |
| `map_events` | an `Integrations::MapEventSource` subclass in `map_event_sources/<key>.rb`, answering on its class side `verify(raw_body:, headers:, secret:)` and `events(payload, headers:)` with `ResourceMap::Event`s, and optionally `setup_steps`, `register(row, url:)`, `refresh(row, webhook_id)`, `remove(row, webhook_id)`, `poll(row, since:)` and `installation_of(payload, headers:)` (see Live updates) | `MapEvents`, `MapEventsController`, `AppEventsController` |

`redacted_fields` names answer fields that hold a credential (a project's own API key in its details, say). `McpExecutor.call` replaces them wherever they sit in the JSON (`Integrations::Redactions`) before anything reads the answer. `ProviderTest` loads every part a definition names and checks the registry's promises against them: a `kind: native` provider has a pack, a remote provider that says Firefight links its results has a builder, and `MapSweepTest` checks a provider on the map has a reader.

**What a provider's code may know about a connection** is `Integrations::ConnectionSettings`, never the row: its workspace, provider key, name, server address, `region` (an `IntegrationProvider::Region`), `site` (the provider's app, which links open: the region's site, or the registry's top-level `site` for a provider that runs in one place), `field(key)` for what the connect form asked (a list for a field that holds several, the field's `default` when it was left empty), `learned` for what its health probe kept, `credential(key)` for what a native pack stored with its credentials, `store_credential!(key, value)` for a token a pack or its client caches there, `region_sites` for every site of the provider's regions (for a link builder that recognises an address on any of them), and its environment. `credential` is for the pack that stored the value, to call its provider. A credential never reaches the model, a chat, an MCP response or the ledger, so nothing else reads it. Adapters, readers, probes and link builders are all handed one, so how a connection keeps these can change without touching any provider. The row writes them (`IntegrationEnvironment#store_fields!`, `#store_learned!`, and the connection's `settings` for its region and the fields that are part of its address).

**Remote readers** (`Integrations::RemoteReader`) are Firefight's own fixed reads through a remote server, never a script a model wrote. A reader is made with the connection's settings, its switched on tools by name, and a block that runs one. `call(name, arguments, reads)` answers what the tool returned, or nil when the admin has it off, so what it would have read is a gap. `on?(name)` says whether a tool is on and `parameters(name)` gives the parameters the connected tool reports, for a provider whose docs do not publish them. `listing(tool, what, arguments, kinds:)` answers a tool's answer as data, and a tool that is off, a refusal or an answer that is not data becomes a gap naming `kinds` and answers nil. `gap(words, kinds:)` records anything else it could not read. `refused!(tool, result)` raises `Refused` with "<provider> refused <tool>: <its words>." for a health probe. `McpExecutor` records each call: a map reader's and a baseline reader's under `SystemAgent.map_sweep` (`Integration::Tool#swept!`), a probe's under `SystemAgent.health_check` (`#checked!`, source `health_check` in the activity log). Switching a tool on or off checks again a connection whose probe reads through its tools (`ConnectionRefresh.tools_changed`, `Integrations::HealthCheckJob`), so what it learned is there without waiting for the half hourly sweep. A native pack reads with its own API and is never checked through tools.

**Answers.** `Capabilities::Answers` is what adapters share when they write a remote tool's arguments or read its answer: the parameters the connected tool reports (`properties`, `named`, `known!`, which refuses a tool whose arguments Firefight does not know), the time and limit asked (`minutes`, `range`, `limit`), the answer as text or data past the link Firefight added (`text`, `data`, `read`, which hands an answer in an unexpected shape back as it came), the capability shapes with that link kept (`presented`, `linked`), a resource's page (`page`) and times in any epoch unit (`time_of`).

**Credentials.** `Integrations::Credentials` is the one way in for anything outside the layer. Besides the outbound headers (`headers_for`), it asks a provider's pack for what the connect form needs, so the controller and serializer never name a pack: `fields_for`, `refusal(provider_key, values, region:)` and `store!` for `connect_with: api_token` (`NativePack::CredentialField`, where `optional` lets a field be left empty and the pack say what empty means), `certificate_fields`, `url_refusal` and `store_url!` for `connect_with: connection_url`, and `install_url` for an app installed first. A pack's `credential_refusal(values, region:, fields:)` is given the region chosen and what the form asked beside the credentials, so it checks the values against the right API and can check that a project or workspace the fields name exists before anything is saved. A non-secret value a pack needs, such as a project, a workspace or the regions an account runs in, is a connect field read with `settings.field`, never a value stored among the credentials. The credentials form asks the provider's connect fields below its own. A `multiline` credential field (`CredentialField`) is pasted into a text area, such as a service account's JSON key, and like any secret is never shown again.

**Live updates.** The hourly sweep reads everything a connection reaches. A provider that can say something changed also names a `map_events` part, so the map follows the change within about a minute. Firefight never takes an event's contents as the truth. An event (`ResourceMap::Event`: the provider's `id`, `at` when the provider says it happened, an `action` of added, updated, removed, linked or rescope, and a `ResourceMap::Scope` of an account, a kind or one resource) is a nudge to read that scope again, so a duplicate or an event out of order changes nothing the re-read would not, and the change is recorded at the event's time. The sweep stays as the safety net.

- **How events arrive.** Each connection row has its own address, `POST /api/v1/map_events/:token` (`IntegrationEnvironment#map_events_token`, given on connecting and with each hourly sweep by `MapEvents.prepare!`). `Api::V1::MapEventsController` copies the issue webhook's shape: a row that is enabled on an active connection, a 1 MB cap, 600 deliveries a minute per address, and the source's own `verify` against the row's `map_events_secret`, a 401 with a log line when it fails and nothing accepted before a secret is saved. A source that answers `register` is registered with by Firefight itself on connecting (`map_events_webhook_id`, `map_events_secret`, `map_events_expires_at`), extended by `MapEventWebhookRefreshJob` a week before it lapses, and taken back by `MapEvents.connection_removed` when the connection is removed. A failed registration is `map_events_error` and is tried again with each hourly sweep. A source with `setup_steps` and no `register` is set up by hand: the connection's details under Integrations show the address, the steps and a signing secret field (`PATCH /integrations/:id/map_events_secret`, a toast on save). A provider that sends every connection's changes to one address for its app answers `installation_of`. Its deliveries arrive at `POST /api/v1/app_events/:provider`, are verified with `INTEGRATION_<KEY>_WEBHOOK_SECRET` and reach each row made through that installation (`IntegrationEnvironment#installation_id`). Neither controller names a provider. A source that answers `poll(row, since:)` is read every five minutes by `MapEventPollJob`, from `map_events_cursor`, answering `MapEventSource::Polled` (its events and the next cursor, kept only once the events are). One provider may poll and be sent events on the same row. An event read both ways carries the same id.
- **Once, then coalesced.** `MapEvents.receive!` keeps each event in `resource_map_events` (`ResourceMap::ReceivedEvent`), unique per row by the provider's id, so a second delivery is a no-op, and queues `MapEventJob` 30 seconds out for each scope a new event names. The first job to run takes every event waiting on its scope (`ReceivedEvent.claim!`, rows locked with `SKIP LOCKED` and the update naming the waiting state), so a burst is one re-read, and two re-reads of one scope never run at once (`limits_concurrency` on row and scope). `MapEventCleanupJob` drops events after a week.
- **The re-read.** `executor.map_refresh(row, scope)` answers a partial `ResourceMap::Snapshot` for the scope alone. A pack answers `map_refresh(environment_row, scope)` (nil by default), and a remote provider's `map_reader` narrows when its `map` takes `scope:`, through the same switched on tools, recorded under `SystemAgent.map_sweep` with `swept!`. The snapshot's `gone` names the keys the provider answered not found for. A scope the reader cannot narrow, nil, a scope of everything or a rescope queues `MapEventSweepJob`, which sweeps the connection once however many asked, since one asked before the last sweep finds nothing left. A rate limit leaves the events deferred to the next sweep and puts a line in the connection's gaps. Any other provider error marks them failed, for the sweep to catch.
- **Writing it.** `ResourceMap.apply!(row, partial, scope:, at:, read_at:)` upserts only what was read, replaces the declared links out of the resources it read when the read was complete, and takes a resource away only when `gone` names it within the scope asked, never for being absent. It replaces the settings and addresses (`uses`, `endpoints`) of the resources it read when it read them all, and otherwise only adds. Changes are written at `at`, the latest event's time. A resource a sweep wrote after the re-read began keeps what the sweep wrote. What follows any write of the map, search indexing and the matchers (`HostMatcher` and `Matcher`), runs from `MapSweep.written!` for both paths, so anything else that reads the whole map after a change joins there.
- **What a person sees.** `IntegrationEnvironment#live_updates` (`IntegrationEnvironment::LiveUpdates`) answers whether changes reach the map, when the last event came and why they do not, nil for a provider with no source. The map's attention panel and the connection's details read "Live updates: on, last event 3 minutes ago" or "Live updates: off" with the reason. `ProviderTest` checks each source answers the contract its definition promises.

**Its own MCP server instead.** A native provider connected with credentials whose registry entry names a `server_url` offers that server too (`Entry#mcp_alternative?`). The credentials form has "Use an MCP server instead", which opens one-click connect or the token form for the server, with "Back to credentials" to return. The choice travels as `kind` (`Entry#connect_kind`) through `oauth_start` and the callback, and a connection made that way is an MCP connection, asking none of the pack's connect fields. Connections made through the server keep running through it.

**Code hosts in the sandbox.** A code host's pack hands `CodeReading` a `CodeReading::Remote`: the root git fetches from, the user it signs in as, a token read only when a fetch needs one, and for a host other than the default one its `host` (so the same path on two hosts is two repositories in the box, kept under `host:path` and stored under a name with a digest) and git `options` the fetch adds, such as the address a workspace's own host was checked at.

**A host a workspace names itself.** `Integrations::PublicAddress.check!(host, provider_key:)` refuses a private, loopback, link-local or reserved address unless an operator listed it in `INTEGRATION_<KEY>_PRIVATE_HOSTS`, and answers the address to connect to (`Integrations::Http.request(..., ipaddr:)`), so the name cannot point somewhere else between the check and the call. PostgreSQL uses it, and so does any pack that reaches a database, a cluster or a code host at an address the workspace gave.

**Talking to a provider's API.** A native pack's client sends its requests through `Integrations::Http`, which owns what every client shares: `Http.request` reaches the host (an `ipaddr` checked beforehand, a `cert_store`, a block for an answer read as a stream), `Http.json` reads the answer as JSON (a 2xx that is not JSON counts as done and reads as `{}`, and `with_status: true` answers an `Http::Answer` with the status and headers beside the body, for a caller that tells 202 queued from 201 done or pages by a header, while `as: :text` answers the body as text, for an endpoint that answers a log, and `redirect: :download` follows a documented redirect to stored content through `Http.download`, without credentials), and any other answer raises "<provider> answered <code>: <reason>". The client says only how its provider words its reason (`reason:`, the usual fields when it says nothing, OAuth's readable `error_description` before its `error` code) and which sharper error some answers are (`refine:`, such as Northflank's feature that is not enabled). A 429 raises the client's error (or its `rate_limited:` class) marked `Integrations::RateLimited`, so a sweep or a pack rescues every provider's rate limit once, and a rescue of the client's own error still catches it. `Http.segment` escapes one path segment. `Http.download(url, provider_key:, error_class:, limit:)` fetches a file at a signed address a provider handed over (a job's log), only over https and on a public address, without credentials, keeping its last `limit` bytes.

**Secrets in answers.** A credential never reaches the model, a chat, an MCP response or the ledger, so every provider's answer, from a remote server or a native pack, passes through `Integrations::Redactions` in the executor. Anything that looks like a credential, in the text and in any structured value, is replaced by a marker naming it (`Chat::SecretFree.redacted`, the transcript scrubber's patterns plus a connection string with a password), and the fields a provider's definition names in `redacted_fields` are replaced wherever they sit in the JSON. A pack needs no redaction of its own for what it returns.

**Lists read in pages.** `Integrations::Pages.read(max_pages:) { |cursor| [items, next_cursor] }` reads a paged list up to a bound and answers its items and whether it read all of them (`complete`, `incomplete?`). A map reader or pack whose list is cut short at the bound records a gap naming the kinds the list held, so the sweep never takes what it did not read as gone. A list is never read one page and taken as the whole: Northflank's services, databases and jobs (ten pages of 100), Vercel's project domains, Fly's certificates, Convex's audit log and the Grafana and OpenStatus health probes all read through it. A probe has no gaps, so one cut short keeps its first pages and says so in the log.

**A repository a provider names.** `ResourceMap.repository_of(url)` puts the repository at a code host's address on the map as that host's own reader does, found by the registry entry whose `site` has the address's host (GitHub and GitLab have one), and `ResourceMap.repository(provider_key, path)` does the same from a host's key and a path, for a provider that names the host. A hosting pack or a coding agent links what it builds to the repository through these, never by naming a code host, so a host building from GitLab or Bitbucket links as one building from GitHub does. Northflank's builds link this way.

**Progress.** `executor.call(..., progress:)` hands a long running tool a callback, which a pack calls through `NativePack#report(text)`. Nobody need be listening, as in a chat.

**Provider guides.** `bin/sync-skill-references [provider...]` copies the guides `config/skill_references.yml` lists. A repository source names `repository`, `license`, an optional `notice` (copied as NOTICE, for a license that asks for it), `paths` (a folder copies each guide in it, a file copies to the path given), `extensions` (the guides' extensions in folders, `md` unless it says, each kept as `.md`) and `exclude`. A documentation site names `site`, `license` in words, `pages` and `page_url`, a format of `site` and `page` (`%<site>s/%<page>s/index.md` unless it says). A path or page that is gone fails the run.

**Gaps name their kinds.** Whatever a sweep could not read is a `ResourceMap::Gap`: the words a person reads in the map's gaps, and the kinds of resource it would have put on the map. A `Snapshot` takes only gaps, never bare words, and its `unread_kinds` are its gaps' kinds, so a refused list, a switched off tool or a cut short page can never empty the map of what it holds. A gap names no kinds only for what holds no resource back, a setting or an infrastructure file. A remote reader records one with `gap(words, kinds:)`, a native pack builds `ResourceMap::Gap.new(text:, kinds:)` in its `map_of`. Northflank's jobs it could not read are kept this way.

**Finding what was named.** `Integrations::Named.find(list, reference, id:, name:, provider:, describe: nil)` finds the one row a person or Halon named in a list a native pack read: by its id first, then by a name only one row has, whatever the case, and nil for nothing or an empty reference. A name two rows share raises `Named::Ambiguous` (a `NativePack::Error`) with each one's id, "More than one <provider> resource is called web: a, b. Name it by its id.", never picking one. `id:` and `name:` are keys or lambdas, and `describe:` names each shared row its own way.

**A provider's reason in a sentence.** `Integrations::Sentence.join(lead, reason, after: nil)` writes "<lead>: <reason>." with the reason's first line, ended once (never "..") and with its semicolons as commas, and `Sentence.of(reason)` ends a reason as a sentence of its own. `Sentence.all(reason, then)` puts sentences one after another, leaving out an empty one, so a provider that gave no reason never leaves a stray space before Firefight's own words. Every refusal, gap and error that carries a provider's words is written through it. Text a person or Halon reads never joins with a semicolon. A list is `to_sentence`, or one item a line where an item holds commas of its own.

**Resource kinds and status words.** The map's kinds (`ResourceMap::KINDS`) are shared, so a provider uses the one that fits rather than adding its own: `virtual_machine` (an EC2 instance, a Droplet, a Compute Engine or Azure VM), `function` (a Lambda, a Cloud Function), `cluster` (GKE, AKS, ECS), `compute` (what serves a database branch) and `site` for a website a host builds and serves, beside the services, jobs, databases and edge kinds. A kind that is truly new adds its label, icon and tone in `app/frontend/pages/map/lib/`. How a resource stands reads as healthy, busy or failing through `ResourceMap::Resource::STATUS_HEALTH`, Firefight's own small set of status words. A provider maps its own words onto them in its definition (`status_words:`, such as `{ "current" => "ready", "suspended" => "stopped" }`), and `MapSweep` writes every status its connection reports in Firefight's words, so the map never reads unknown for a word that means one Firefight has, and the list never grows a provider's words. `Integrations::ProviderTest` fails for a mapping onto a word Firefight does not have. A resource switched off on purpose is `stopped`, which is busy as paused is, and one that cannot be reached is `unavailable`. An observability adapter watches `Adapter::APP_KINDS` (services, workers and jobs) or, for an uptime check, `Adapter::ENDPOINT_KINDS` (domains, services, workers and sites), rather than its own list. Every error tracker answers errors for `Adapter::ERROR_KINDS`, which adds sites, since a frontend's errors come from the site that serves it.

**Issues opened by Halon.** A provider whose tools open and close issues names an `issue_tracker` in its definition, and `Integrations::Issues.report` asks it what a tool call that succeeded did. Linear's (`IssueTrackers::Linear`) reads `save_issue`'s answer: no `id` asked is a new issue, and an issue whose `statusType` comes back completed or canceled is closed. Jira's (`IssueTrackers::Jira`) reads the key from `createjiraissue`'s answer, and since `transitionjiraissue` does not say where the issue went, reads the issue with `getjiraissue` and calls it closed when its status is in Jira's done category. The page is `https://<site>/browse/<KEY>`, the site from `cloudId` or else from `getaccessibleatlassianresources`. A tracker's reads go through the connection's switched on tools only, authorized through the gateway as whoever made the call and ledgered like any call of theirs, so a tool that is off means the change is not seen. `Chat::Tools::TrackedIssues` acts on the report after every connection call in a chat or a run. An opened issue is kept on the incident the chat or run is about (`Conversation#incident`, `Investigation#incident`) as an action or a follow-up, holding the issue's title, key and link (`IncidentAction#external_key`, `#external_url`), once per link. The kind comes from the work. A tool in a tracker's `OPENS` is offered one more argument there, `keep_on_incident_as` (action for work during the live incident, follow-up for work after it), which is never sent to the provider. Left out, it is an action while the incident takes actions and a follow-up once it is over, and an action asked for on an incident that is over is kept as a follow-up, with the agent told why. A closed issue completes every open action or follow-up in the workspace that holds its link, from whichever chat closed it. Both writes are `incidents.update` through the gateway as the run's principal, and the agent is told what was recorded so it does not add it again. A chat about no incident records nothing on opening, since nothing says which incident the issue is for.

**Keeping items and issues in step.** Settings, Workspace chooses one connection to a tracker (`Workspace::IssueSync`, by its slug), when a new item gets an issue there (never, only when someone asks, always for follow-ups, always for actions and follow-ups, never by default) and where new issues go, as the tracker's `TARGET_FIELDS` ask it (a Linear team, a Jira site, project and issue type). The settings change through `IssueSyncService#update_settings!`, from the page and from `update_workspace_settings` alike. A tracker that keeps items in step answers the rest of the `issue_tracker` contract: `create(title:, description:, target:, assignee_email:)` and `update(key:, target:, title:, state:, assignee_email:, unassign:)` answer an `Issues::Outcome` (the issue, notes about what was left alone, `gone` when the issue is no longer there) and `read(key, target:)` the `Issues::Issue` or nil. Each raises `Issues::Failed` with words a person reads. `SYNC_TOOLS` names every tool those call. A status is one of Firefight's `Issues::STATES` (open, started, done) mapped through the tracker's documented kinds, Linear's workflow state `type` and Jira's status category. A person is matched by an exact email, and one the tracker has no account for leaves its assignee alone with a note.

**Sync runs as its own agent.** Every call to the tracker is made as `SystemAgent.issue_sync`, never as the person whose change it was, so an item gets its issue whoever made it and no person's reach is borrowed. Choosing a tracker switches on its `SYNC_TOOLS` and grants exactly those to the agent through `Ability::Grant.grant!` (`Workspace#grant_issue_sync!`), and choosing another or none takes the grants back. `IncidentAction#authorize_issue_call!` authorizes each call through the gateway with source `issue_sync` and the person's name in `triggered_by_label`, so approval rules still apply and the activity log says whose change it carried. A grant taken back or a tool switched off is `Workspace#issue_sync_tools_blocked_reason`, which the setting shows. A call parked for approval stores `ApprovalResumption::KIND_ISSUE_SYNC` with the person, and runs again once approved. An issue that could not be opened leaves the item saved with `issue_sync_state` failed or declined and the reason in `issue_sync_note`, and asking again retries.

**Firefight's own apps and the webhook.** Linear and Jira are reached through their MCP servers, and also through Firefight's own OAuth application (the registry's `app`, `IntegrationProvider::App`, with `INTEGRATION_<KEY>_APP_CLIENT_ID` and `_APP_CLIENT_SECRET`), which the connect dialog offers as a native connection (`Entry#app_connect?`, `IntegrationsController#app_start`, `OauthClient.begin_app_flow`). The app's pack (`Packs::Linear` over Linear's GraphQL API, `Packs::Jira` over Jira's REST API through Atlassian's gateway) offers tools with the MCP servers' names and arguments and answers in their shapes, so the trackers read either connection the same way, and registers the webhook itself: Linear's `webhookCreate` on the team with a secret Firefight makes, Jira's dynamic webhook on the project's issues, which `IssueWebhookRefreshJob` refreshes before its 30 days run out. Registering and removing it is authorized as the admin who changed the settings (`workspace.update`, source `issue_sync`), and a registration that fails is `issue_webhook_error`, the setting's reason. Choosing another tracker or removing the connection removes it. A connection through an MCP server has the admin create the webhook from the `setup_steps` the setting shows and paste its signing secret. Deliveries arrive at `POST /api/v1/issue_events/:token`, an address only the workspace has, which `Issues.verify` checks as each tracker documents: Linear's `Linear-Signature` hex HMAC of the raw body within a minute of its `webhookTimestamp`, Jira's `X-Hub-Signature` `sha256=` HMAC for a webhook an admin made, or for one Firefight registered a bearer token Atlassian signs with the app's client secret whose `matchedWebhookIds` holds the workspace's webhook. `Issues.event` reads a delivery into an `Issues::Event` naming the fields that changed.

**Applying a change.** `IssueChangeJob` applies an event as the agent through `IncidentActionService#apply_issue_change`, which never sends it back. Each field keeps the time of its last change from either side (`issue_title_synced_at`, `issue_status_synced_at`, `issue_assignee_synced_at`), and a change is applied in one guarded `update_all` only when it is newer, so an echo or a delivery out of order changes nothing. Renaming, reopening and letting go of an item (`rename_action`, `reopen_action`, `unassign_action`, from the dashboard, Slack, the API and MCP) reach the issue like any other change. A deleted or archived issue moves the item to `gone` and it stops being kept in step. Only items whose `issue_integration` is the chosen connection are kept in step, and an issue Halon opens is linked to the connection it came through.

## Regions and connect fields

**Regions.** Where a provider runs its service in more than one place, such as Datadog's US1, EU1 and AP1 sites, its registry entry lists `regions` instead of a `server_url`: each a `key`, a `label`, its MCP server's `server_url`, its app's `site` (which links open) and, only where they differ from what its server names, its OAuth `authorization_endpoint` and `token_endpoint`. The first is the one a connection that names none reaches, and `IntegrationProvider::Entry#server_url` is its server. The connect dialog asks which only when there is more than one (`RegionSelect`), on one-click connect, on the token form (choosing one fills in its server's address) and on a pack's credentials form. `oauth_start` checks the region (`Entry#connect_refusal`), asks the token for the region's server (`OauthFlow.begin(server_url:, region:)`, whose endpoints stand in for the discovered ones in `OauthClient.discover`) and keeps the region in the session, and the callback writes the region and that server on the connection (`settings["region"]`). A connection made by pasting a server's address is in the region whose server has that host (`Entry#region_for_url`), and a native pack's connection made before its provider listed regions is in the first (`Integration#region`). A connection is in one region. Connecting another environment somewhere else is refused with words saying to add it as another account (`Integration#move_blocked_reason`), and reconnecting where it already is keeps calling the server it was made with, so a connection made before regions keeps its address. Link builders read the site from `settings.region`. Honeycomb (US, EU), Logfire (US, EU), Honeybadger (US, EU) and SigNoz (US, EU, India) list the regions their hosted MCP servers run in, each confirmed against the provider's own docs or source and cited on the entry, and each region's server names its own OAuth endpoints. A SigNoz team has its own address inside a region, so its regions have no site and its links use the address its health probe read. Axiom documents one hosted server, in the US, and OpenStatus and Better Stack one each, so they list a `server_url`, and Axiom and OpenStatus a top-level `site` for their links. A native pack's region carries only a `site` and no `server_url`, and the pack maps the region's key to its own API hosts, as a cloud with sovereign regions does. Regions are a single choice for the whole connection. An account that spans several regions lists them as a connect field with `options` and `multiple`. Datadog lists its seven sites with an MCP server (US1, US3, US5, EU1, AP1, AP2, UK1), each at the `/v1/mcp` address Datadog's documentation gives (DataDog/documentation, `regions.config.js`, `mcp_server_endpoint`). US1-FED and US2-FED have no MCP server, so they are not offered. New Relic lists its three data centers, US, EU and JP, each with the MCP server its setup guide gives (`mcp.newrelic.com`, `mcp.eu.newrelic.com`, `mcp.jp.newrelic.com`, all at `/mcp/`) and the app its documentation names (`one.newrelic.com`, `one.eu.newrelic.com`, `one.jp.newrelic.com`). Each server's resource metadata names the same authorization server, so no region lists OAuth endpoints. PagerDuty lists its US and EU service regions, each with its own hosted server (`mcp.pagerduty.com`, `mcp.eu.pagerduty.com`) and app (`app.pagerduty.com`, `app.eu.pagerduty.com`), from PagerDuty's MCP server and service region pages. Both servers name their own OAuth endpoints. Opsgenie lists its US and EU instances with no server, since it is a native pack. Each region's `site` is the Opsgenie app (`app.opsgenie.com`, `app.eu.opsgenie.com`, from Atlassian's page on the European service region), and `OpsgenieApi` reaches `api.opsgenie.com` or `api.eu.opsgenie.com` by the region's key. Tinybird lists the ten regions its API reference gives (Regions and endpoints), each keyed by its cloud and region (`gcp-europe-west3`, Tinybird's default and the first, `aws-us-west-2` and the rest) and labelled with its city, cloud and API host, with no server, since it is a native pack. `TinybirdApi::HOSTS` maps each key to its API host, and each region's `site` is its address in Tinybird Cloud (`https://cloud.tinybird.co/<cloud>/<region>`), as Tinybird's CLI maps an API host to it (`CLOUD_HOSTS` in the `tinybird` package's `tb/config.py`). Toronto is not in that map and Tinybird documents no address for it, so it has no site and a Toronto workspace's results carry no link.

**Connect fields.** `connect_fields` are what the connect form asks beside the credentials, each a `key`, `label`, `hint` and `placeholder`, and optionally `numeric`, `optional`, `path`, and `pattern` with `allowed` (`IntegrationProvider::ConnectField`, whose `refusal` checks a value). `pattern` is the shape a value must have, matched whole, and `allowed` says in words what it allows, which the form says when a value does not fit, so a field cannot declare a pattern without it. `options` (each a `value` and a `label`) makes a field a choice from a documented list, shown as a select, and `multiple: true` lets it hold several, shown as the shared multi-select (`SearchableMultiSelect`) and kept as a list, for an account that spans several regions. A value outside the list is refused with the list's labels. A path field holds one value. A path field without a pattern of its own takes a slug's (`SLUG_PATTERN`, a letter or number then letters, numbers, dots, dashes and underscores), so no value can carry a slash, a query or a fragment into the address and reach another organization or project, and `server_url_for` escapes each part as well. None is a secret. A `path` field is part of the server's address, appended in the order listed, and an optional one left empty ends the address there (`Entry#server_url_for`), so an organization and then an optional project make `/mcp/<organization>/<project>`. A field with `query: <name>` is the address's query parameter of that name, joined to the server's own query, escaped, and left out when empty, such as a project ref. Both belong to the connection (`settings["fields"]`), and the token form, where the whole address is pasted, does not ask them. A field with a `default` may be left empty, shows its default as its placeholder (by its option's label for a field with `options`), and `settings.field` answers the default for it. A path or query field left empty takes its default in the address too, so the address matches what `settings.field` answers.

**Chosen after connecting.** A field with `learned: <key>` takes its choices from what the connection's health probe learned under that key (a list of `value` and `label`), so the connect form never asks it. Once the probe has found two or more, the connection's details show the choice beside the environment as a select (`IntegrationSerializer#environments`, `choices`), and choosing one (`PATCH /integrations/:id/choose`, `IntegrationEnvironment#choose!`) keeps it on the environment with a toast, refusing anything the connection did not learn. `settings.field` reads it like any other field. It is how a provider with several datasources of a kind, none marked default, is told which to read, rather than skipping it or guessing. Every other field belongs to the environment it was connected for (`IntegrationEnvironment#fields`). The fields come from the registry through the serializer (`connectFields`), so the form holds no provider list (`ConnectFields`), and the connection's details show its region and fields beside each environment (`IntegrationSerializer#environments`, `settings`).

## Groups on the Integrations page

A provider sits in one group, its registry `category`, which only helps a person find it: Cloud and hosting (where apps run and what can be changed there, Northflank, Cloudflare, Kubernetes, DigitalOcean, Netlify, Convex, Trigger.dev, Modal, AWS, Google Cloud, Azure, Vercel, Render, Railway and Fly.io), Observability (logs, metrics, traces and errors), Alerting and on-call (who is on call and what is paging them, PagerDuty and Opsgenie, whose skills sit under `alerting_and_on-call`, the category's slug), Product analytics (who an incident reaches and the feature flags behind it, PostHog and Mixpanel), Databases, Code (GitHub, GitLab and Bitbucket), CI (builds and tests run outside the code host, CircleCI), Coding agents (Devin, Cursor and Factory, which write a fix's code change and open the pull request), Issues, Knowledge and Custom. The `categories` list sets the order the gallery shows them in, and Halon's connection groups follow the same names (`Chat::Tools::Groups.of_connection`). A provider's skills live under `config/skills/<provider>/<category slug>/`. Every connected provider is usable by Halon through its own tools, and what a provider can do is not its group. A card's info button opens its details (`ProviderAbout`): its description, what Halon can do through it (`IntegrationProviderSerializer#halon`, from `Capabilities.halon_sentence`, which names the capabilities its adapter answers and says a provider without one is used through its own tools, shown only where Halon is on), whether it is read onto the map (`on_map`, the registry's `map`), and that only switched on tools are used and changes follow permissions and approval rules.

## Capabilities

A capability answers one question, or makes one change, for anything on the resource map, whichever connected provider holds it (`Integrations::Capabilities`). The provider tools are what a provider can do. A capability is how an agent asks for it without knowing which provider runs the resource.

- **The capabilities** are `SPECS`, each with its tool name and parameters: `search_logs`, `query_metrics`, `recent_deploys`, `resource_status`, `search_errors`, `search_traces`, and the changes `rollback`, `restart` and `scale`. Every one takes `resource`, its name or id on the map, and `connection`, the integration's slug, offered as an enum only when more than one connection could answer. Metric names (`METRIC_NAMES`) and log streams (`LOG_STREAMS`) are one vocabulary every adapter maps to its provider's own.
- **An adapter per provider** (named by its definition, under `app/services/integrations/capabilities/`) declares `SUPPORTS` (the kinds of resource each capability covers), `TOOLS` (the provider tool each one runs as), `WRAPPED` (the provider tools it answers one to one) and `route`, which turns a request into a `Route` with what the connection was set up with (`settings:`, its `ConnectionSettings`): the tool, that tool's own arguments, and `present`, which reads the provider's answer back into the shapes every capability returns (`Integrations::Telemetry` results, charts and links). Northflank maps onto its own tools, with a change through `api_request` on the paths its fixes skill gives. Render, Railway, Fly.io and Vercel have a pack tool for each capability, changes included, so their adapters only rename streams and metrics into the provider's own words and refuse what the provider cannot take, such as a regular expression where its log search has none. Cloudflare writes every request itself into `execute`, each value a JSON literal (`Capabilities::Cloudflare.script`). A time range is worked out by the script when it runs, from the minutes asked, so a call reads the same each time and a replay matches it, and an answer Cloudflare marks failed (`success: false`, or GraphQL `errors` with no data) is thrown, so a chat and a fix see an error. It reads on the endpoints and GraphQL fields Cloudflare's docs give: Workers Observability for logs, `workersInvocationsAdaptive` (bucketed by Firefight) and `httpRequestsAdaptiveGroups` by `datetimeHour` for metrics, Workers and Pages deployments, and their rollbacks. The account id is read from the resource's dashboard address, which the map's reader writes as the dashboard, then the account id. AWS (`Capabilities::Aws`) runs each capability as its pack's own tool, by the resource's ARN, which the map keeps as its id. Each change has a tool of its own (`rollback_deployment`, `restart_service`, `scale_service`), so each is granted and approved apart. Its metric names map onto the CloudWatch metric AWS documents for the same reading: cpu and memory for an ECS service, requests and errors as a Lambda function's Invocations and Errors, cpu and network for an EC2 instance, cpu and tcp_connections (DatabaseConnections) for an RDS database. `cloudwatch_metrics` reads more metrics than those names cover, so it is not wrapped.
- **An observability tool watches what others run.** An adapter that declares `OBSERVES` instead of `SUPPORTS` (Datadog) answers for a resource some other connection holds, by the resource's name, through a reachable connection to it (`IntegrationEnvironment.reachable`, the scope `Resource#holders` uses too) whose tool for the capability the caller may run (`Capabilities.observers`). A connection wired to an environment answers only for a resource held in the same one. One that cannot take what was asked (`accepts?`, Datadog for a regular expression or a stream other than app) is passed over for the platform unless it was named, so connecting it never takes away a read the platform answers today. Datadog answers logs, traces and errors through `search_datadog_logs`, `search_datadog_spans` and `search_datadog_error_tracking_issues`, and metrics through `get_datadog_metric` for cpu or memory asked alone (`container.cpu.usage`, `container.memory.usage`, which Datadog documents for every tagged service, one metric a call). Any other metric, or several, is the platform's. Datadog publishes its tools' parameters only from its server, so `route` writes the arguments against the parameters the connected tool reports (`params_schema`): the service as its own argument or as `service:` in the query, the time as two fields or one object holding them, and a limit only when the tool takes one. Minutes alone are sent as Datadog's relative time (`now-15m` to `now`), so the same request reads the same each time and an approved call matches its retry, and a start or end in ISO 8601. A shape it does not know, or a time field that is not a string, is refused with words, never guessed. The parameter names are matched against what the server reports, since Datadog does not publish them. Its tools reach every service Datadog sees, so none is wrapped and all stay offered. Other metric names for a service depend on how each team set Datadog up, so they are not routed there. Sentry (`Capabilities::Sentry`) answers errors and deploys for the error kinds every error tracker watches (`Adapter::ERROR_KINDS`, a service, worker, job or site) by the Sentry project of the same name, which has to be a slug Sentry's server accepts. Its tools, parameters and answers are read off its open source server, getsentry/sentry-mcp. Errors go to `search_issues`, one row per kind of error with its counts. The window goes in the query as Sentry's relative time, `lastSeen:-30m`, so a retry matches an approved call. A start or end goes as `lastSeen:>=` and `lastSeen:<=` in ISO 8601. `period` is the smallest of the tool's windows, 24h to 90d, that covers it, `sort` is date, and `text` becomes `message:"..."`. Releases go to `execute_sentry_tool` running `find_releases`, a tool Sentry keeps in its catalog rather than listing it, and `present` turns its structured answer into one line per release with its times, last deploy, last commit and new issues. Every Sentry tool needs the organization, and the server reads it from the connection's address, `/mcp/<organization>` or `/mcp/<organization>/<project>`, holding the session and an OAuth grant to what it names. The registry's path fields ask for the organization and an optional project on one-click connect, so the address is built from them, and a pasted address is read the same way. Each field takes only what Sentry's own slug rules allow, `ORG_SLUG_PATTERN` and `MIXED_SLUG_PATTERN` in getsentry/sentry `src/sentry/utils/slug.py`, at most 50 characters. They are narrower than the foundation's default slug: an organization has no dots or underscores and does not end in a dash, a project is lowercase, and neither is only numbers. A connection made at the bare `/mcp` is refused with words telling an admin to connect again with the organization. One held to a project answers only for that project, and the server fills the project in. Sentry has US and EU data regions behind one server address, which resolves the region itself, so it lists no `regions`. Deploys are not in `SIGNALS`, so the platform that runs a resource answers them unless `connection` names Sentry. Sentry cannot roll anything back. Its logs, traces and metrics are not routed there, so connecting Sentry never takes a read away from Datadog or the platform. Its health check is the MCP ping every remote connection gets, and it keeps no metric Firefight routes, so it has no baselines. Grafana's adapter, `Capabilities::Grafana`, reads Loki for logs, Prometheus for cpu and memory, and Tempo for traces, through its MCP server's `query_loki_logs`, `query_prometheus` and `search_tempo_traces`. The tool names, arguments and answers come from grafana/mcp-grafana's source (`tools/loki.go`, `tools/prometheus.go`, `tools/tempo.go`). Logs use the stream selector `{service_name="<name>"}`, a label Loki fills on every stream from the labels a shipper sets. Text, exclude and a regular expression become the LogQL line filters `|=`, `!=` and `|~`, newest first, at most 100 lines, the server's default cap. Metrics are cpu and memory only. They come from the kubelet's cAdvisor metrics by the Kubernetes `container` label: `container_cpu_usage_seconds_total` as a rate in cores and `container_memory_working_set_bytes` in MiB, one series per pod. Both go in one PromQL query, each series labelled `firefight_metric` by `label_replace`, so one call draws both charts. cAdvisor keeps network counters per pod with no container label, and every other metric depends on how a team instruments its code, so the platform answers those. Traces use the TraceQL `{ resource.service.name = "<name>" }`, with text as a regular expression on the span name, slowest first. An empty answer stays Grafana's own, with its hints, and counts as no answer, so the platform is asked. Each read goes to the datasource of its type that a person chose on the connection's details (`logs_datasource`, `metrics_datasource`, `traces_datasource`, connect fields with `learned`), else the only one the health probe found, else Grafana's default. A connection without one is passed over (`reaches?`), so connecting Grafana never takes away a read the platform answers today.
- **New Relic answers through NRQL** (`Capabilities::Newrelic`). It observes logs, metrics, deploys, errors and traces for services, workers and jobs, and each one runs as `execute_nrql_query` on New Relic's MCP server with one NRQL query Firefight writes. The tool's name is from New Relic's MCP tool reference (docs.newrelic.com/docs/agentic-ai/mcp/tool-reference). Its parameters are not published, so, as with Datadog, the query goes in whichever of `query`, `nrql_query` or `nrql` the connected tool reports, and any other shape is refused with words. The account goes in `account_id` or `accountId` when the tool has one, as a number unless the tool says string. New Relic's own agent skills say the tool needs an account, and one sign-in reaches every account in the organization, so each environment keeps the account it reads, from the `account_id` connect field (`settings.field`). Without one, New Relic is passed over, and refuses with words when named. The queries use event types and attributes from New Relic's attribute dictionary:
  - logs: `Log` by `entity.name` (logs in context) or `service.name` (OpenTelemetry), newest first, with text as `LIKE`, exclude as `NOT LIKE`, and a regular expression as `RLIKE` wrapped to match anywhere in a line, since RLIKE matches the whole value
  - errors: `TransactionError` grouped by `error.class` and `error.message`, with when each was first and last seen. A site's errors (`ERROR_KINDS`) are `JavaScriptError`, what browser monitoring caught in its pages, by the browser app's name, grouped by `errorClass` and `errorMessage` with the page each was last seen on

Other metrics are the platform's.

  An answer with no transactions at all comes back as text with an empty chart list, which `definitive?` reads as no answer, so the platform answers instead. NRQL counts zero for a name it has never seen, and that zero must not read as evidence. Minutes alone are sent as `SINCE 30 minutes ago`, so a call reads the same each time and an approved call matches its retry. A start or end goes into `SINCE` and `UNTIL` as ISO 8601. ## Native packs

A provider marked `kind: native` in the registry executes through a first-party Ruby pack instead of an MCP server. Everything downstream of execution is identical — same `Integration::Tool` allowlist, same minted actions, same gateway, same ledger — and the connect flow simply skips the server URL.

- **`Integration#executor` is the one place kinds diverge.** It returns the per-kind facade (`McpExecutor` or `NativeExecutor`), and each facade owns the whole provider conversation: `call` (execute an authorized invocation), `tool_definitions` (what the provider offers, as `Integrations::ToolDefinition` rows), and `check_health!` (probe with a row's credentials). Discovery, health checks, and `ConnectionToolFactory` go through the facade and never branch on kind — adding a kind is one facade class, touching no existing flow.
- A pack subclasses `Integrations::NativePack`, declares its tools with the `tool` DSL (name, description, params schema, read-only flag), and implements one instance method per tool. The declarations are the native analogue of an MCP server's `tools/list`; `DiscoveryService` reconciles both with the same semantics (arrive disabled, vanished tools marked removed never deleted).
- A provider's definition names its pack (`Integrations::Provider`, `pack`), and `NativePack.for(key)` reads it. A registry sanity test fails if a `kind: native` provider has no pack.
- **Declaring a new tool on a shipped pack does not reach existing connections.** Discovery runs at connect and at **Refresh tools**, and the health sweep only probes. So adding a tool means either every admin clicks Refresh or the PR carries a data migration calling `DiscoveryService.sync!` for `kind: native` integrations (`20260912140000_sync_native_integration_tools`). Native definitions come from code, so that migration calls no provider.
- **Errors share one hierarchy.** `Integrations::Error` is the base; `McpClient::Error` and `NativePack::Error` subclass it, and rescue sites catch the base so they never grow with new kinds. A pack's `check_health!` raises `NativePack::Error` with a readable reason and the row records as failing.
- **Results share one shape.** Executors normalize through `Integrations::ToolResult` on the way out (MCP content shape), so callers read `result["content"]` without defending.
- Adding a native provider = the registry entry with `kind: native`, the pack class, and its definition naming it. The `http` kind remains a constant with no executor.
- **A pack can connect from a pasted URL.** `connect_with: connection_url` in the registry makes the connect dialog ask for a connection URL per environment (`components/integrations/connection-url-form.tsx`) instead of an install or OAuth. The pack answers `connection_refusal` for the URL and any pasted certificates before anything is saved, so a bad or private address or a malformed certificate is said on the form, and `store_connection!` writes them on the environment row, since the pack owns the credential's shape. Each connect sets the whole credential, so certificates left out are removed. The same connection name adds an environment or replaces its URL, through `connect!` like OAuth. `connection_url` and `certificates` are filtered from request logs.
- **PostgreSQL is a native pack** (`Integrations::Packs::Postgres`), connected from a URL by default. The dialog still offers "Use an MCP server instead" for a team that runs one or cannot open its database to the internet, which saves an MCP connection (`kind` is per connection, so both kinds share the entry). Connections made through an MCP server before keep running through MCP. The tools are `list_tables`, `describe_table`, `run_query`, `explain_query`, `current_activity` (connections by state against `max_connections`, the longest running queries, and who blocks whom), `table_health` (scans, dead rows, vacuum and analyze times) and `database_status` (version, size, uptime, primary or replica, connections, lock waits, the oldest transaction, transaction ID age, commits, rollbacks, deadlocks and cache hit rate since the last reset, and replication, all from the statistics views any user may read), all read only, in the Databases group. Every call opens one connection (`Postgres::Connection`) with `default_transaction_read_only`, a 10 second `statement_timeout`, a lock timeout and an idle timeout, inside `BEGIN READ ONLY`, so a user with write rights still cannot write. `run_query` reads through a cursor, which Postgres only allows for statements that return rows, and fetches at most 200. Statements go through the extended protocol, which takes exactly one, so nothing rides after a semicolon. Cells are cut to 300 characters.
- **A database is only reached on a public address.** The host is resolved before connecting, and a private, loopback, link-local or reserved address (including the 100.64.0.0/10 range clouds use inside their own networks) is refused, since the connection is made from Firefight's network. The connection goes to the resolved address (`hostaddr`), so the name cannot point somewhere else after the check. Sockets and several hosts are refused, and so is any URL option that names a file on Firefight's servers (`sslrootcert` other than `system`, `sslcert`, `sslkey`, `sslcrl`, `passfile`, `service`), since certificates arrive pasted as text. A public database is only reached encrypted: a URL that says nothing or `prefer` gets `require`, and `disable` or `allow` is refused. A pasted CA certificate, client certificate and unencrypted client key are written to files readable by this process only for the length of one connection. An operator allows private hosts with `INTEGRATION_POSTGRESQL_PRIVATE_HOSTS`, comma separated names, addresses or ranges, which is how Firefight reads its own database and how a self-hosted install reaches its own. MCP server addresses have no such check yet.
- **A pack can connect with credentials.** `connect_with: api_token` in the registry makes the connect dialog ask for the fields the pack lists in `credential_fields` (`NativePack::CredentialField`: key, label, hint, placeholder, secret), per environment (`components/integrations/credentials-form.tsx`). The serializer ships the fields, so the form holds no provider list. The pack answers `credential_refusal` by calling the provider with the values before anything is saved, so a wrong token is said on the form, and `store_credentials!` writes them on the environment row. The same name adds an environment or replaces its values. `credentials` is filtered from request logs.
- **Google Cloud is a native pack** (`Integrations::Packs::GoogleCloud`), connected with a service account's JSON key, its one credential, pasted into a text area, and a project per environment, a connect field matched against Google's rule for a project id, through `Integrations::GoogleCloudApi`. The key signs a JWT that Google trades for an hour's token, the JWT bearer grant Google documents for service accounts, with scope `cloud-platform`. The token is cached on the environment row, and connecting again replaces the whole credential, cache included. Google's MCP servers were not used. - **Azure is a native pack** (`Integrations::Packs::Azure`), connected with a service principal's client secret, its one credential, and the tenant, client id and subscription as connect fields, each matched against the GUID or domain Microsoft documents, through `Integrations::AzureApi`. Every region of the subscription and every location of the project is read, so neither asks for a list of them. Logs are Kusto queries through Log Analytics, by the resource's id for App Service, Functions, PostgreSQL and Azure SQL tables, and wherever a Container App's environment sends its logs. A table no diagnostic setting fills answers as a plain result that says how to send it. Metrics come from Azure Monitor with the names and aggregations in `Packs::Azure::Metrics`, a total turned into a rate, an App Service app's CPU read from its plan. A rollback is `slotsswap` with production, or a Container App's ingress sent back whole with all traffic on one revision, which needs multiple revision mode. Scaling reads an App Service plan and puts it back whole with only `sku.capacity` changed, naming the apps that share it, or sends a Container App's template back with only its scale changed. A resource is named by its Resource Manager id (`Packs::Azure::Target`) or by its name, and only the connected subscription is reached. Results link to the resource's page in the portal in the form Microsoft's docs print it, `<portal>/#@<tenant>/resource<id>/overview`. Microsoft documents no address that opens Log Analytics on a query, so log results link to the resource too. The health check reads the subscription.

## Coding agents

Firefight's own agent writes a fix's code change with OpenCode in Firefight's sandbox, through GitHub's `fix_code` (see Code sandbox, and docs/ai.md). A coding agent writes it in its own environment and opens the pull request itself. Devin, Cursor's cloud agents and Factory's Droids are native packs in the Coding agents category, each registered in `providers/<key>.rb` with only its `pack`. They share a base, `Integrations::Packs::CodingAgent`, and connect with an API key (`connect_with: api_token`). Each declares `fix_code`, a write that arrives switched off, and `session_status`, a read. `fix_code` takes GitHub's parameters (`repo`, `brief`, `title`, `summary`, `base`, `context`), so a code step's arguments (`RemediationStep#code_arguments`) fit either. The registry entries carry `code_fix_tool: fix_code`, `code_agent: true`, `map: none` (they run nothing of the workspace's) and `source_links: firefight`. The base answers `halon_sentence` for all three, since their work is a code change and not a capability. The API clients are `DevinApi`, `CursorApi` and `FactoryApi`, on `CodingAgentApi`, which reads answers through `Http.json` and raises a 401, 403 or 404 as `Unauthorized`, `Forbidden` or `NotFound`, so a pack says what to change. ArchSpec lets each pack use only its own client, and only the base uses `CodingAgentApi`.

- **The workspace chooses who writes code changes.** `Workspace#code_fix_agent` holds a coding agent connection's slug. It starts empty, so Firefight's own agent writes code changes until an admin picks another under Settings, Workspace ("Write code fixes with") or with `update_workspace_settings` over MCP. `Workspace::CodeFixes` checks the slug against the workspace's coding agent connections, lists the choices, and says why code steps cannot reach the chosen agent (`code_fix_agent_blocked_reason`: it was removed, it is turned off, or its `fix_code` is off). `RemediationStep#code_tool` returns the chosen agent's `fix_code` while it is on. When it is off the step waits for a person, and Firefight's own agent is never used in its place, since nobody chose it. With no choice the step uses GitHub's `fix_code` as before (`IntegrationProvider.code_hosts`).
- **The same guarantees as `fix_code`.** The step calls the agent's `fix_code` through `RemediationStep#authorize_call!` as the person who applied the fix. Grants, approval rules and the ledger see `<slug>.fix_code` with arguments fixed when the step starts. An investigation is offered no write (`STATE_READS_ONLY`), so it never starts one, though it can read a session with `session_status`. The brief carries the finding, its evidence, how to tell it worked, the repository and the branch. It asks for one pull request, ready for review and never merged, nothing under `.github/`, and no logs, customer data or credentials in the pull request or its commits. Anything that looks like a credential is redacted (`Chat::SecretFree::SECRET_PATTERNS`) before it leaves Firefight. Firefight cannot refuse a change the agent pushes itself, so the brief is the only control there.
- **Followed to an answer.** `fix_code` starts the session and reads it every `POLL_EVERY` seconds, for at most `CodingAgent::TIME_LIMIT` (30 minutes, under `RemediationStep::CODE_STALE_AFTER`), then stops it. A pull request opened in time counts. A run that ends without one is read `PULL_REQUEST_GRACE` more times, because a pull request can land a moment later. After `MISSES_ALLOWED` failed reads in a row it gives up and says where to follow the session. The answer names the pull requests, the agent's last words, what it used and the session's page, and links the pull request (`Telemetry.result`). A failure says why, with the same details. While it runs the pack calls `report`, and `FixRunner#progress_of` writes the words onto the step with `RemediationStep#progress!` and redraws the thread. `progress!` is a guarded update on a running step, so a late report never overwrites how the step ended.
- **Devin** (`DevinApi`, v3, from Devin's OpenAPI document) is one organization per environment. It takes a service user's key or a personal access token (both start `cog_`) as its credential. The organization id (`org-`, checked by the registry's `pattern`) and an ACU limit per change (`max_acus`, sent as `max_acu_limit`, which Devin enforces, with the registry's `default: 5` when left empty) are connect fields, read with `settings.field`. The prompt names the repository and the branch, as Devin's own handoff docs do, because the `repos` field's format is not documented. Devin's `status` and `status_detail` decide where a session stands. New, claimed, resuming and running are working. `waiting_for_user` and `waiting_for_approval` wait for a person in Devin and are still followed. `exit` or `finished` is done, and so is a wait with a pull request open. `suspended` and `error` stop it, with words for each `status_detail`. Pull requests come from `pull_requests[].pr_url`, the page from `url`, and the last words from the last `devin` message. A session is stopped by terminating it. The health check is `GET /v3/self`, which refuses a service user of another organization. Devin documents one API host.
- **Cursor** (`CursorApi`, Cloud Agents API v1, in public beta) takes a user's or a service account's key. A change is an agent on the repository's address, with `base` as `startingRef` and `autoCreatePR`. The address comes from the resource map, or from `repo` given as an address, never built from a name. A path two code hosts both hold, such as a mirror, is two repositories, so Cursor asks for the address instead of picking one. A pull request's link is named for the code host whose registry `site` it is on (`ResourceMap.repository_of`). The first run's `status` decides where it stands: CREATING and RUNNING work, FINISHED is done, ERROR, CANCELLED and EXPIRED stop. Pull requests come from `git.branches[].prUrl` and the last words from `result`. The run is cancelled at the limit. Cursor has no spending limit for an agent, so what it used is read from its usage, in tokens. The page is the agent's `url`, and the health check is `GET /v1/me`. Cursor documents one API host.
- **Factory** (`FactoryApi`, from Factory's OpenAPI document) takes a Factory API key as its credential and a Droid Computer's name as a connect field, per environment. Factory switches its sessions API on for selected organizations only. A connection is in Factory's Global or EU deployment (registry `regions`, from Factory's deployment docs), and `FactoryApi` reaches `api.factory.ai` or `api.eu.factory.ai` by the region's key. A change is a session on the computer, in the folder where the repository is cloned (`clonedRepoDirectories`, matched by the repository's name and refused when there is none or several), with `interactionMode` auto and `autonomyLevel` high, which Factory's docs give for work that commits and pushes. The brief is its first message. The session is followed until it is idle again and interrupted at the limit, and what it used is `factoryCredits`. Factory returns no pull request and documents no page for a session, so the pull request is read from the Droid's messages and is the only link. The health check reads the computer and refuses one still provisioning or failed.

## Code sandbox

A code host's code tools read in a sandbox, one per run, in `Integrations::Packs::CodeHost::Code`, which GitHub's, GitLab's and Bitbucket's packs include. A pack names its repository parameter (`REPO_PARAM`), the repositories a definition is looked for in (`visible_repositories`) and where git fetches from (`code_remote`, a `CodeReading::Remote` with the host, the user git signs in as, the token and any git settings). The tools are `list_files`, `code_search`, `find_definition`, `find_usages`, `git_log`, `show_commit`, `diff_refs`, `ask_language_server`, `run_shell` and `run_tests`. Repo content is untrusted input, so the rules are structural, not advisory:

- **One box per run, found by key.** `Chat::Tools::Connection` passes the run's `code_box_key` (an investigation, a conversation, or an outside agent over MCP by principal) through the executor into the pack. `Integrations::CodeReading` finds the live `CodeBox` for the key or starts one, under a Postgres advisory lock so two tools called at once start one box. A code tool called outside a run is refused.
- **The whole history goes in, no credential does.** The first time a run names a repository, the worker mirrors it with the connection's token as a per-call `http.extraHeader` (GitHub's installation token as `x-access-token`, unless the pack's remote names another user), bundles every ref with `git bundle create --all`, and pushes the bundle to the box. The box keeps a bare repository, so any commit reads locally, `git log -S` included. A commit the box has not seen fetches the repository again once. git stderr is scrubbed of the credential before it reaches an error. A repository on another host is kept under the host's name (`gitlab.com:acme/web`) and stored apart in the box, so a project mirrored on two hosts is two repositories.
- **Commands are argument lists.** The app sends `argv` to the command service in the image (`sandbox/server.rb`), never a string it would have to trust, except `run_shell` and `run_tests`, whose whole point is a command. Refs that start with `-` are refused on both sides. Reads run as `reader`, who cannot write the code. Checkouts are per commit and read only. Tests and language servers run as `runner` in a writable copy per commit.
- **Secrets-shaped paths** are filtered from listings, search and definitions in the pack, as before. `run_shell` can read any file in the checkout, so it and `run_tests` wait for the workspace's AI SRE flag.
- **Language servers** for Ruby, TypeScript and JavaScript, Go and Python run per checkout and language, kept alive for the box's life. The Ruby server runs from its own bundle (`sandbox/lsp/Gemfile`), so it reads a repository's code without installing that repository's gems. Servers that index first are waited on until they report progress done.
- **Tests** install what the repository's lockfiles and version files ask for, once per copy (mise for `.ruby-version`, `.nvmrc`, `.tool-versions`, `mise.toml`, then bundler, npm, yarn, pnpm, pip or go), and can start Postgres and Redis inside the box, which set `DATABASE_URL` and `REDIS_URL`. The image also carries libvips and a font, which image code such as Firefight's own chart drawing needs to load, since a repository's system libraries are not installed on demand.
- **Providers only start and stop boxes** (`Integrations::Sandboxes`). `SANDBOX_PROVIDER=docker` speaks the Docker Engine API over the daemon socket (`DOCKER_HOST`, default `/var/run/docker.sock`), puts a box on `SANDBOX_DOCKER_NETWORK` when set and reaches it by name, and publishes it on loopback otherwise. `SANDBOX_PROVIDER=northflank` creates a private service in `NORTHFLANK_SANDBOX_PROJECT` with `NORTHFLANK_API_TOKEN`, reached as `http://<service>:8080` inside the project. Both start `SANDBOX_IMAGE`, default the published `ghcr.io/firefightlabs/firefight-sandbox:latest`. Without a provider the tools answer that code reading is not set up. ArchSpec lets only the integrations layer name a provider, so a new one is one class.
- **A box that cannot start is said once.** No provider, or a provider that refuses (a Docker daemon the worker cannot reach, a Northflank error), raises `Integrations::Unavailable` with `CodeReading::UNAVAILABLE`: the reason, that every sandbox tool will fail the same way for the rest of the run, that fetching one file or its blame from the code host still works, and that the answer should say code could not be searched. The failure is remembered for the run's key for `UNAVAILABLE_FOR` in process memory, so later reads fail at once without asking the provider again. A failed step keeps the error's message as well as its class (`Investigation::Step#fail!`), since `Error` alone says nothing.
- **A box that is gone is replaced.** A row can say a box is live after its container or service went away outside Firefight (stopped by hand, a Docker restart, a reboot, the provider). When a call fails and the box no longer answers `/health` (`Sandboxes::Client#alive?`), `CodeReading` closes the row, starts a new box, pushes the repository again and runs the call once more. A failure in a box that still answers is reported as it is.
- **Boxes stop.** An investigation closes its box when it finishes or gives up. A conversation's box closes after `CodeBox::IDLE_AFTER` without a read (`CodeBoxIdleJob`). `CodeBoxSweepJob`, every 10 minutes, stops boxes unused for `CodeBox::ABANDONED_AFTER` and any box a provider still runs that no row knows, once it is older than the start-up grace.
- **The image carries OpenCode** (`opencode-ai`, pinned in `sandbox/Dockerfile`), the coding agent GitHub's `fix_code` runs. It reaches a model only through Firefight's proxy with a session token, never a provider key. See docs/ai.md. A workspace can choose a connected coding agent instead, see Coding agents.
- **Egress is open.** Northflank's hosted cloud cannot deny outbound traffic from a box, only a BYOC cluster can, and a plain Docker network allows it too. The read tools only run commands the pack builds, so the commands a repository chooses, `run_shell` and `run_tests`, are the ones that wait for the AI SRE flag.

`Integrations::HealthCheckSweepJob` (recurring, every 30 minutes) probes every enabled environment row of every active integration with the executor's `check_health!` and records the result, so dead credentials surface before an incident needs the connection. A remote server is pinged, and a provider with a health probe is also read through its own tools (see How a provider plugs in). Grafana's server answers a ping without reaching Grafana, so its probe, `HealthProbes::Grafana`, calls `list_datasources`, every page. That only answers when the server reaches Grafana with its token, so a refusal marks the connection failing in Grafana's words. The probe keeps the Loki, Prometheus and Tempo datasources, and each type again as a list of value and label (`loki`, `prometheus`, `tempo`) for the connection's details to offer. The details show a choice only for a type Grafana has two or more of. Once, through `generate_deeplink` for an Explore link, the probe also learns Grafana's own address, the part before `/explore`, kept only when it is an http or https address. With `list_datasources` off the ping alone decides and nothing new is learned. With `generate_deeplink` off there are no links rather than a guessed address. A server that allows writes marks `generate_deeplink` a write, since it can save a short link in Grafana, so it arrives off and reads only leaves it off. OpenStatus's probe keeps its monitors, Better Stack's its monitors when the answer is in its Uptime API's shape, Honeybadger's its projects and each one's uptime sites (ids, names and addresses, at most 25 projects), Logfire's the project's address on the region's app, and SigNoz's the team's address from a service's page. Honeycomb's and Axiom's check that the environment or datasets the connection names are among the ones the provider lists. Transitions to failing are logged; the admin-facing alert is a pending product decision.

## Connections

```
Integration (kind: mcp | http | native, immutable slug, kill switch)
├─ IntegrationEnvironment   per-environment encrypted credentials, health
└─ Integration::Tool        the allowlist; enabling mints one Ability::Action
```

- **Discovery never auto-enables anything.** Tools arrive disabled and an admin allowlists them.
- **Vanished tools are marked removed, never deleted or switched off.** `enabled` is the admin's allowlist and `removed_at` is whether the provider still offers the tool. Discovery writes only `removed_at`, so a tool that comes back keeps the admin's earlier choice. A removed tool cannot be toggled (the row's `toggle_blocked_reason` says why), is skipped by bulk enable, is not published over MCP, and fails the config check. Its action row and grants survive.
- Disabling an integration is a kill switch: its tools leave the outward MCP registry entirely.
- Every connect and refresh path goes through `Integrations::ConnectionRefresh`, so an unreachable server always lands as a readable error on the row instead of an exception a caller has to remember to catch.

## Resource map

What each connection reaches, synced by machines, kept apart from the catalog (which people curate and alert routing reads). `ResourceMap::Resource` rows carry a provider, an account (a Northflank team and project, a GitHub owner, a domain's apex), a kind (`ResourceMap::KINDS`), the provider's own id, a status, a link to the resource's page and a few details, plus the connection that last reported it. A resource is identified by provider, account, kind and id across the workspace, so a repository two connections build from is one resource. `ResourceMap::Link` rows join two resources with a relation (`ResourceMap::RELATIONS`, read as "from runs builds of to") and an origin: declared by a provider, matched, added by a person, or suggested by Halon.

- **Sweeps read, the model writes.** `Integration#executor.map_of(environment_row)` returns a `ResourceMap::Snapshot` (resources, links, and gaps in words), or nil for a connection with nothing to put on the map. A native pack answers it (`NativePack#map_of`, nil by default). An MCP server lists tools, not what it reaches, so an MCP provider goes on the map through the reader its definition names (`map_reader`), which calls only the tools an admin switched on. A tool that is off is a gap, never called anyway. Without a reader the connection puts nothing on the map. `ResourceMap.record!` upserts every resource the snapshot names, marks the ones this connection reported before and no longer does as removed (kept, so a resource that returns keeps its first sighting and its links), and replaces this connection's declared links. A person's links, Halon's suggestions and the links matched from settings (below) are never touched by a sweep.
- **A failed sweep leaves the map as it was.** `Integrations::MapSweep` records the provider's error on the connection (`map_error`) and returns. The hourly `MapSweepJob` sweeps each connection on its own, so any other error, such as an answer Firefight could not read, is recorded on that connection (`MapSweep::UNEXPECTED`, with the error in the log) and the sweep goes on to the rest. What a sweep could read but not all of goes in `map_gaps`, such as Northflank jobs when the token lacks the Jobs permission, so a partial map says what it is missing.
- **When it runs.** `Integrations::MapSweepJob` runs hourly (`config/recurring.yml`) and sweeps every enabled connection that is due (`MapSweep.due?`). A reader sets how often with `EVERY`, hourly unless it says (`McpExecutor.map_every`), and Cloudflare says daily. Sync now and `ConnectionRefresh` sweep a connection at once, whatever it says, so a new connection is on the map straight away.
- **Every cloud is on the map** (CLAUDE.md, Architecture Rules). Each provider in `config/integration_providers.yml` declares `map`: `firefight` (a pack's `map_of` or its definition's `map_reader`), `none` with a `map_note` (it holds no infrastructure, such as a telemetry or issue tool) or `unchecked` (it may, and no reader exists yet, which no provider declares now). The registry refuses to load an undeclared or unknown value, and `Integrations::MapSweepTest` fails for a `firefight` provider nothing reads.
- **A remote reader's calls are in the activity log.** `McpExecutor.map_of` runs each call through `Integration::Tool#swept!`, which records it under `SystemAgent.map_sweep` (source `map_sweep`), allowed because an admin switched the tool on, with what it read and never the script, and finalizes it with its outcome and, for an error, the first line of what the server said. The activity log's sources come from `LEDGER_SOURCES`. The sweep holds no grants and calls nothing an admin has not switched on.
- **Northflank** puts its services, build services, databases and jobs on the map, each with its page in Northflank's app. A deployment service runs builds of the build service its deployment names (`deployment.internal.nfObjectId`), a service built from GitHub is built from that repository (`vcsData.projectUrl`), and a service serves the domains on its public ports. Private ports' domains are left off. Its lists follow Northflank's cursor (`pagination.hasNextPage`, `cursor`) for up to ten pages of 100, and one cut short is a gap naming its kinds. The provider's `status_words` read an addon's in-between states (preDeployment, allocating, scaling, upgrading, backup, restore and the like) as Firefight's words, so a database never reads unknown while it changes.
- **Cloudflare** (`MapReaders::Cloudflare`) is read through Cloudflare's own server with Firefight's fixed scripts, never one a model wrote, through `execute`, the one tool that reaches the account. A connection made read only can only be read, whatever a script asks. It reads every account the connection sees. Zones are resources, and so is every hostname with an A, AAAA or CNAME record (`ResourceMap.domain`, the same identity Northflank uses, so the hostname Cloudflare points at a service and the one that service serves are one resource). Workers (their routes, custom domains and bindings), Pages sites and their domains, R2 buckets, D1 databases, KV namespaces, Queues and their consumers, Hyperdrive configurations with their origin, Tunnels and the hostnames their ingress serves, load balancers, their pools and origins, and Access applications and the hostnames they protect are resources too. A hostname is `part_of` its zone, `served_by` whatever answers for it (a CNAME target, a Worker, a Pages site, a Tunnel, a load balancer) and `protected_by` an Access application. A Worker `uses` what it is bound to. A zone's SSL mode, certificates, DNSSEC and its WAF custom, rate limiting, cache and page rule counts are read into its details, so a change to one is recorded as `configured`. Products are named by the API path segment after `/accounts/<id>` or `/zones/<id>`. `READ` and `SETTINGS` are read, `LEFT_OUT` is left out on purpose (logs and analytics, billing and account administration, Cloudflare's own lookups and catalogs), and every other product the live spec offers, listed through `search`, is named in the map's gaps as not on the map yet. `test/fixtures/files/cloudflare_api_products.txt` is the spec's product list when the reader was written, and a test fails for a product in the reader that the API does not offer. Zones are read ten to a script, with their settings, Worker routes and load balancers, and other lists a page at a time with only the fields the map needs, so a result stays under the server's size cap. An answer the server cut short keeps what it holds (the markers it leaves are dropped). A rate limit (429, Cloudflare's code 971) stops the read until the next sweep, and a script that catches its own errors still stops on one, including the products listing. The provider's `status_words` read a zone that is initializing as pending and one moved away as unavailable, and an inactive Tunnel or a disabled load balancer or pool as stopped.
- **Only a complete read takes anything away.** A reader says which kinds it could not read in full (`Snapshot#unread_kinds`), such as hostnames when a zone's DNS records were refused, or every kind after a rate limit. A snapshot with any unread kind is not `complete?`, and `ResourceMap.record!` then removes nothing at all, of any kind, and keeps every link the connection declared, since a list it missed can hold what it reports no longer (a service list cut short also holds the domains and repositories those services name). What it did read is still upserted. A gap with no kinds, such as a setting that could not be read, holds nothing back, so a connection missing one permission still has what it no longer reports removed. A gap still names the right kinds, since they tell the person what was not read. A list in each reader names everything it puts on the map: a Kubernetes service or ingress list its hostnames, a DigitalOcean app list, a Netlify, Vercel, Render or Railway list and a Northflank service list their domains and repositories, a Cloud Run list its `run.app` addresses, and an App Service or Container Apps list its hostnames. A remote reader reads a list through `RemoteReader#objects`, which takes a bare list or one under its name, and an answer in any other shape is a gap naming the list's kinds, never an empty list.
- **A resource several connections report stays while any of them does.** `sightings` keeps each connection's details by its environment row, and `details` is their union. A connection that stops reporting one removes its own sighting, and the resource is marked removed only when none is left.
- **What is defined as code.** A code host's `map_of` (daily) puts every repository the connection sees on the map, and reads the infrastructure files in them through the host's API into memory, never a checkout (`Packs::CodeHost::Infrastructure`, whose subclass per host lists a repository's files, reads one and links to it: GitHub from its git tree and blobs, GitLab from its repository tree a page at a time and each file's size from its headers before reading it, Bitbucket from its source listing). GitLab puts every project the token is a member of on the map under its namespace, and Bitbucket every repository of the workspace. A file read on one host suggests only that host's copy of the repository (`Infrastructure::File#provider`), so a mirror is never mistaken for it. What is read is Terraform and Terragrunt, Pulumi and CDK entry files (beside `Pulumi.yaml` or `cdk.json`, never the application code around them), Helm charts, Kubernetes manifests (YAML under a manifest directory that says its `kind`, and kustomizations), and Wrangler, Fly, Render, Vercel, Serverless and Netlify configs. It skips archived repositories, forks, vendored and build directories, `Secret` manifests and Pulumi stack configs, reads at most 500 files under 200 KB across 200 repositories, stops at GitHub's rate limit (`GithubApp::RateLimited`), and says in one gap per repository what it left unread. Past 1,000 repositories the listing is cut short and repositories go in `unread_kinds`. The files ride on the snapshot (`Snapshot#code_files`, with `code_read` naming the repositories read in full), and `ResourceMap::CodeDefinitions` suggests each resource named in one as `managed_by` that repository. Only values count as names (quoted strings and YAML values, never keys), with a stop list for words every config uses. A suggestion is `likely` when the resource's provider is named within ten lines (a Terraform type such as `northflank_service` counts) or, for a hostname, when the lines around it declare one (a record, route or zone), and `possible` otherwise. A generic name such as web, or one under five letters, needs its provider nearby. Each clue ends with the file's GitHub link, which the map renders as a link. Suggestions are `origin: inferred` under the connection that read the file, written under a workspace advisory lock, kept in place while they hold, removed only when a repository read in full stops naming them, never made again once dismissed or linked another way, and taken up by the next connection when theirs is removed. The Matcher only ever touches its own `uses` suggestions. `managed_by` is ownership, not a dependency, so `RUNTIME_RELATIONS` leaves it out of what fails with a resource and `Resource#neighborhood` does not walk past it. Halon reads it in `get_resource_map`, and a fix to something managed as code is a pull request to that code.
- **A link can end at another connection's resource.** `ResourceMap.record!` resolves a link whose end another connection reported in the same workspace (`present_ids`), such as a CNAME to a hostname a Northflank service serves.
- **Direction.** A link always reads "from depends on to" (`ResourceMap::RELATIONS`, worded by `RELATION_WORDS`), so what fails with a resource is everything with a path of links into it. A domain is `served_by` its service, not the other way round, because the domain goes down with the service.
- **What changed.** `ResourceMap.record!` writes a `ResourceMap::Change` for a resource that appeared or came back, one gone from its connection, a new running commit (`details.deployed_commit`, a deploy), a status that moved, a new name (`renamed`, the old and new name) and a setting that moved (`configured`, with the setting in `detail`, for the keys in `ResourceMap::CONFIGURED_DETAILS`, and only when it was read before). A rename or removal also flags what Halon remembers about the resource as possibly outdated (see docs/ai.md, Memory). Changes are facts and need no confirming. The page shows the last 24 hours and each resource's latest.
- **The catalog meets the map.** `ResourceMap::EntryLink` points a catalog entry at a resource it runs on. An incident names catalog services through its fields (`IncidentFieldValue#catalog_entry`), so `ResourceMap::View` lights up a resource with the open incidents on its entries and counts its incidents over 30 days, with no link of its own between incidents and the map.
- **People and Halon add links.** A person adds one (`ResourceMap::Link.add_by_person!`, origin person) and may remove it. A provider's link carries `removal_blocked_reason`, since it goes when the provider stops reporting it. Halon suggests one with `suggest_resource_link` and its evidence (`note`), which stays dashed until a person confirms it (`confirm!`) or dismisses it (`dismiss!`), each one guarded update, so a confirm and a dismiss cannot both land. A dismissed suggestion is kept (`dismissed_at`) and refused if suggested again, and it is left out of the map (`Link.standing`).
- **Who reads the map.** Reading it is its own resource, `map` (`Ability::Action::RESOURCE_MAP`), with only `read`, so it is grantable on the Permissions screen and the API key matrix and scoped by environment like any grant. Members hold it in every environment until a grant narrows them (see Who holds what without a grant), admins hold it everywhere, a service key or customer agent only through a grant, and Firefight's investigator through the unscoped grant `Workspace::AgentDefaults` gives it at install (and migration `GrantInvestigatorMapRead` gave every workspace before), which an admin may narrow or revoke like any other. Halon in a chat reads as the person who asked. `ResourceMap::Resource.visible_to(principal, workspace)` is the one rule, a relation of the resources principal may read: all of the workspace's for every environment, none for no reach, and otherwise those a connection row wired to one of its environments reports, by `integration_environment_id` or a sighting. A resource only a connection wired to no environment reports is read with every environment and never with a few, as a scoped grant never matches a call that names no environment. `environments_visible_to` gives the same reach as catalog entry ids (nil for every one). Every reader starts from it: `ResourceMap::View`, `get_resource_map`, a capability's lookup by name (`Capabilities.resolve` and `resolve_all` take `principal:`, and a hostname is followed to what serves it only within it) the Memory page's resource picker and the map search (Searching the map). So does every write that finds a resource by name or id: adding, confirming, dismissing and removing links and linking catalog entries on the page, `suggest_resource_link`, and a memory or instruction's subject (`Chat::Memory.subject_named` and `subject_for_key` take `principal:`). A hidden resource answers exactly as a missing one, a 404 or "nothing called", while the write's own permission is unchanged. Memories and instructions about a hidden resource are hidden too (`Chat::Memory.visible_to` and `Chat::Instruction.visible_to`, docs/ai.md, Memory and Instructions). A link is shown only when both ends are visible, so one to a resource outside is left out, never named. `Resource#neighborhood(within:)` walks only visible links, and `links_out_of_reach(within)` counts the ones it left out, which a fact sheet says in a line without names. A connection row outside the reader's environments is left out of what each sweep could not read, since a gap can name a resource.
- **The page** (`/map`, `ResourceMapController`) reads as `map: read`, and says which environments a narrowed reader sees (`readsIn`). Adding, removing, confirming and dismissing links and linking catalog entries is `catalog: update`, since it is people curating knowledge. Sync now is `integrations: update` and queues a sweep per connection. `ResourceMap::View` reads everything the page shows in a fixed number of queries, including each resource's dependents (every resource with a path of links into it), which ranks the table.
- **Settings that point at a store** (`ResourceMap::Use`, `ResourceMap::Endpoint`, tables `resource_map_uses` and `resource_map_endpoints`). A service names what it talks to in its settings, such as `DATABASE_URL=postgres://user:pw@ep-cool-river.eu-central-1.aws.neon.tech/app`. A pack reads its services' settings during its sweep, in memory only, and hands each one's name and value to `ResourceMap::Use.read(from:, workspace:, values:, names:)`. `ResourceMap::ConnectionString.parse` reads the value (URLs with a password holding `@` or `/`, IPv6 in brackets, `jdbc:`, libpq's `key=value`, the .NET `Server=tcp:host,1433;...` form, `redis://` and `rediss://`, a port taken from the scheme when missing), never raises and never echoes it, and a socket path is no address. `DB_HOST` beside `DB_PORT` (or `PGHOST` and `PGPORT`) is read as one address. What is kept is the setting's name and keyed digests (`ResourceMap::Fingerprint`, HMAC-SHA256 under a key derived from `secret_key_base` and the workspace): of the host and port, of the domain the host is one label under, of the database's name and of the tenant in the user's name (`role.tenant`, before any `|`), with the scheme and port. A value never reaches the database, a log, an error, the ledger, a snapshot's details or anything Halon reads, and `assert_no_setting_values` (test/support) fails a test whose values were kept. A setting whose value the provider hides (`names:`) is kept by name only, when the name says where something is (`URL`, `DSN`, `HOST`, `DATABASE`, `REDIS` and the like) or names a store's provider. A store's own addresses come from its provider's sweep as `ResourceMap::Endpoint.at(resource:, host:, port:, workspace:, database:, tenant:)`, `Endpoint.within(domain:, ...)` for a shared pooler whose hosts are numbered per cluster (a tenant or a database is required there), and `Endpoint.reference` with `Use.reference` for something both sides name exactly, such as a secret's ARN. The snapshot carries them as `uses` and `endpoints`. A complete read replaces the connection's rows, and a partial one only adds, so a gap with `settings: true` (`ResourceMap::Gap`), such as a settings list that was refused, keeps what was read before without holding back any resource.
- **An exact address is a fact** (`ResourceMap::HostMatcher`, run by the matcher under its lock after every sweep). One SQL join on the digests links a service to the one store whose address a setting names, as `origin: matched` with the settings in `variables` and a clue naming the setting and the store's provider ("DATABASE_URL on web names the address Neon reports for app-db"). A matched link has no connection of its own, so a sweep's `record!` leaves it, and it goes when the setting stops naming the address. Its id stays while it holds, an open suggestion for the same pair becomes the fact in place, a pair a person dismissed is never linked again, and a pair already a fact another way is left as it is. A server holding several databases names each one's database (`database:`), and the database in the setting picks it, which is still a fact. What only narrows it down is a suggestion: a host other accounts share (`shared: true`) told apart by the database's name alone (another account may have one of the same name) is `likely`, and an address two stores both report is `possible` for each. A provider that declares a reference, such as a variable that names a database, says so as a `FoundLink` with `variables`, a declared fact.
- **Firefight suggests which services use which databases** (`ResourceMap::Matcher`, after every sweep) when nothing names the address. A service or job and a database are a match when they share a project word (the service's name or its account's last segment against the database's name, generic words such as web, db, main and every environment word left out). The pairs that share a word are found in SQL, so a map of 100,000 resources is never compared whole, and each pair is judged as before. The environment sets the certainty. It is `likely` when both name the same environment, or the service names none and is assumed production. It is `possible` when the database names no environment. Different environments are no match. A setting whose name points at a store's provider (the registry's `setting_words`, such as `NEON` or `SUPABASE`) or engine (`REDIS`, `MONGO`, against a database's `engine` detail), and whose value was hidden or named no address a store reported, is a clue too: alone it is `possible`, and only when one database fits, and with a project word the pair shares it makes the suggestion `likely`. The link goes to the database's production branch when the map has one, found through its `branch_of` link and the `production` detail (`ResourceMap::PRODUCTION`). Each suggestion is `origin: inferred` with its `certainty`, `clues` (a sentence each) and the settings in `variables`. While unconfirmed it is updated in place every run, written in bulk (`Link.write_all`), so it keeps its id, and removed once the map no longer supports it. It is never made again for a pair already linked or dismissed. Every connection's sweep runs the matchers for the whole workspace, so they take one per-workspace advisory lock (`Matcher.lock!`). Ranking and what stops if something fails count facts only (`Link.facts`), and what suggestions would add is kept apart (`suggested_dependent_ids`). Firefight does not use who is connected to a database (PlanetScale's connected client names) as a clue, since a Rails app does not name its connections unless it sets `application_name`. `test/models/resource_map/scale_test.rb` runs both matchers on 100,000 resources.
- **What a resource is for, who owns it, and how its incidents ended.** Both the page and the fact sheet show, for each catalog service a resource runs, what it is for (the entry's description, `CatalogEntry#purpose`) and the teams it points at (`CatalogEntry#owning_teams`). They also show the last five incidents that named those services and ended in the last 180 days (`Incident.past_on`, never a deleted one), each with one line on how it ended (`Incident#outcome`). That line is read, never generated. It is a completed postmortem's summary, else the incident's summary, else the running summary, cut to its first sentence and 200 characters, and labelled with where it came from. The running summary is a digest of the channel, so it is used only when the workspace has transcript access on and the incident is not private. The purpose is ended as a sentence once, in `CatalogEntry#purpose`, and the 180 days reach the page as `PAST_INCIDENT_DAYS`. The fact sheet also lists what people confirmed about the resource and its services. Unconfirmed memories stay with `recall`, since they are hunches.
- **What normal looks like** (`ResourceMap::Baseline`, table `resource_map_baselines`). Once a day at 5am, `Integrations::BaselineSweepJob` queues one read per connection, so a slow provider never holds up another workspace. Each read asks the connection for a week of metrics for the resources it reported, and an observability tool's for the resources it watches (`Capabilities.watched`, the ones its observers would answer for), through `executor.baselines_of`: a pack's own, or the baseline reader a remote provider's definition names, nil by default. It keeps, per resource, connection and metric, the median, the level 95% of readings fall under, the peak, the number of readings and the window, replacing the day before. Each baseline remembers the connection that read it (`integration_environment_id`), so a platform and an observability tool reading one resource each keep their own, and one connection's read never removes another's. A reading of a resource another connection runs is labelled with the connection that read it, such as "CPU (Datadog)". A metric a connection no longer reads, on a resource it read, is removed. A baseline no sweep has renewed in two days (`Baseline.fresh`) is not shown, so a resource whose connection went away stops showing an old normal. Grafana's reader, `BaselineReaders::Grafana`, reads the same cAdvisor cpu and memory its adapter reads, every pod of a container added up, at a 15 minute step, twenty containers to a `query_prometheus` call. It reads only names that can be a Kubernetes container's, which are DNS labels, and only with `query_prometheus` on and a Prometheus datasource learned. A batch Grafana refuses keeps yesterday's baselines, and when every batch is refused Grafana's words become the connection's `baseline_error`. ClickHouse's baseline reader reads a week of `metric_log` hour by hour, one `run_select_query` per service, adding up the replicas for queries and failed queries per minute, CPU and memory, in the units the metrics capability uses. Upstash's asks `redis_get_stats` for the `7d` period, only when the connected tool reports a period that takes it, for commands per second, connections and data size. Turso keeps no metrics over time, so it has no baselines. Logfire reads requests, 4xx, 5xx and CPU in hourly buckets, five services a query, with the capability's own SQL, and SigNoz reads requests and errors per minute in hourly steps, twenty services a call. Honeycomb and Axiom answer in markdown and text, so they read none. Northflank reads requests, 4xx and 5xx responses, CPU and memory for a service and CPU, memory and disk for a database, one metrics call each. A week comes back in coarse steps, so it groups readings to Northflank's step (the most common gap between one container's readings) before adding containers up. A percentage is averaged, a disk is its fullest volume, and a count per step becomes a count per minute, so a live reading can be compared with it. A resource Northflank cannot read keeps its baselines, a 429 stops that connection's read, and a failed read is kept as the connection's `baseline_error` and shown with the map's other connection problems. AWS makes one `GetMetricData` call per resource for the week, an hour a point: CPU and memory for an ECS service, invocations, errors, duration and throttles for a Lambda function, CPU and network for an EC2 instance, and CPU, connections, freeable memory and read and write latency for an RDS database, with sums per minute. Google Cloud reads requests, 5xx responses, CPU and memory for a Cloud Run service, CPU, memory and disk for a Cloud SQL instance and CPU for a Compute Engine instance. Azure reads requests, 5xx responses and memory for an App Service or Function app, requests, CPU and memory for a Container App, CPU and storage for an Azure SQL database and CPU, memory, storage and connections for a PostgreSQL server. Both read a point an hour and keep a count as a rate per minute. A connection whose only trouble is its baselines is listed with the map's connection problems too, and a read that finds nothing to read, such as a reader whose tool was switched off, clears an earlier error. New Relic (`BaselineReaders::Newrelic`) reads throughput, error rate and response time for each service it watches by its APM name, an hour at a time over the week, in one NRQL query a service. An hour with no transactions counts for throughput but not for a rate or an average, and a service New Relic never saw gets no baselines from it. The page shows them under Normal, over the last week, once a resource has any, and the fact sheet under `normal`, so Halon and the scheduled checks can tell an unusual reading from an ordinary one. Neon, Supabase and PlanetScale offer no metrics over time through their servers' tools, and a database reached by URL keeps only running totals, so none of them has baselines. A code host keeps no metrics, so its repositories have none, and CircleCI's hosted server has no metrics tool either.
- **Reading it.** `get_resource_map` (docs/mcp.md) gives the whole map or one resource's fact sheet with everything within two links, so Halon and outside agents start from what is known rather than listing each provider again. From 300 visible resources it gives the map's numbers instead of a list. `find_resources`, `get_resource`, `get_resource_links`, `get_resource_neighbours`, `traverse_resource_map`, `blast_radius` and `resource_map_stats` read a map of any size through the four models below, each within what the caller may read. They sit in the agent's own map group, and a provider's skill may name `get_resource_map` too. Halon locates a resource here before asking a person or using a provider's own tools (docs/ai.md, Look before asking).
- **Finding things on a large map.** A workspace's map is read at the size of 100,000 resources through four models, each taking an optional `within:` relation of the resources a reader may see, so nothing outside it is listed, counted or walked through. A reader passes `ResourceMap::Resource.visible_to(principal, workspace)` (Who reads the map), and with it `Stats` also keeps its connections to rows that report a visible resource and its changes and suggestions to visible ones. `ResourceMap::Query` filters by provider, kind, account, environment (the name of the environment the reporting connection is wired to), status, health (read off the status the way `Resource#health` reads it), owner (a team catalog entry: resources linked to the team or to an entry that names it as an owner), catalog entry, tag, an exact match on details (`details @>`), changed since and a name prefix, leaving removed resources out unless asked. It pages by keyset with an opaque cursor, in name order or by direct dependents (fact links into a resource, along `RUNTIME_RELATIONS`, from present resources), and counts exactly up to 10,000, then says "10,000+". `ResourceMap::Graph` walks the links in one recursive query, towards dependents or along what a resource depends on, through present resources only, facts only unless suggestions are asked for, along `RUNTIME_RELATIONS` unless relations are named, ending at a `managed_by` link as `Resource#neighborhood` does. Its rows are deduplicated by resource and hop, so a cycle or a diamond costs at most a row per resource per hop rather than one per path, and a hop limit (at most 25) and a node limit (with the number left out) bound it. `ResourceMap::BlastRadius` is what fails with a resource: the same dependents `ResourceMap::View` counts, by kind, provider and environment, the catalog services they and the resource run with their owning teams and open incidents, the dependents ranked by their own direct dependents, and what unconfirmed suggestions would add, kept apart. `ResourceMap::Stats` counts by provider, kind, account, environment, status or health under any of the Query's filters, and gives each connection's last sweep, error and gaps, the suggestions waiting on a person and the last day's changes. Partial indexes on present resources serve each filter and the name order (`lower(name) COLLATE "C"`, so one index answers a prefix and the paging), a `jsonb_path_ops` index serves tags and details, and partial indexes on standing links serve the walk. `test/models/resource_map/scale_test.rb` checks the plans against 100,000 resources.
- **Search rows.** What a person or Halon finds by its words lives in `search_documents`, one row per resource on the map or catalog entry, never a memory (its text is encrypted, so memories are matched when searched, docs/ai.md). A row holds a title, a `tsvector` built with the `simple` configuration so an id such as `payments-db-2` is kept as written rather than stemmed, the names, ids and account as `trigram_text` for matching a fragment (`pg_trgm`), `facets` (kind, provider and environments, or the catalog type, plus the lowercased names an exact match is checked against) and a digest. `SearchDocument::Indexing` is what a record says: `ResourceMap::Resource::Searchable` its name and provider id (weight A), its account, the string values of its details, its tags as `key=value` and each half, the catalog entries it runs and their owning teams (B), and its kind and provider (C), and `CatalogEntry::Searchable` its name and slug, what it is for, its text, select and list attributes, its owning teams and its type. `SearchDocument.index!` writes a batch in one statement and leaves a row whose digest matches untouched, `updated_at` included, and drops the row of a record that is gone or archived. A removed resource keeps its row, and a search leaves it out as `ResourceMap::Query` does. **A sweep never writes a row per resource.** `ResourceMap.record!` returns the ids whose searched columns changed (`SEARCHED_COLUMNS`, or reported no longer) and `MapSweep.run!` queues one `SearchDocumentIndexJob` with them, none when nothing changed. A catalog entry indexes its own row as it is saved, then queues the resources linked to it, and on a rename or an archive every row still holding the old name (`SearchDocument.naming`, its phrase or an environment of that name), such as a service it owned. Linking or unlinking a resource and a service, rewiring a connection row to another environment and archiving a catalog type queue the rows they change. `SearchDocumentBackfillJob` runs hourly and indexes whatever has no row yet, such as everything from before search, and embeds each catalog entry it indexes once.
- **Searching the map.** `SearchDocument.search(workspace, query, principal:, types:, filters:, limit:, cursor:, meaning:)` (`SearchDocument::Search`) is the one search, called by `search_map` (docs/mcp.md) and the dashboard's `GET /search` through `MapSearchService`, which supplies `meaning` as a call for the query's vector. It ranks five lists of at most 200 each and merges them. An exact name, provider id, slug or account (`facets -> 'names'`) always comes first. The rest is reciprocal rank fusion (k 60) of each word or the start of one (`to_tsquery('simple', 'word':* | ...)`, ranked by `ts_rank_cd` so a name outranks a description), a fragment or misspelling of a name, id or account (`word_similarity` over `trigram_text`, the `<%` operator), a catalog entry whose description reads like the query (`SearchEmbedding.nearest`, similarity at least `MEANING_FLOOR`, 0.2, measured for the default model by `test/models/search_document/meaning_floor_test.rb`, which calls the model and runs only with `LIVE_EMBEDDINGS=1` and a key) and a confirmed memory holding the words (`Chat::Memory.matching`, in Ruby, docs/ai.md). Stop words are dropped unless nothing else was asked. **Every result is within the reader's reach.** Resources come from `ResourceMap::Query.new(workspace, within: ResourceMap::Resource.visible_to(principal, workspace), **filters).scope`, so the `find_resources` filters narrow them and a removed resource is left out, catalog entries only with `catalog: read`, memories only through `Chat::Memory.visible_to` with `memory: read` while Halon is available. A type the reader may not read is named in `left_out` rather than searched. Each result says why it matched from the fields that hold the words (`SearchDocument::Indexing#search_document_matched`) and opens on the dashboard (`Result#path`): a resource on the map in Focus (`?view=focus&resource=<id>`, `ResourceMap::PAGE_VIEW_PARAM`, `PAGE_RESOURCE_PARAM`), a catalog entry open in its type (`?entry=<id>`, `CatalogEntry::QUERY_PARAM`), a memory marked on the Memory page (`?memory=<id>`, `Chat::Memory::QUERY_PARAM`). Paging is an offset into the merged ranking, in a cursor tied to the query, types and filters.
- **Tags.** A provider's own tags or labels go in `details["tags"]` (`ResourceMap::TAGS`) as a hash, never under `DETAIL_LABELS`, so they are for finding a resource rather than shown on it. AWS keeps an EC2 instance's tags and an RDS instance's `TagList`, which their lists return, an ECS service's tags by asking `DescribeServices` to include them, and a Lambda function's through one `ListTags` call each, which only the map's sweep makes. A key whose policy refuses either still puts every service and function on the map without tags, with a gap naming no kind, since nothing was held back, so what is gone is still taken away. Being asked to slow down while reading tags stops the read like any list. The connect form's hint names `ecs:ListTagsForResource` and `lambda:ListTags`. Google Cloud keeps a Cloud Run service's and a Compute Engine instance's `labels`, a Cloud SQL instance's `settings.userLabels` and a GKE cluster's `resourceLabels`. Azure keeps every resource's `tags`, Kubernetes each object's `metadata.labels`, and DigitalOcean a Droplet's and a database's tags, which carry no value, as keys alone. A tag filter is `key=value` or a key alone.
- **Kubernetes** puts each connected namespace on the map under the account `<API server host>/<namespace>`, each resource with the id `namespace/kind/name`. Deployments, statefulsets and daemonsets are services. Cronjobs, and jobs no cronjob owns, are jobs. Services and ingresses are load balancers, with their Kubernetes type in `type`. A workload's state is one of Kubernetes' own words (`state_of`), which the provider definition's `status_words` reads as Firefight's: scaled down is stopped, progressing is deploying, a cronjob that is scheduled is ready, a rollout that finished with too few pods ready is degraded (pods that crash after a Deployment's Progressing condition says NewReplicaSetAvailable, a StatefulSet on its update revision or a DaemonSet fully updated), so it reads failing rather than busy, a finished job completed, a suspended cronjob paused. A service is active, or pending while a LoadBalancer waits for its address, and an ingress is active. A service is served by each workload in its namespace whose pod template labels hold its selector. An ingress is served by the services its rules and default backend name. A hostname in an ingress rule is served by that ingress (wildcards are left out), and a load balancer's hostname by its service. A list the service account may not read, or an API the cluster does not serve, is a gap and its kind goes in `unread_kinds`. A list cut short at ten pages of 500 (`Integrations::Pages`) is a gap too. Any other failure, such as an expired token, fails the sweep.
- **AWS** (the pack's `map_of`) puts each connected region's ECS services (`service`), Lambda functions (`function`), EC2 instances other than terminated ones (`virtual_machine`) and RDS database instances (`database`) on the map, under the account `GetCallerIdentity` names. Each has its ARN as its id, its state and its console page. `DescribeInstances` returns no ARN, so an instance's is written in the form AWS's service authorization reference gives. An ECS service's state is its primary deployment's rollout state, and degraded when that rollout completed but the service runs fewer tasks than it wants, since COMPLETED stays after its tasks start failing. A list AWS refuses, or one past ten pages, is a gap naming its kind, and a throttle stops the read with a gap naming every kind. The provider's `status_words` map RDS's instance statuses, EC2's and Lambda's states and an ECS service's DRAINING and INACTIVE onto Firefight's words, so every kind reads a known health.
- **Google Cloud** puts the project's Cloud Run services and the `run.app` addresses they serve, Cloud SQL instances, Compute Engine instances (`virtual_machine`) and GKE clusters (`cluster`) on the map. A product the key cannot read, or whose API is off in the project, is a gap and its kind is unread, and a Cloud Run list's gap also holds back its `run.app` addresses. A zone Compute Engine marks unreachable (`unreachables`, or a scope's UNREACHABLE warning) or GKE names in `missingZones` is a gap naming the zone, and the machines or clusters there are not taken as gone. A Cloud SQL instance whose activation policy is NEVER reads stopped, since a stopped instance still reports RUNNABLE. A cluster's workloads stay off the map. The GKE API gives clusters and node pools, a workload needs the Kubernetes API, and Cloud Asset Inventory, which lists them, syncs only every few hours.
- **Azure** puts the subscription's App Service and Function apps and Container Apps with the hostnames they serve (never the `scm` ones), Azure SQL databases and PostgreSQL flexible servers on the map. A list the principal cannot read is a gap and its kind is unread, and an app list's gap also holds back the hostnames apps serve. A server still provisioning reads pending.
- **Neon** (`Integrations::MapReaders::Neon`) puts every project it reaches on the map as a database (Postgres version and region), through `list_organizations` (each organization's projects are listed by its id, and without the list `list_projects` picks the account's own), `list_projects`, `list_branches`, `list_postgres_endpoints` and `list_postgres_databases`. Each branch is `branch_of` its project, with whether it is the default (`production`), and the Postgres databases on it in its details. Each compute is a `compute`, and the branch it serves is `served_by` it, since a branch is unreachable when its computes are. A disabled compute reads disabled. Databases are read for the default branch and the latest others, 25 in all, and the rest is a gap. Pages are the console's, as Neon's server writes them (`console.neon.tech/app/projects/<id>` and `/branches/<id>`).
- **Supabase** (`Integrations::MapReaders::Supabase`) puts every project on the map as a database, named by its ref, with its status, Postgres version and region, through `list_projects`, and each branch, a project of its own, as a branch of it with whether it is the default and its git branch, through `list_branches`. A connection scoped to one project by its `project_ref` field has no account tools, so the reader puts that project on the map by its ref, with its branches, and says so in a gap. Both readers, and PlanetScale's, list through `RemoteReader#listing` and read the answer through `RemoteReader#objects`, and every gap names the kinds it held back: a project list Neon refuses, or its project cap, holds back databases, branches and computes, a project's branch list its branches and computes, and Supabase's project list its databases and branches, so the sweep takes none of them as gone. A Neon project has no state of its own and reads ready once listed. Each provider maps its own status words onto Firefight's in its definition (`status_words`): Neon's idle compute and archived branch are sleeping (Neon archives a branch nobody has used and wakes it when it is used), a disabled compute stopped, Supabase's ACTIVE_HEALTHY healthy and INACTIVE paused, PlanetScale's awakening starting. A database reached by its URL reads running once the sweep has connected to it. Pages are the dashboard's, `supabase.com/dashboard/project/<ref>`.
- **PostgreSQL** puts the one database its URL reaches on the map (`Packs::Postgres#map_of`), named by host, port and database name, with its version and whether it is a primary or a replica. Nothing of the URL's credentials is kept.
- **CircleCI** holds no infrastructure of its own (`map: none`), since it builds what a code host puts on the map, and its hosted server lists no projects.
- **PlanetScale** (`Integrations::MapReaders::Planetscale`) puts every organization's databases (engine, plan, region) and their branches on the map, each branch linked to its database, through `planetscale_list_organizations`, `planetscale_list_databases` and `planetscale_list_branches`, 100 a page and at most 10 pages each. A list PlanetScale refuses is a gap.
- **Tinybird** (the pack's `map_of`) puts the workspace on the map as a database, under the workspace's id as its account, each data source as a database `part_of` it with its engine, and each pipe published as an endpoint as a function `part_of` it that `uses` the data sources its nodes read (the Pipes API's `dependencies`). Their `type` (Workspace, Data source, API endpoint) tells them apart. Each status is the last hour of a service data source: an endpoint is failed when every request failed, degraded when any answered a 5xx, ready when none came and healthy otherwise, a data source failed, degraded, healthy or ready the same way from its operations, and the workspace deploying while a deployment job waits or works, running otherwise. A 4xx alone degrades nothing, since it is the caller's mistake. A list Tinybird refuses is a gap naming its kind, and a service data source it refuses a gap that leaves every status unknown. Other pipes (copies, sinks and materializations) stay off the map. Baselines are requests and failed requests per minute, for each endpoint and the workspace, read hour by hour from `tinybird.pipe_stats_rt` in one query, an hour with none read as zero since Tinybird records every request.
- **ClickHouse, Turso and Upstash.** ClickHouse's reader puts every organization's services on the map as databases through `get_organizations` and `get_services_list`, with the Cloud API's `Service` fields, and the organization's id as the account that status needs. Turso's puts the databases its connection's organization or group holds on the map through `list_databases`, a database branched from another as a branch of it, with blocked reads or writes in its status. Upstash's puts its Redis databases on the map through `redis_list_databases`, and the QStash of each region through `qstash_list_users` with `region` us and eu, as a queue named QStash us or QStash eu. A tool switched off, a refusal or an answer in a shape the reader does not know is a gap naming the kinds that list holds, so none of them is taken as gone. Each definition maps its provider's own states onto Firefight's words: ClickHouse's idle reads as sleeping, awaking as starting, provisioning, stopping, terminating and softdeleting as pending, terminated and softdeleted as stopped, and partially_running as degraded. Turso's blocked reads or writes read as unavailable, and Upstash's suspended or inactive as stopped.

## Connecting from a chat

The agent never connects anything. `list_integrations` says what a category holds, and the dashboard chat draws it as a card (`pages/agent/components/integration-card.tsx`) whose Connect button opens the same `ConnectDialog` the Integrations page uses, moved to `components/integrations/` so both pages share it. Where a provider stands (connected, needs attention, turned off, not connected), its label, and what a row offers (connect, reconnect or manage) are decided once, on `IntegrationProvider::Row`, from the workspace's rows and their health. The page and the Slack list both read them and decide nothing. A category's key is `IntegrationProvider.category_slug`, the same key the agent's tool groups use.

- **Back to the chat.** The dialog passes `return_to`, which `create`, `oauth_start` and the callbacks carry through the session and honour only when it is a chat on this dashboard (`safe_return_to`), so a crafted link cannot send someone elsewhere. The chat gets a toast saying the connection is made. From the Integrations page nothing changes.
- **A link that opens the dialog.** `/integrations?connect=<provider key>` (`Integration::CONNECT_QUERY_PARAM`) opens that provider's dialog on arrival, for whoever may manage integrations. The page reads both links from its address, the way the runbook sheet does. The Slack card's buttons use it, since OAuth cannot happen in Slack.
- **A connection's details have an address.** `/integrations?integration=<id>` (`Integration::DETAILS_QUERY_PARAM`) opens that connection's details sheet, and opening or closing the sheet rewrites the address, so it can be shared. The card's Manage link uses it, and names each connection when a provider backs several.
- **The rows are read fresh.** The chat page loads every category's rows on each visit (`integrationCards`), so coming back from connecting shows it connected without the agent being asked again.

## Credentials

- `Integrations::OauthClient` owns the credential shape: `exchange` produces it, `refresh` consumes and reproduces it, `stale?` reads its expiry. **Nothing else indexes into it.**
- `IntegrationEnvironment` owns persistence (`oauth`, `store_oauth!`, `rotate_oauth!`).
- `Integrations::Credentials` builds outbound headers and rotates expiring tokens before use.
- **Secrets never enter the session, an MCP tool response, or the ledger.** Alert-source tokens and OAuth client secrets are read server-side at the moment they are needed; connection UIs link to the settings page rather than returning a secret.

## OAuth

- **Nothing is persisted until the customer returns authorized.** Abandoning the provider's screen must leave no half-connected row.
- State is verified with a constant-time compare and every MCP flow runs PKCE. A pre-registered app (`_CLIENT_ID` / `_CLIENT_SECRET`) adds the client secret to the exchange but does not replace PKCE.
- Install-first connect (the provider's app install screen, `_APP_SLUG`) belongs to native packs only; see the Native packs section. The MCP client never builds an install URL.
- Discovery follows RFC 9728 then RFC 8414, trying the path-inserted, issuer-suffix, and OIDC metadata locations. Dynamic client registration is used when the server offers it.
- Requested scopes come from the resource metadata's `scopes_supported`. **Do not add a per-provider scope list to work around a provider that omits it.** Providers fronting their own hosted MCP server (PlanetScale) hold a fixed app scope set and ignore the `scope` parameter outright; the customer narrows access by picking organizations and databases on the consent screen, and an unticked organization is what a `forbidden` on an org-scoped call usually means. A scope list we cannot enforce reads as a least-privilege guarantee we do not have.

## Ledger

`Ability::Invocation` is written **before** execution and finalized exactly once.

- Denials: always recorded
- Allowed writes and destructive calls: always
- Allowed **tool** calls, reads included: always. Crossing into another system is the question an audit asks
- Allowed system reads: never, they run at request volume and the request log covers them
- `completed_at` nil means attempted with unknown outcome, the crash signal
- A call that raised is an `error` with the exception's class. A call that ran but answered with its own error is an `error` too. That is a provider's `isError`, or an error response from one of Firefight's own tools. Its summary is `Ability::Invocation.summary_of`, the first line it said with credentials redacted by `Chat::SecretFree.redacted`, at most 200 characters. The gateway hands its block the `Authorization`, the caller marks the answer with `answer_failed!`, and `finalize_answered!` writes it. Chats, investigations, MCP and fix steps write it this way, for Firefight's tools, connection tools and capabilities alike. The map sweep and the health check write the same summary from `Integration::Tool#recorded!`
- Identity is stored as values (labels), never join-dependent, so rows outlive their principals
- **No result bodies.** Outcome, error summary, and duration only

## Approvals

- `Policy::DOMAIN_APPROVALS` on the existing rule engine, matched over `{action_key, risk_level, reversible, environment, severity}`. Nothing sets `severity` in the context yet, so a rule on it never matches.
- One workspace-wide policy (`Workspace#approval_policy`), created by the first rule (`find_or_create_approval_policy!`). No policy means nothing waits, which is the default.
- Rules are written from Gateway → Permissions (`ApprovalRulesController`). The dialog asks three questions (abilities, risk levels, environments) and `PolicyRule::ApprovalConditions` turns them into `is_one_of` conditions, so the engine stays generic. Environment values are catalog-entry ids, matching grant scopes.
- Outcome contract (`PolicyRule::ApprovalOutcome`): `require: { role, count: 1, self_approval, notify, approvers, agents_may_approve }`. `approvers` is a list of `{ kind, id }` principal references (`Ability::Principal.reference`, a bare string is a person) validated against the policy's workspace. When present it replaces the role for deciding (`Ability::Approval#approver?`), and the role only describes the request. A role is only ever held by a person. A machine (agent or service key) can be named, and decides only when `agents_may_approve` is true, which the validator enforces at write time and `approver?` again at click time. `approver` on the approval is polymorphic for the same reason.
- `notify` is `channel` (incidents channel, the default), `dm` (each approver, named or everyone holding the role), or `both`. `ApprovalNotificationService.post!` fans out and records every posted message on `approval.notifications`, and `mark_resolved!` rewrites each one.
- Bound to a digest of action, params, and scope, so an approval admits exactly one call and is single-use
- Resuming re-enters `authorize!`: grants and config are re-checked against current state, only the policy match is skipped
- `approvals.*` and `permissions.*` are exempt from policy matching (`Ability::Action.approval_exempt?`): resolving an approval would otherwise need an approval, and a rule that held the Permissions screen could lock admins out of removing it
- Self-approval is allowed by default (a human confirming their own agent's proposal is the safety mechanism). Opt into four-eyes per rule with `require.self_approval: false`

## MCP exposure

- Read and config-write tools declare `authorize_as <resource>, <action>`; upserts override `authorization(workspace, args)` with a **side-effect-free** probe so create and update authorize differently
- Connection tools are published outward by `Mcp::ConnectionToolFactory`, so the same registry serves inbound and outbound
- Capabilities are published by `Mcp::CapabilityToolFactory`, each routed to the provider tool that holds the resource and authorized as that tool's action
- `approval_id` rides **outside** the digested params, so an approved retry hashes identically to the original request
- Incident lifecycle writes stay out of MCP until they carry the full approval UX
