# Operator console

`/operator` is for the people who run a Firefight install, not for a workspace. It holds the overview, the incident process, workflows, the jobs dashboard, and Halon's runs, health, traces and chats. Its pages share `OperatorLayout` (`pages/operator/components/`), a layout with no workspace selector, since an operator sees all workspaces. `/operator` opens on the overview.

## Boundary

The console is self-contained, so it can be replaced or removed without changing app code.

- **Everything is under `Operator`**: controllers in `app/controllers/operator/`, models in `app/models/operator/` (including `Operator::Credential` and `Operator::WorkflowRuns`), serializers in `app/serializers/operator/`, pages in `app/frontend/pages/operator/`.
- **The app never references it.** ArchSpec (`Archspec.rb`) makes the operator files their own components, lets only them name `Operator`, and forbids every other component from using them. The same layer rules as the app's controllers, models and serializers apply to them.
- **Dependencies point one way.** The console reads app models, the ability ledger and the SolidWorkflow tables. `User` has no association to the credential, and the database deletes a user's credential with the user.
- **Shared files hold one line each**: the route block in `config/routes.rb`, the Flightdeck base controller in `config/initializers/flightdeck.rb`, and `Operator::TypescriptConstants` in `lib/tasks/typescript_constants.rake`, which writes the console's own `app/frontend/pages/operator/generated/constants.ts` next to the app's, so the app's constants never name the console.
- **What the app records for everyone** and the console reads: `PlatformCallFailure`, `CodeBox` (where a box ran, its size, price and time, and its failover), `ProviderSandbox` and `SandboxProviderRead` (what each provider holds, and who each box says it was started for), `Workspace#sandbox_provider`, `SandboxProviders`, `investigations.answer_posted_at`, `inferences.prompt_version`, `inferences.error_kind`, `AiAccount`, `Chat::SkillProblem`, `Investigation::RegressionRun`, `Conversation::BenchRun`. They name nothing in the console.
- **Actions have one guard each** in `Operator::Actions`, a sentence saying why not or nil. Controllers refuse with it and serializers ship it, so a page shows a button only when the server would accept it.

## Who gets in

- **An operator is a user id in `OPERATOR_USER_IDS`**, comma separated, read on every request (`Operator::Credential.operator?`). It is deploy config, so nothing a workspace can edit makes someone an operator. A user id rather than an email, since an email is only as good as whichever sign-in method last vouched for it.
- **Anyone else gets the app's own not found page**, signed in or not, on every console address including the jobs dashboard (`Operator::BaseController#require_operator!`). The console does not reveal it exists. Flightdeck serves its own stylesheet, script and fonts without a check, by design, so an asset address can show that it is mounted, and nothing more.
- **Then an authenticator code**, asked for again every `Operator::Credential::VERIFIED_FOR` (12 hours) in a session, so a taken-over sign-in alone opens nothing. Any TOTP app works.

## The second factor

`Operator::Credential` (table `operator_credentials`), one row per operator:

- **Setup** at `/operator/setup` shows a QR code (drawn by the page from the squares `rqrcode` returns, so no markup crosses to the browser) and the key in groups of four. The secret is created once and kept until the first code confirms it, so a mistyped code does not mean scanning again. It is encrypted.
- **Recovery codes**: ten, each working once, handed back once when setup is confirmed and rendered rather than redirected with, so they sit in no address, flash or log. Only an HMAC of each is stored.
- **A code works once.** The step it belongs to is claimed with one guarded `update_all`, so the same code cannot open two sessions, even from two requests at once. A code from the step before is taken, for clock drift.
- **Five wrong answers lock the factor for 15 minutes**, counted on the row so the lock holds across every process. A lock that has run out starts the count again. Rails' `rate_limit` is not used, since its count lives in the cache, which is off in tests and can be split per process.
- **After a correct code** the browser loads the next screen whole (`inertia_location`), since Flightdeck is not an Inertia page.
- **A lost phone and lost recovery codes**: `bin/rails 'operator:reset_authenticator[USER_ID]'` removes the row, and the next visit sets up anew.

## Find

The box at the top of the sidebar takes anything with an id (`Operator::Finder`): an incident, a Halon run or chat, or a workflow, and the records inside them that lead back to one (a saved chat, a model call from the inference ledger or a chat's usage row, a tool call's step or its ledger entry, a chat message, a webhook delivery). The start of an id works from 6 characters, so an id cut short in a log still finds its record. A trace row's key, as the `span` in a trace's address shows it (`model-<id>`), opens that trace at that row. An incident number such as `INC-042` is matched in every workspace, since each counts its own. One match opens the record, and several are listed with where each lives and which id found it. Matching casts each table's id to text through Arel (`Finder.id_starts`), which `WorkflowRuns.starting_with` shares for the engine's table.

## Window and workspace

The overview, Halon and chats read one window (the last 24 hours, 7 days or 30 days) across every workspace or one, from the query string (`Operator::Filter`). The window is open ended, so nothing written while the page loads is missed. The last day is charted by the hour, anything longer by the day. Figures that are not per workspace, the job queue, say so.

## Overview

`/operator` puts what needs a person first, then each process in numbers.

- **Needs attention** (`Operator::Attention`) is failures in the window and anything backed up or stuck now: failed and stuck workflows, failing webhook deliveries (one item per webhook), failed Slack calls (one item per workspace, call, error and channel, with a count), alerts stuck in routing, backed up queues and failed jobs, Halon runs that failed on our side, reached their budget or turn limit, finished without their last post reaching the thread, or have no worker, provider skills naming tools their provider no longer offers (`Chat::SkillProblem`, one item per skill, for the whole install only, since skills are not per workspace), AI accounts out of credit or running short, code sandboxes that failed over to the backup provider (one item per workspace and refusing provider, with a count and the latest reason, a warning since the run went on, opening the workspace's page), and from the Sandboxes page boxes and copies with no record (one item per provider), boxes that failed or are stuck, and providers that could not be read. An AI account is the deployment's key for one model provider, so these are for the whole install only too, one item per provider. It is **out of credit** while its `AiAccount` row says so (docs/ai.md, Output budgets and credit): from the first call refused for good until a call answers or the hourly balance check shows credit, and the item gives when it ran out and how many calls were refused since. A refusal posts an alert to the team webhook, always when the account first runs out and then at most once every four hours while it stays out, and so does the hourly check when the account runs low, at most once every four hours and never within four hours of another alert (docs/ai.md, Alerting the team). A provider refused for credit in the window that has credit now is **short of credit**, a warning, since someone added credit. A provider the deployment calls whose balance cannot be read, because the key that reads it is not set (`OPENROUTER_MANAGEMENT_KEY` for OpenRouter), is **AI balance not checked**, a warning that stays until the key is set, since without it no low balance alert is sent and a refilled account reads as out until a call answers.
- **Panels** (`Operator::Overview`) count incidents, workflows, jobs and Halon for the window.
- **The job queue** is read by `Operator::JobHealth` from Solid Queue's own tables. It returns nil when they are not there, as in tests, so the page says the queue could not be read rather than failing. It checks the table exists before querying, since a failed query would abort the transaction a caller is in.

## Halon

- **Runs and health** at `/operator/halon` (`Operator::HalonHealth`): runs and chat turns, how many answered, median and p90 time, spend from the inference ledger (runs, their citation re-read and chat turns), and the team's verdicts. A chart of runs by how they ended, and why the rest did not answer. Tools from the invocation ledger, with failed calls, calls one of Firefight's own rules refused, denied calls and median time. Model calls with their error classes. The run prompt's latest wordings, each with how the runs it started went, over all time so an older wording is there to compare, and its text. Then the runs, filtered by how they ended. Rehearsals are never counted, their model calls included.
- **How a run ended** (`Operator::HalonRuns`): answered, stopped (a limit it reached, said to the thread in `PLAIN_STOP_REASONS`, or a person), failed (anything else, a cause on our side), or working. A failure is shown with the technical cause in `error_summary`, which only operators see.
- **A run's trace** at `/operator/halon/runs/:id` (`Operator::RunTrace`) draws every record the run left on one clock: the job claiming it, the facts it started from, each model call (from the inference ledger, placed by its latency, with its reply), each tool call (with the gateway's decision, who it ran as, its scope, time and ledger id), theories, the critique, the answer or why it stopped, the thread opening and the last post (or that it was not posted), failed Slack calls in its channel, and verdicts, which come later and do not stretch the clock. A legend says a bar took time and a diamond is a moment, and what each colour means, and hovering a mark gives when it started and how long it took. The gateway ledgers every call that leaves Firefight and every refusal, but not a read of Firefight's own data, and a refused call never reaches the step that would hold its row, so a step without a ledger row is named by what it was (a read of our own data, denied, or replayed when the run is a replay).
- **Regression** at `/operator/halon/regression` (`Operator::HalonRegression`): the regression runs (docs/ai.md, The regression set), each with why it started, its prompt version and model, and how many cases passed, failed or could not finish, then how many rated answers there are and how many workspaces opted in. Run asks for a model, Halon's own by default, from the priced registry, loaded as the optional `models` prop when the picker opens. A run's page lists a case that passed in the run before on the same model and fails now first, then the other failures, with the rated answer, the replay's answer, the grader's reason and links to both traces.
- **Bench** at `/operator/halon/bench` (`Operator::HalonBench`): the chat bench's runs (docs/ai.md, The chat bench), each with why it started (an operator, the terminal or CI, with its label), its prompt version and model, its total and the mean of each of the four scores, and what it spent. Real chats replayed from the terminal are not listed, since they hold customer data. Run asks for a model the same way as Regression (`ModelRunDialog`), one run at a time (`Operator::Actions.bench_blocked_reason`). Ticking two runs and pressing Compare opens `/operator/halon/bench/compare?base=&head=`, the older as the base: the change in the total and each score over the scenarios both scored, whether it dropped by more than the noise (and that a drop between two models says how the models differ), and every scenario's total on both sides, the biggest drop first. A run's page lists the scenario that dropped most since the run before on the same model first, with its scores, what took marks away, the judge's reason and Halon's answer folded, and links to compare with that run. Find leads a bench run's id, and anything in a scenario's replay, to its run, and a real chat's replay to the chat it replayed.
- **Chats** at `/operator/halon/chats`, and one chat's trace (`Operator::ChatTrace`), each turn on its own clock from what the person asked. A chat's ledger rows name its incident rather than the chat, so its model calls come from RubyLLM's usage rows and its tool calls from its saved tool calls. A tool result is saved as the tool starts and filled in when it answers, so a tool call runs from the result's `created_at` to its `updated_at`, and a model call starts when the message before it was last written. The latest 20 turns are drawn.
- **Span content is read one span at a time.** The trace carries no tool output, model reply or question, only whether a span has one. Opening a span asks for the optional `spanBody` prop with `span` in the query string, so the address says which span is open. Content past 100,000 characters is cut and says so. It is the customer's data, and the page says so beside it.

## Workspaces

`/operator/workspaces` lists every workspace by name with where its code sandboxes run, and how many boxes started, what they cost and how many failed over in the window (`Operator::WorkspaceSandbox.rows`, one grouped query over `code_boxes`). One workspace's page (`Operator::WorkspaceSandbox`) shows:

- **Where its code sandboxes run**, a choice between following the deployment (`SANDBOX_PROVIDER`, then `SANDBOX_BACKUP_PROVIDER`) and holding it to one provider (`Workspace#sandbox_provider`). Save posts to `sandbox`, refused with `Operator::Actions.sandbox_placement_blocked_reason` (the workspace's own `sandbox_provider_blocked_reason`), and says what changed in a toast. It is set only here, since it is a fact about the deployment's providers and not a workspace setting.
- **Failovers**: each box that started on the backup, when, which provider refused it, where it ran instead and the refusal in the provider's words.
- **Code fixes**: each `CodeAgentSession` in the window with its AI cost (`spent_micros`) and its sandbox cost and time, the boxes with the session's `box_key` that were up while it ran (`CodeBox#cost_micros`, a box's price by the hour times the seconds it ran). A box with no price, such as Docker on the deployment's own machines, shows no cost rather than nothing spent.

## Sandboxes

`/operator/sandboxes` shows every code sandbox and kept copy each provider holds, set against what the app recorded (`Operator::Sandboxes`).

- **Where the provider side comes from.** `CodeBoxSweepJob` (every 10 minutes) ends with `Integrations::SandboxInventory.record!`, which asks every provider in use for its `inventory` through the sandbox provider contract (each box and kept copy named or labelled as Firefight's, any state, with the state also in `ProviderSandbox::PHASES`) and writes it to `ProviderSandbox`, marking what a provider stopped reporting as gone. Each provider's last read and why it failed is `SandboxProviderRead`, shown as a banner and under Needs attention, so a provider that cannot be read never looks empty. Northflank lists only services named like a box, so the app's own services in a shared project are never listed.
- **Flags.** No record: a provider holds a starting or running box, or a prepared copy, that no live `CodeBox` or `PreparedCopy` names, seen for more than 15 minutes (the app writes its row once the box answers). Overdue: a recorded box unused for `CodeBox::ABANDONED_AFTER` or alive past 6 hours, or a stopped box a provider still keeps after 2 hours. Failed: the provider says so. Stuck: starting or stopping for more than 15 minutes. Gone at provider: a live row whose box a successful read no longer finds.
- **Each box** shows its provider, size, state, age, last use, workspace, what holds it (an investigation, a chat or a code fix, linked) and its cost so far at its recorded price. Its address and key never reach the page.
- **Kept copies**: prepared repositories (on a provider, or as an archive in Firefight's storage) and copies of the sandbox image, with size, last use and storage cost. boat keeps an account's 10 newest named snapshots free, so a copy of Firefight's beyond them carries $1.70 a month.
- **Totals**: running now per provider, cost today and this month (boxes started in the period at their price, plus kept copies' storage for the days so far), failovers and boxes with no record.
- **Last 24 hours**: one lane per provider, a bar per box from its start to its stop or now, red for no record or failed, amber for overdue or stuck.
- **Actions**, each asked first, said in a toast and recorded as an `Operator::SandboxAction` under the operator's email: Stop (a running box), Delete (a box or a kept copy, for good), Adopt (a box with no record that can be matched, below) and Clean up rogue (deletes every box and copy with no record, adoptable or not). They go through `Integrations::SandboxInventory`, which closes the app's row first, or opens one for Adopt. Guards are in `Operator::Actions`.
- **Adopt.** Every box is started with its owner, the workspace id and the run's box key (`Sandboxes::Owner`), written where its provider keeps such things: Docker labels (`firefight.workspace`, `firefight.box-key`), the Northflank service's description, and the boat sandbox's name (`halon-box-<workspace>-<key>`, left as the plain name when it would pass boat's 120 characters). The inventory reads it back into `ProviderSandbox#owner_workspace_id` and `owner_key`. A box with no record is matched by that owner, or else by the stopped `CodeBox` it outlived (its stop failed at the provider), as an `Operator::Sandboxes::Claim`. `Operator::Actions.sandbox_adopt_blocked_reason` refuses a box that is not rogue, carries no owner, names a workspace that is gone, or whose run holds another live box, and the serializer ships the sentence as the disabled Adopt button's tooltip, so an unmatched box is left with Stop and Delete. `SandboxInventory.adopt!` asks the provider to `reclaim` the box with a key the app knows (Docker and Northflank read the key it was started with, boat starts the image again in it with a new one, keeping its volumes), then under the run's `CodeReading.locked` lock writes a live `CodeBox` for the workspace and key, billed from when the box started running unrecorded (`box_started_at`, the provider's start or the old row's stop) at the provider's price for its size. From then on it is any other box: the run uses it on its next read, and the sweep stops it once unused for `CodeBox::ABANDONED_AFTER`.
- **What the sweep does on its own.** A box named like Firefight's that a provider still runs, that no live row knows and that started more than `CodeReading::ORPHAN_GRACE` (15 minutes) ago is stopped, as before. On boat a stopped box is deleted an hour later, a `halon-kept-` copy no row names an hour after it was made, and an image copy after a day. Nothing not named like Firefight's is ever touched, and everything else waits for an operator.

## Jobs

Flightdeck (`solid_queue-flightdeck`) is mounted at `/operator/jobs`, with `Operator::FlightdeckController` as its base controller, so every one of its pages runs both checks above. It reads Solid Queue's own tables. The test database has none, so tests prove the checks and not Flightdeck's pages.

## Incidents

`/operator/incidents` lists every incident across workspaces, newest first, with how many of its records failed (`Operator::IncidentProcess.problem_counts`: failed workflow steps, failed webhook deliveries and failed platform calls in its channel). One incident opens its whole process on one timeline, built by `Operator::IncidentProcess` from every table that records it: alerts and their routing, incident events, each workflow and its steps, webhook deliveries, failed platform calls in the incident's channel, and Halon's runs. It is read only. A failed step offers **Run again** and **Skip** (skipping asks first), and a failed delivery offers **Send again** (`WebhookDelivery#replay!`, a delivery of its own with the bytes sent the first time). The raw cause of a failure is folded under each record, and a Halon run opens its trace.

## Workflows

`/operator/workflows` lists every SolidWorkflow run, filtered by state and kind. The console reads the engine's records through `Operator::WorkflowRuns`, and ArchSpec allows only workflows, the engine and the console to name `SolidWorkflow`. One run shows its steps drawn from `depends_on` (`Operator::WorkflowGraph` puts a step one column after the last step it waits for), the selected step's attempts, time and last error, and every event the engine recorded. **Pause**, **Resume** and **Cancel** (which asks first) call the engine's own `pause!`, `resume!` and `cancel!`, and **Run again** and **Skip** its `retry_now!` and `skip!`, which bring a failed workflow back to running. Each is recorded on the workflow under the operator's email. The engine's `pause!` and `resume!` return nothing meaningful, so the state they leave is what the toast reports. Every action button is disabled while its request runs, so a double click does not act twice.

## Failed platform calls

`PlatformCallFailure` keeps every Slack API call that failed, written in `Slack::Client.noting_failure` around `api_get` and `api_post`, so every caller is covered and none can forget, and the client decides which answers are worth keeping. It keeps the endpoint, the error class and message, and the channel when the call named one, which is how an incident's timeline finds its own. Answers the app expects and handles itself (already in the channel, a channel name taken, already archived or not archived) are not kept. Recording can never break the call it records. Rows are kept for 30 days (`PlatformCallFailureCleanupJob`, daily).
